## Problem Statement

用户需要一名运行在自己服务器上的全天候私人助理，通过飞书处理日程、任务、备忘、会议准备、持续跟进和主动提醒。日常工作应构成完整闭环，不能仅提供聊天建议，也不能以手写识别取代常规助理能力。

用户特别重视纸质手写笔记的整理：笔记以中文为主，夹杂英文、待办和简单图示。识别可能误读或遗漏，整理也可能引入推断，因此原稿必须可回查，AI 生成与人工确认必须分清，飞书文档需明确标识具体内容版本是否通过本人审核。

用户希望在飞书统一交办，由一个 Lead 分派给不同专业 Worker，同时推进多个工作。一个 dsh 本地工作区拥有稳定配置、原生会话和结构化记忆；管理与维护在 dsh 中完成。所有业务 Agent 共用同一个飞书 CLI profile 和用户授权。查看、继续或停止某项工作不应干扰其他事项，重启后不能丢失已接纳工作或重复执行外部动作。

服务器已有 Docker 部署的 PostgreSQL，应用直接连接。方案必须复用已有 dsh 组件，避免另建会话引擎、Agent runtime、时间规则算法或 SQLite 业务库。

## Solution

将24私助作为常驻插件加载到服务器现有 dsh Host，使用飞书企业自建应用机器人作为首版唯一外部聊天平台，通过一个固定 CLI profile 操作本人授权的飞书资源。dsh 原生24私助会话也支持本人交办与维护。日常助理与手写个性化能力均为 v1 必交付内容。

助理持续完成收集、澄清、规划、执行、跟进、复盘和资料找回。飞书任务、日历与文档保留其业务权威地位；PostgreSQL 保存路由、委托、操作、审核、提醒与发送记录。确定时间的提醒可独立于模型发送，需要推理的晨报、复盘和周回顾复用原生 dsh Schedule 唤醒。

助理工作区 AGENTS.md 定义稳定规则及可校验配置；JSON 保存可检索的长期记忆。飞书接入会话与 dsh 本地助理会话均可承担 Lead 职责，按事项创建原生 continuable Worker，并按实际父会话回传。本地顶层助理会话还可维护配置与记忆，整理仅由本人发起。手写照片从飞书进入，形成可编辑草稿、指定待审版本、原稿引用和人工审核凭证；确认内容与执行候选行动分别授权。

成功表现为：日常工作能够完成并查证；至少五项独立工作正确委派、查看与继续；提醒有用且可控制；人工审核绑定具体版本；中断后可核对和续办；无法确认的状态明确显示。

## Implementation Decisions

### 1. 运行范围与组件所有权

- 首版单用户、一个固定飞书 CLI profile、一个活跃 dsh Host、一个完整飞书入站消费者；每工作区固定一个飞书接入顶层 Session，可另有多个本地24私助顶层 Session。它们按各自发起入口承担 Lead 职责；Worker 是按事项隔离的原生子 Session。可同时存在至少五项未完成工作，模型并发上限单独配置。
- 默认在现有 Host 中安装 24PA bundle 与专用助理 preset，共用 SessionController、Agent Registry、会话持久化、投影、附件、模型路由和工具机制。安装使用 dsh 的标准插件装配和生命周期。
- dsh 启动 profile、飞书 CLI profile、工作区与 Agent Session 是不同概念。飞书普通消息统一进入 Lead；事项路由不切换身份或 preset。
- 复用公开服务和包出口并固定兼容版本；不复制或深引私有调度 runtime。服务器实际版本和组合在开发获批后的 M0 核对。
- 常驻组合必须真正具备 SessionController、Schedule、会话持久化及其依赖。一次任务后退出的 headless 不作为全天候入口。插件卸载必须释放长连接、连接池、子进程和 worker。
- jobs-local 和现有 workflow 只能辅助当前进程执行，跨天审核与中断恢复以 PostgreSQL 工作记录为依据。

### 2. 领域模块与业务接口

| 模块 | 对外职责与契约 |
|---|---|
| FeishuChannel | 接收消息/卡片/资源事件，校验真实主体，向指定聊天发送带来源的结果；返回实际消息标识或结构化失败 |
| LeadCoordinator / WorkRouter | 接单澄清、委派、进度汇总；保存实际父会话、发起入口和固定结果目标，原生子 Agent 的接纳不等于完成 |
| WorkspaceConfig / MemoryStore | 注册工作区、校验 AGENTS.md；查询结构化 JSON、版本写入与人工发起的整理 |
| AssistantService | 编排任务、计划、会议、备忘、项目、个人清单和复盘；只提交有依据的领域请求 |
| ExecutionPolicy | 在实际工具执行入口检查主体、资源范围、授权依据、业务版本与操作编号 |
| LarkCliWorkspace | 将文档/任务/日历请求转为固定命令或必要的原生 API；明确身份，校验完整响应并返回对象链接 |
| NoteService / ReviewService | 管理原稿、转写、候选版本、指纹、疑点、审核凭证与派生行动；人工批准只由可信用户动作处理器执行 |
| ScheduleBridge | 将智能工作映射到原生 Schedule；为固定提醒调用公开时间规则；记录唯一执行归属 |
| DeliveryService | 认领到期发送工作，处理回执、重试、结果未知、取消、静默、过期和限频 |
| PaRepository / RecoveryService | 提供业务事务与版本检查，持久化工作进度，核对 dsh、飞书与发送结果后续办 |

第一版先组织为一个插件包中的清晰模块，不以微服务拆分为前提。未来消息平台适配与飞书工作空间访问可独立替换，但首版不开发第二平台实现。

### 3. 飞书身份、事件与外部操作

- 使用企业自建应用机器人和官方 SDK 长连接；CLI 负责其已封装的工作空间操作。所有 Session 固定使用同一个飞书 CLI profile；按资源操作明确选择用户或机器人身份。
- 主人通过受控配置或一次性绑定建立，核验应用、租户、用户与私聊关系；不将第一个发送者自动设为主人。
- 消息回调在平台时限内校验并向 PG 保存最小耐久 Inbox 后才 ACK。耗时识别、模型调用和文档写入在后续执行。持久化失败不得回报已接收。
- 固定 SDK 版本验证等待 handler 的行为，事件订阅与处理器必须完整；同应用不并行启动另一套不完整的 CLI 事件消费者。
- 业务请求使用固定参数和受控正文传递；模型不生成任意 Shell。CLI 未覆盖的接口才由同一适配层补充官方 API。
- 同时检查进程退出、JSON 业务结果、警告和部分成功；只有返回了明确结果并完成必要回读，才报告该阶段完成。
- CLI 独自管理同一 profile 的用户令牌续期。授权失效进入需要重新授权状态；仍可用的机器人链路可报告降级，不创建竞争刷新器。
- 文档/任务/日历仅操作用户选定范围。明确本人指令无需重复确认；推断出的行动和建议变更需获得对应选择。对外消息、邀请和分派需要明确指令。
- 笔记、文档和引用历史都是输入材料，不是更高权限指令。终端、通用文件与委派工具（含 ralph 与外部 CLI 委派）仅在本地24私助会话的角色白名单内开放；飞书接入会话与 Worker 不获得 Shell，预设与执行器共同限制安装和动态扩展能力。

### 4. 日常助理的业务行为

- 飞书任务和日历是实际对象的权威来源。业务库保存关联、同步水位、建议计划、等待项和执行记录，不形成第二套无法同步的任务事实。
- 截止日期、计划时间、估时和完成状态分别记录。日历被占用不代表任务完成；时间已过不代表会议已参加。
- 每日规划遵守工作时段、缓冲和明确偏好，输出容量与冲突说明。采纳后仅执行选定变更，保留实际外部结果。
- 目标拆解、子任务、重复事项、等待跟进、项目下一步、个人事务清单、会议前后工作属于首版。重复能力优先使用飞书现成接口；不满足所需规则时，按模板与唯一发生实例创建普通任务。
- 无权读取等待对象回复时，只按检查点询问本人状态。会议纪要只基于用户提供或明确授权的材料。
- 备忘与历史回答给出来源、时间和审核状态；资料不足明确报告。未审核转写不自动晋升为确定事实。
- 偏好只保存明确告知或确认的内容，支持查看、修改、删除和有效期。各 Session 按需访问共享事实，不自动拼接全部历史。

### 5. 工作区、Lead/Worker、路由与并行

- dsh 仅提供一个产品预设「24私助」，兼具事务协调、工作区维护与标准模式完整编程能力（1.3）。预设携带标准预设的插件全集并追加 pa24 业务插件；角色白名单决定各入口实际可见工具。默认对话按钮恢复该工作区绑定的本地助理会话，主人也可在同一工作区新建采用此预设的会话。飞书接入会话单独持久绑定，负责飞书消息与业务 Schedule；二者均通过 SessionController 创建/恢复，共享工作区事实而保留各自历史。路径复用原生 WorkspaceRegistry 与目录入口，AGENTS.md 经原生 instructions 插件加载。
- AGENTS.md 包含稳定工作规则与一个结构化配置块，指定 profile、主人、资源范围、时区、Worker 能力目录、并发和模型路由；秘密只引用环境/凭据服务。加载器严格校验后应用，失败保留旧配置。维护通过原生会话编辑、校验和重载；不覆盖已有文件。
- 固定专业职责至少包括日程、待办/项目、提醒、备忘/资料与手写。Lead 按输入明确委派，跨能力输入可创建多个 WorkItem；收到工作接纳回执与最终结果分开汇报。
- Worker 使用原生 continuable child API，WorkItem 保存 origin（飞书/dsh）、parentSessionId（实际父会话）、childSessionId 与固定投递目标。workspaceLeadId 单独表示飞书接入会话，不可代替本地事项的 parentSessionId。子 Agent 继承 cwd/preset，运行时按可信父子关系与角色限制工具；手写识别没有批准和外部行动工具，默认禁止 Worker 再递归创建 Worker。
- 专业 Worker 是能力类型，每项工作是隔离的子会话；明确修订/继续恢复原 child，完整聊天不自动跨事项拼接。长期背景来自按需读取的 JSON 记忆或带来源的资料。
- 飞书新消息先入 Lead；明确事项或引用消息固定到原 WorkItem，冲突或指代不清就澄清。旧卡片始终绑定原对象和版本，后台结果带事项来源，无全局 A–E 当前指针。
- Lead 输入默认 queue；本人明确补充/停止才 steer/interrupt。Worker 有界并发，其余事项排队；查看一项工作不会停止其他事项。工具每次检查 WorkItem 是否仍可执行。
- 相同飞书资源的写入按资源协调，写前读取最新状态和版本，完成后刷新投影；不同资源可并发。内部锁不等于远端 CAS。
- dsh 管理面板查阅状态、配置与记忆正文，所有对话按钮进入同一个24私助入口。事务交办与配置/记忆维护均在本地原生会话完成；飞书仍是日常移动端文字、拍照和版本审核入口。原生 Worker 会话供查看与诊断，业务续办经协调工具定位实际父会话，保持授权与事项账本一致。
- 结果回到已验证的发起入口：本地事项经真实父会话接收，飞书事项由其接入会话汇报。仅本人明确委托的提醒/订阅按约定发往飞书；本地事务结果、维护输出和宿主其他会话不自动广播。跨会话查看/续办必须核对同一工作区、主人及原父子映射；知道会话 ID 不构成授权。
- 权限由宿主核验的入口、实际父子关系、工作区与当前角色决定。绑定工作区的本地顶层24私助会话可以使用受限配置/记忆写工具，并携带标准模式编程工具全集（bash/pwsh 按平台择一、read/write/edit/read_image/glob/grep、jobs、skill、goal、plan-mode、压缩、todo/web/present、subagent/subagent_fork/workflow、ralph；codex/claude-code 外部 CLI 委派需 provider 安装后经 extraLocalTools 显式开启）；飞书接入会话与 Worker 维持业务白名单、只检索记忆。同一 preset 或 persona 文字本身不授予维护权限，子 Agent 继承预设不会继承本地维护授权。tool-schedule 不并入预设，提醒统一经 PostgreSQL 账本。
- interrupt 只停止运行，不代表撤销成功写入或删除持久任务。归档先核对运行工作和绑定 Lead 的原生计划，默认拒绝不安全归档；显式停止并归档回读部分成功，不自动重建已删除计划。
- 新 Worker 通过职责/输入/工具权限/输出契约与模型路由注册，使用相同工作账本、记忆、授权与结果通道；不增加新的总控运行时。

### 6. PostgreSQL 与数据边界

直接连接现有 Docker PostgreSQL，使用独立 schema 或表前缀、受限服务账户和有界连接池。不使用 SQLite，也不提供不可用时静默退回内存或 SQLite 的写路径。容器与宿主网络地址按实际部署配置，不假设容器内 localhost 指向数据库。

| 数据组 | 权威内容与约束 |
|---|---|
| 工作区绑定与配置版本 | 主人、固定 profile、资源范围、Lead 归属和配置摘要；配置权威为 AGENTS.md，个人长期记忆权威为 JSON |
| Inbox 与 MessageRoute | 平台事件/消息唯一键、接收顺序、原始输入引用、固定会话目标 |
| WorkItem 与 RunReceipt | 委托、origin、实际 parentSessionId/childSessionId/职责关联、固定投递目标、请求标识、dsh 消息/turn 关联、已完成阶段、取消原因、恢复代次 |
| ActionOperation | 授权依据、参数、幂等键、外部对象标识、成功/失败/未知与核对结果 |
| ReminderRule、Occurrence、Outbox | 规则及唯一执行归属、来源版本、发生点、期限、认领 lease、尝试次数与平台回执 |
| NoteRevision 与 ReviewReceipt | 具体内容快照、原稿/正文摘要、疑点、人工主体、版本、决定和时间 |
| SyncCursor 与资料索引 | 授权范围、完整同步水位、最近成功、新鲜度、可回查的外部来源 |

- 业务变化与对应 Outbox 在同一 PG 事务提交；例如人工审核凭证、版本状态和文档标识同步意图共同成功或失败。
- 外部网络调用在短事务之外执行。worker 先认领并提交，再调用外部 API，最后按 claim 版本保存回执；数据库失联后停止领活。
- 唯一约束、预期版本和短事务锁控制业务并发。可使用跳过锁定行的队列领取机制，但不把它当完整业务查询。
- PG 事务不覆盖 dsh 日志或飞书 API；lease 也不能消除远端成功后、本地回执保存前崩溃的窗口。结果未知必须核对。
- dsh 原会话日志、附件和原生 Schedule 域沿用其已有非 SQLite 持久化。本地出厂是 JSONL/JSON；不把重写 PG Session 或 KV provider 作为首版前提。
- storageDomain 仍是单 Host 缓存与串行 KV 写入，不因底层换数据库就获得跨表事务或多活一致性。24PA repository 不旁路改写已打开的 dsh 域数据。
- 既有 Session 查询 provider 可使用 openAt: never 保留精确读取和列表，禁止 SQLite I/O，全文索引搜索明确禁用。资料检索由飞书与业务索引支持；不为包名重写查询系统。
- 大图与大快照保存在受控附件/对象存储，PG 保存引用与哈希；不能只备份 PG 而遗漏原稿。数据迁移必须有版本和明确恢复步骤。

### 7. 会话及外部动作的恢复

- 分别恢复工作区/Lead 绑定、子 Agent 聊天上下文、已收委托和外部动作。恢复 Session 不代表工具进程从中断指令位置继续。
- 准入流程先耐久保存原输入与目标，再提交给 SessionController、执行 Session flush，随后保存回执。accepted 仅表示准入，不是持久完成或任务完成。
- 稳定 requestId 配合 PG 去重和按 Session 串行准入；重启先核对日志与回执，不依赖单一请求标识保证跨系统 exactly-once。
- 已经领取或部分执行的工作使用明确恢复代次续办缺失阶段。已完成结果只补发送；已完成工具不从日志重新执行；外部写入未知时先核对远端。
- 优雅 teardown 也可能清掉 dsh inbox，故已接纳承诺保存在 PG。停机停止接纳、保存恢复状态并尽量排空；区分用户取消、停机中断和结果未知。
- 原生 child 完成消息不是耐久父邮箱；父 Agent 未存活或通知窗口丢失时，由 PG 结果账本补交原 parentSessionId，并按 origin 补回对应入口；不一律转投飞书 Lead。不能只依赖进程内 catalog。冷读采用查询、投影与历史页；follow 可能激活 Agent，不能用于无副作用的批量查看。resolveAgent 也不被当作保证排空旧队列的 wake-only 方法，唤醒路径须通过真实组合验证。
- 恢复先加载 Lead 与未完成事项映射，按需恢复其原生 child；不批量激活所有历史 Session。持久化损坏、会话缺失或 writer 争用给出可操作状态，不复制同 ID 会话或强抢写入权。
- 旧备份恢复后核对飞书实际状态与附件完整性，确认后才继续发送或写入。

### 8. 主动工作、Schedule 与可靠投递

- 晨报、晚间复盘、周回顾和其他推理型周期工作完整复用原生 Schedule 创建、恢复及顶层 Lead 唤醒，随后由 Lead 委派。原生 Schedule 拒绝 child Session，不能直接挂在 Worker 上。
- 会议、截止和一次性模板提醒复用 dsh-schedule 公开规则创建与 recurrence 函数；PG 保存发生实例并由 Outbox worker 直接投递。24PA 不另写 cron、DST 或通用调度平台。
- 每个业务规则只有一个执行归属：原生 Agent Schedule 或直接投递。日历重复实例优先采用飞书返回的实例，不用近似 cron 重解释日历规则。
- 原生 Schedule 成功仅表示已持久化投递到 Session inbox。24PA 单独跟踪智能工作是否完成及结果是否进入发送队列。
- 保存业务计划、原生 schedule、Lead Session 和稳定业务标识的映射。创建结果未知时按明确标识和规则核对，不能根据标题相似盲目认领或重建。
- 当前 Schedule source 没有独立结构化 occurrence 标识；关联使用 Lead 内持久消息、规则标识与公开投递历史；多规则共享 Lead 时不能仅凭会话 ID 判断归属。回执等待有上限，历史写入失败时进入 delivery_unconfirmed。
- 无法证明归属时暂停结果发布及外部写入，核对规则、会话和 PG 工作记录；仍无法确认则过期或请求处理，不能用当前时间猜发生实例或无界重投。
- 确定性提醒产生唯一 occurrence 与 Outbox，再推进规则。来自多个 Session 的同一业务提醒按主人、来源、版本、发生点和渠道去重。
- 发送状态区分待发、发送中、平台接受、待重试、未知、过期和需处理。保存平台消息标识；发送成功不推断已读或事项完成。
- 网络、限流与临时错误按有界退避重试，权限问题请求重新授权，响应丢失先按接口幂等能力核对。平台去重窗口与卡片有效期不能当作永久业务保证。
- 日程/任务同步要完整处理分页、增量水位与游标失效；事件触发刷新，兜底轮询保持收敛。发送前复核来源状态，取消/改期使旧实例失效。
- 数据不新鲜时说明依据或报告同步异常；改期与发送竞态可能产生已发旧提醒，需关联更正，不作绝对零竞态承诺。
- 触发点保存 UTC，同时保留 IANA 时区和原表达。固定本地时刻与每隔固定小时区别处理。停机后只补仍有用的实例，过期消息合并或记录错过。
- 晨报、复盘等由用户开启；安静时段、限频、稍后和原生提醒协调可配置。用户明确预约的提醒如何覆盖静默策略，在设置回执中说明。

### 9. 手写处理与飞书文档

- 首版接收 JPEG、PNG、WebP 图片；明确批次、页序、消息来源与资源摘要。文件大小、页数、解码、并发与预算有界。
- 原件指飞书实际传回的字节；可能不等于相机原始文件。先保存原始字节与哈希，再生成方向修正、整页和裁片识别副本。
- 通过 dsh 已有视觉路由和附件调用识别模型，主助理模型与识别模型可分别选择。真实路由、账号与中文手写表现须实测。
- 流程包含质量检查、页面布局、区域转写、结构化候选、独立整理、规则核对、写入和回读。转写、摘要、推断、疑点与候选行动分别表示。
- 坐标保留裁剪/旋转映射并区分可靠、估计与页级引用；不把模型估计框当精确字框。图示保留原图加说明。
- 关键日期、人名、数字、责任人、否定词与复选状态突出复核；自报置信度不作为准确概率。相对日期保留原话及解释依据，未知内容不补成事实。
- 飞书文档包含整理摘要、正文、候选行动、疑点、逐页转写、原图索引及修订记录。所有必须部分完成写入并回读后才通知进入审核；部分失败保留可恢复阶段。

### 10. 人工审核、版本与行动项

- 一份可编辑草稿配合按需发布的指定待审版本。审核卡分别提供查看待审版本与编辑草稿入口；服务器保存不可变快照。
- 快照指纹覆盖正文文本、结构顺序、标题、行动字段和资源摘要；只排除已登记的系统状态块，不按任意标题排除正文。新副本的 block 标识、远端 token 和渲染时间不影响正文等价判定。
- 版本文档写后回读，并核验资源。分页读取固定同一 revision；读取期间变化、历史权限不足或资源不支持时不形成混合版本的完整审核结论。
- 首版模板限制为已验证文本、列表、基础表格和图片。后来插入的同步块或动态外部资源必须形成可核验快照，否则阻止整稿批准并说明原因。
- 按钮动作绑定主人、租户、笔记、版本、内容哈希、有效期和不透明动作标识；重新校验事件主体、权限、版本、草稿与待审内容。模型没有人工批准工具或任意修改账本能力。
- 批准/退回在 PG 事务内作版本条件裁决；保存凭证、状态及同步意图。重复动作返回原结果，冲突或过期动作明确拒绝。
- 疑点须修正、删除或明确保留原稿不清；保留未知不转成自动行动。审核凭证记录准确版本、原稿依据、审核主体和时间。
- 飞书显示版本限定的人工审核状态。凭证已保存但投影未更新时说明同步中并恢复；文档和 PG 没有跨系统原子事务。
- 文件编辑事件与轮询核验当前正文为 matches、changed 或 unknown；读取为可信知识或生成行动提案前再次核验。历史批准事实保留，但不覆盖后来改动。
- 飞书版本参数不当作已证明的严格 CAS，文档 ACL 也不构成绝对不可变保证。当前状态无法验证时不能继续宣称最新全文已人工通过。
- 审核内容与执行行动分开记录。选中行动并明确授权后按笔记版本、行动标识与操作键创建任务/日程；重复执行返回已有对象。后续修改影响外部对象时提出变更建议。

### 11. 就绪、数据与运维

- 能力就绪检查覆盖必要插件、PG、入站连接、CLI 授权、同步与发送队列；宿主进程活着不等于全部助理能力可用。
- 单一模型故障只影响需要该模型的工作；固定提醒继续。PG 或发送链路不可用时暂停相应操作并保留可恢复状态。
- 正常运行保持一个活跃 Host 和一个入站消费者，部署互斥与卸载清理防止重复运行；不承诺多活。
- 用户数据会经过飞书、用户服务器、选定模型服务并回写飞书。普通模型输入与额外原始日志上传分开说明；同 Host 全局日志开关的影响须显式列明。
- 备份覆盖 PG、会话日志、原稿、审核快照和必要配置，恢复先核对外部状态；只恢复数据库表不足以完成恢复。
- 监测积压、发送延迟、同步新鲜度、失败、待核对操作、预算及数据库/磁盘状态。完全离线告警复用独立服务器监控。
- 保留期限、每批输入、模型并发、重试与费用均可配置；触及预算时保留已完成内容、暂停相关识别并说明。

### 12. 结构化记忆与会话维护

- JSON 是记忆唯一可编辑权威，AGENTS.md 保存稳定规则；PG 保存业务运行事实，dsh 保存完整会话。记忆不等同聊天历史或上下文压缩。
- 文件有 schemaVersion/version 与单调 revision，记录有 id、类别（偏好/事实/项目/决定）、主题、内容、出处、来源版本或指纹、confirmed/unverified 状态、有效期、更新时间、修改人及理由。
- Lead 与获准 Worker 按关键词、类别、主题、状态检索，结果有界且带来源；只把相关条目放入本次上下文。不能把未审核笔记变成确定事实，也不因多次引用自动提升状态。
- 写入口位于绑定工作区的本地顶层24私助会话，与交办事务共用预设和会话入口。新增、修改、删除和整理必须基于本人指令；先查 revision，再以 expectedRevision 和指令依据提交。飞书接入会话与所有 Worker 不具有写权限。文件更新使用原生 fs 原子发布与文件版本条件，同一工作区只允许一个活动写进程。
- 原型按条目提交，正式版提供可查看/撤销的修订记录与明确变更集；批量整理中的重复、冲突、过期项说明来源，矛盾不能默默覆盖。删除不留可被继续检索的已删除正文索引。
- 文件手工变化在下次读取可见；校验失败明确报错，绝不自动清空或用缓存假装成功。查询索引如存在，只是 JSON revision 的派生物，可丢弃重建，不能第二处编辑。
- 记忆整理仅由本人在工作区会话发起；没有定时、空闲、后台自整理或自动采集入库。业务提醒/晨报与记忆整理分开，前者仍可按本人设置自动运行。
- 记忆与配置随工作区备份，恢复检查 schema、revision、来源与过期状态；不把恢复的旧记忆无条件覆盖较新文件。

- 顶部以24私助身份和对话主操作为重点，工作区路径为次级信息。Lead/Worker、技术 ID、完整 JSON 与调试信息按需展开；不要求用户先选择内部角色。

- 长连接已启动、平台已接收、身份已核验、资源可读和可写分别显示；未知/未检查不显示为通过。CLI profile 缺失不自动改用其他 profile。配置文件变化须指明当前展示的是哪个生效版本。
- 使用一致的 SVG 图标与语义配色，状态同时提供文字/图标，避免仅凭颜色区分。五类能力允许各自色彩；错误、待确认、处理中和完成状态全局一致。具体色值为视觉实现选择，不作为业务契约。
- 跟随 dsh 明暗主题，桌面与 390px 窄视口均可阅读；卡片适应实际面板宽度，只有导航等明确区域可横向滚动。主操作、正文和字段保持足够对比度，长路径和长正文不撑破布局。
- 页签有明确选中状态、语义与可见焦点，可用方向键、Home/End 切换；图标按钮具有可访问名称。触控操作保持可点击面积，装饰动画尊重 reduced-motion。
- 加载中、空记录、无匹配和读取失败分别呈现，失败保留可操作重试，不冒充零条数据。工作区切换、查询变化与离页时避免旧请求覆盖新结果；连接中断时明确标识上次读取状态。
- 面板打开、搜索与刷新均不得隐式启动模型、派发 Worker、写飞书或整理记忆。真实模式与体验模式明确标识，示例数据仅用于隔离验证，不能填入主人的工作区制造就绪或完成状态。

### 14. 仓库指引与助理配置

仓库根 AGENTS.md 指导开发协作和查阅文档；主人选择的助理工作区 AGENTS.md 才是运行规则与接入配置。两者用途独立，不把仓库说明当成生产配置加载。模板创建保留已有文件，非秘密配置经校验再生效；原型的模板、默认值与存储位置不自动成为正式版迁移契约。

## Testing Decisions

### 已确认的主测试边界

用户已确认：主测试通过真实 dsh Loader、会话与 PostgreSQL，模拟飞书消息/卡片输入并检查最终业务结果；仅替换模型、外部网络和时钟等边界，再以真实飞书租户与 30–50 页手写样本验收。

主要产品测试从飞书渠道的消息、资源或卡片动作进入，经过真实插件装配、路由、会话、业务事务及发送流程，观察最终对用户可见的结果。同一真实宿主内补充本地24私助会话的交办/维护与管理面板验收，验证来源隔离、权限和展示；不另建替代业务测试 runtime。复用公开服务、Loader 和现有测试支持。

- 保留真实业务模块、dsh Agent/工具/Session 机制、事务和迁移；自动化测试使用隔离的真实 PostgreSQL 数据库或 schema、独立会话和附件数据。
- 模型响应、外部飞书网络与时间由可控边界提供回放、延迟、错误、重推和时钟推进；不把整个业务服务替换成自报成功的 mock。
- CLI/SDK 的固定版本另做接口契约验证，真实租户烟测证明身份、令牌续期、图片、文档、日历、任务和消息 API 可用。离线桩不能替代平台能力验证。
- 原始主入口经过真实 Loader 与预构建发布包各有集成验收。不得仅用手工挂载插件的单元测试证明可部署。
- 测试只断言外部行为、权限拒绝、持久结果、消息路由与可观测状态，不锁死内部函数调用顺序、私有字段或类拆分。
- 用实际飞书对象/消息或外部测试端读取结果，不能只匹配 Agent 自述的“已完成”。会话记录和数据库状态用于验证持久性、去重与审批凭证。
- 快速的纯逻辑用例仅用于必要的新业务规则边界；不复制 dsh 已有 cron/DST 算法测试。回归测试必须能在相关行为被破坏时失败。

### 需要覆盖的模块与验收行为

| 测试组 | 模块与观察点 | 必须成立的结果 |
|---|---|---|

### 可复用的既有测试先例

下列 dsh 测试与支持能力作为正式版测试模式参考；本轮可丢弃原型的一次性真实宿主验证单列验收记录，不等于正式版测试完成：

| 既有先例 | 24PA 采用的方式 |
|---|---|
| dsh testing policy、loader-smoke、发布 profile 的真实组合测试 | 使用真实装配入口和构建产物，在隔离环境中验证用户/持久结果；辅助函数以公开能力复用 |
| SessionController 的 cold merge、cold history、并发 resume 去重 | 验证列表/查看不会激活历史会话，明确继续时才恢复执行 |
| SessionController 的 inbox projection、control queue、archived-session gate | 验证排队来源、冷/热状态、取消、归档门禁和插件卸载清理 |
| Schedule 的 domain restart、serial delivery 与 delivery history | 验证原会话绑定、重启、最近错过实例、投递回执与时钟回退的可观察行为 |
| Agent loop 的 shutdown drain、resume 与 Session 持久化测试 | 在 flush、关停、中断点前后重启，对照持久事件与业务回执 |
| 附件原文件保存和图像 normalization 测试 | 分别验证原始字节保留与识别副本变换，覆盖方向和缩放；不把规范化图当原稿 |

### 故障、质量与发布门槛

1. 故障覆盖重复/乱序事件、PG 提交前后退出、Session flush 前后退出、优雅关停清 inbox、外部成功但响应丢失、模型停用、授权过期、限流、会议改期竞争、审核期间编辑、Schedule 回执永久缺失、误启动第二 Host 及旧备份恢复。
2. 每个测试拥有独立数据库命名空间、会话、文件、端口与进程清理；重启使用真实持久介质。并发运行不能依赖共享可变测试数据。
3. 手写先用获准提供的约 30–50 页样本，覆盖中英混排、人名/数字/日期、否定和勾选、潦草小字、简单图示、多页及模糊/缺页。将调优样本与留出评测样本分开，报告字符错误、关键字段错误/漏检、行动项误提取/遗漏、人工复核时间、时延与费用。
4. 当前不承诺未经测量的识别准确率；依据样本结果确定可接受阈值，再作真实使用验收。所有疑点可回查、无人工动作不能批准、未知项不得自动执行是硬性约束。
5. 健康依赖条件下，固定提醒从到期到平台接受的 P95 初始工程目标不超过 60 秒；记录样本数和故障条件。平台接受、已读和完成分别统计，不承诺跨系统 exactly-once。
6. Lead 与至少五项原生 Worker 工作的完整交互、工作区/JSON 记忆维护、固定 profile、无 SQLite I/O、人工审核版本约束、重启续办和必要外部接口实测必须通过。缺少真实授权或视觉评测时标记未验证，不能以离线通过宣称完整验收。
7. 连续试运行覆盖至少一次周回顾、真实日程/任务和手写材料；发布记录包括复用组件、已测版本、剩余限制、恢复结果与运行成本。

## Out of Scope

- 本次修订不授权正式版实施、创建生产飞书应用、修改服务器、连接生产数据库或上线。另行授权的可丢弃原型见验收记录。
- 定期/自动记忆整理、模型自行长期记忆入库、飞书端第二套记忆编辑界面。
- 多用户、群聊协作、第二聊天平台、多个飞书 CLI profile 切换及多账户管理。
- 任意既有 coding 会话的接管、改变其锁定 preset 或从飞书开放通用 Shell。
- 单会话由多个 Host 同时写入、主动多活、重写 dsh Agent loop、完整会话存储、cron/DST 或通用工作流引擎。
- 为统一存储而默认迁移 dsh Session/Schedule 到 PostgreSQL，或为包名而重写整个查询系统；首版只要求不使用 SQLite 数据库。
- 自动读取所有组织聊天、无授权对外催办、自动监听或转写会议录音、邮件渠道、订票/支付/自动购买。
- PDF、HEIC、复杂公式和复杂图示的专门处理，默认双 OCR/VLM 全量识别，未经验证的精确图示重绘。
- AI 自行人工批准、将审核通过视为全部行动授权、对可编辑云文档作绝对不可变承诺。
- 保证所有网络与平台故障下的零重复/零延迟、把消息发送成功等同用户已读、未经真实样本验证的准确率承诺。
- 全量向量库、Redis 和微服务平台作为首版前提。数据量或实际需求证明必要后另立规格。

## Further Notes

### 术语与规格依据

业务名称由[术语表](../GLOSSARY.md)定义，历史「24PA 机器人」「24PA 工作区维护」不是额外产品或当前独立预设。实现中的会话指原生 dsh Session，固定 profile 指飞书 CLI 配置；这两者不随页面切换或产品更名改变。

规格继承第一轮审核、Docker PostgreSQL 直连说明与 Q1–Q6，纳入已确认的统一预设、记忆正文、SVG/配色反馈及正式命名；设计对应 v0.4。旧 A–E 指针与独立维护 preset 均已取代。源码研究基线为 dsh 0.2.1-alpha.1、提交 5badb15009ae1756c3afe0ae0cef1faafc290ccc；它不等于服务器版本。测试边界延续用户已确认的真实 Loader/Session/PostgreSQL 和真实手写样本验收。

### 交付顺序与执行门槛

正式开发获批后按[12 个功能 PR 计划](planning/24PA-v1-PR交付计划.md)及已发布工单依赖交付。M0 兼容性至 M5 试运行仅是阶段说明；每个 PR 都要交付可独立使用的用户流程，不按一票一 PR，也不按数据库层/接口层拆空壳功能。

M0 核对实际 dsh/Node/SDK/CLI/模型版本、Docker PG 网络和权限、飞书资源范围、固定 profile、既有插件与持久化配置、真实 API 限制。工作时段、静默、会议提前量、轮询频率与预算按部署配置落定；整体方案中的初始建议不冒充用户已确认的个人偏好。

规格最初由 to-spec 发布并标记 ready-for-agent。44 张实施/验收工单已按用户后续 to-tickets 指令发布；本轮校准既有票的正文与覆盖关系。标签和文档同步不替代用户对正式版实施、生产配置或部署的另行授权。

GitHub [Issue #1](https://github.com/benz-ai-x/dsh-24-PA/issues/1) 是父规格，本文为仓库对应版本；更新时同步两处正文及工单覆盖。原型代码和体验证据由 [Issue #2](https://github.com/benz-ai-x/dsh-24-PA/issues/2) 跟踪，历史验收中的旧名称保留为当时事实。

当前为 44 张工单：43 张实施票归入 12 个功能 PR，P40 / #46 跟踪整体发布验收。新增 UI/UX 与命名验收归入既有功能，不新建第 13 个功能 PR；原型不计入生产 PR。
