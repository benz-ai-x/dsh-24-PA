## A1 · V05：SQLite 备份必须来自同一一致性快照

**现象**：DB 文件复制后，外部 reader 退出并切换 WAL 代次，备份继续复制新 WAL；恢复缺少备份前已提交行，但 `complete=true`、`integrity_check=ok`。源账本仍保有该行。

证据：[结果](../research/evidence/2026-10-20-main-final/pa24-backup-complete-result.json) · [复现](../research/evidence/2026-10-20-main-final/pa24-backup-complete-probe.mjs)。源码：[sqlite.ts:374](https://github.com/benz-ai-x/dsh-24-PA/blob/0ef85772a10f45e8e3b4c4d2c85d7249bf28e256/packages/24pa/src/sqlite.ts#L374)，联合备份入口为 `backup.ts`。

- [x] 核实支持的 Node/SQLite 版本具有哪些可靠快照能力，确定可验证的一致性方案。不能把分别复制 DB 和之后的 WAL 继续作为成功回退。
- [x] SQLite adapter 收拢快照、busy 处理和失败清理；联合备份 module 只在该一致性承诺成立后报告成功，明确业务账本与其他在线文件的一致性范围。
- [x] 读取、快照或写目标失败时报告失败/不完整；保留源账本及既有有效备份，不生成误导性的完整结果。
- [x] 复现“持有 reader → DB 读取 → reader 退出 → checkpoint/WAL 换代 → 新提交”，恢复后必须包含快照开始前已提交标记，且不能拼接不同时间点的业务状态。
- [x] 覆盖无 WAL、checkpoint busy、并发写入、目标写失败；执行实际恢复后比较业务行和关键关联，不能只看摘要、文件数量或 `integrity_check`。
- [x] 回归联合备份所需集合、既有凭据排除和 PostgreSQL 备份；V21 的重叠目录凭据问题仍独立保留，不因 V05 修复自动关闭。

## module 设计约束

| 功能组 | depth、seam 与 adapter | locality / leverage 与 deletion test |
| --- | --- | --- |
| A | SQLite/PG 两个真实 adapter 支持账本 seam；备份 module 保证快照承诺，接纳 module 保证归属；暂不指定 interface 形状 | 调用者无需自行拼文件或猜账本归属。删除承担责任的 module 后，恢复及接纳规则会散回调用者，说明其 depth 有价值 |
| B | WorkItem module 的 implementation 收拢完成证据、原归属、重试与恢复；测试和调用者走同一 interface | locality 集中在生命周期；leverage 覆盖事件、重启、关闭。删除后这些规则重新分散到各调用者，不能以增加转发函数代替 |
| C | 飞书/企微 adapter 满足原操作恢复 seam；手写待审版本 module 保证同源。保留两种领域责任，不强行统一 interface | locality 分别落在版本和操作记录；leverage 覆盖首次执行及恢复。删除后调用者又需判断版本/渠道，说明需要收拢责任 |

保持 ADR-0001 的发起入口、父子关系、固定回传目标和权限语义；F45 时钟提醒仍由日历 App 原生送达。本轮不引入新的调度引擎或权限入口。
