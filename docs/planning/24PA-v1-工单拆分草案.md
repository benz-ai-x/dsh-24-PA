# 24PA v1 工单拆分草案

日期：2026-10-05。父规格：[Issue #1](https://github.com/benz-ai-x/dsh-24-PA/issues/1)。状态：等待用户确认拆分，尚未创建实施 Issues，未开始开发。

已回读父规格全文及评论：正文与本地规格一致，当前无评论；仅有父规格 Issue，未发现已有实施票。本文的 P01–P40 是临时工单编号，父规格 T01–T16 是测试组，发布后以实际 GitHub 编号建立依赖。

建议 40 张完整流程工单，覆盖父规格全部 100 条用户故事与 22 个场景。每票将入口、必要持久状态、真实外部结果/展示与测试一起交付。当前只有设计文档，无前置重构事项；P01 是可验证的部署者启动/诊断流程，并非单独搭一层数据库。

每票的验收条件聚焦一个可演示流程，按一次独立 Agent 工作上下文控制范围。基建随首个使用它的业务流程建立；例如 P08 以本人任务建立外部写入和核对契约，P14 以备忘建立文档读写，后续票复用。恢复、授权与关键故障随各票验收，P40 做全量真实整合与发布验收。

用户已确定按可用功能交付 PR。40 张 Issue 用于实施拆分，当前建议组合成 12 个功能 PR，另以 P40 跟踪整体发布验收；分组、依赖和合并标准见 [PR 交付计划](24PA-v1-PR交付计划.md)。同组 Issue 共用功能分支和 PR，完成一张票后继续组内工作。

本轮请求确认工单颗粒度、功能 PR 分组与依赖，批准发布不等于授权开发。父规格 Issue #1 的正文、状态、标签和评论均不修改。

## 编号清单

1. **P01 · [启动常驻插件并检查 PostgreSQL 与宿主就绪](ticket-drafts/P01.md)**

   **Blocked by：** 无。

   **交付：** 部署者通过标准 dsh 装配启动 24PA，并获得可读的依赖、数据库和插件状态；可安全停止与重载。

## 推荐实施顺序与可并行范围

编号采用拓扑顺序方便发布，不要求全部串行。实施按功能 PR 组织：同组前置在功能分支验收通过后可推进，跨组依赖等待相应功能合并；完整规则见 PR 交付计划。当前仍需另行开发授权。

- 首个闭环：P01 → P02 → P03，证明常驻、绑定、可靠收发与真实会话。
- P03 后可分别推进会话、任务、日历查询、备忘、偏好、提醒和原稿收集；不因为都叫“基础能力”就互相阻塞。
- 多会话的查看/切换是 P04；旧消息路由 P05、控制 P06 和恢复 P07 分别验收。
- 手写首个可见成果是 P28 + P14 → P29；视觉增强 P30 与版本审核 P31 可并行，审核后的失效/提醒/执行再按实际前置推进。
- 原生智能 Schedule 的 P24 独立复用 dsh；固定提醒 P18/P20 用其公开时间函数，没有互相重复拥有同一规则。
- 日常排程、项目推进、会议秘书、复盘与待审收尾均属 v1，不是放到后续版本的可选项。
- P40 汇合分支末端作为发布门槛，不把所有祖先重复列为直接依赖。
