## What to build

主人主动在本地24私助会话要求整理指定记忆，先看重复、矛盾、过期项及建议变更，再应用或撤销可核验的变更集。

**功能 PR：F02 · 并行事项与记忆维护**。本组 8 张实施票共用一个功能分支及 PR，一个 PR 交付一个可用功能，不按单票建 PR。

同组前置在该功能分支已有提交且验收通过即可继续，前置票可保持打开；跨组代码依赖须等对应功能合并并通过验收。本票在所属功能合并且验收通过后关闭。

该功能合并前置：F01 工作区助理与随手记。

**依赖理由：** P36 及其前置提供版本化维护、修订记录和一致查询；本票补齐批量变更集及撤销的完整用户流程。

**覆盖规格：** 用户故事 105, 106, 107, 108；测试组 T18, T19。

**验证边界：** 使用真实 dsh Loader、原生 Session/Agent 与隔离 PostgreSQL；仅替换模型、外部网络和时钟。观察真实工具执行、持久状态及最终用户结果，不以模型自述或内部调用顺序代替验收。构建产物、权限、重复、部分失败、重启和必要迁移/恢复说明随本票交付；相关真实飞书/模型验证另记实测或未验证状态。

## Acceptance criteria

- [ ] 整理只由本人维护指令触发且范围明确；没有定时、空闲、后台自整理或自动采集计划，业务晨报不会调用记忆写入。
- [ ] 输出带来源的变更集，分别列出去重、冲突、过期和保留项；相互矛盾事实不默默覆盖，未确认内容不自动提升为 confirmed。
- [ ] 依据本人指令范围应用；需选择的冲突先澄清，使用 expectedRevision 原子提交整个变更集，竞争修改时重新核对，不能留下半批结果。
- [ ] 可以查看历史差异并明确撤销某次变更；撤销也产生新 revision，遇到后续更改冲突不覆盖较新内容，已删除正文不混回当前检索。
- [ ] 演示指定主题整理→查看来源与差异→应用→撤销→重启，验证冲突、坏 JSON、中途失败，并断言未创建任何自动记忆整理计划。
