# 24私助智能工作晨报实施计划

确认日期：2026-11-02，Asia/Shanghai。主人确认围绕今日安排、到期事项和昨日进展安排今日工作，并明确选择使用模型的智能工作晨报。规格 2.17，故事 158，交付 F48／[#259](https://github.com/benz-ai-x/dsh-24-PA/issues/259)，依赖 F47。实现与验收另记；本计划不代表已经部署或通过真实账号验收。

## 目标

主人明确希望晨报包含「今日安排、到期事项、昨日进展」，重点帮助一早安排今日工作。读完后应能回答：今天有哪些必须遵守的安排、最值得完成什么、第一步怎么开始，以及需要自己决定什么。

晨报复用已有每日工作计划：晨报生成当日建议，主人采纳形成确定安排，日终复盘再供下一次晨报参考。晨报与首页展示同一份建议和采纳记录。

## 内容与阅读顺序

| 顺序 | 内容 | 选取原则 |
|---|---|---|
| 开头 | 今天怎么安排，用两三句话先给结论 | 先说主要成果、固定约束和推荐顺序；信息不足时说明影响 |
| 昨日进展 | 已推进到哪一步，什么会影响今天 | 只保留与今天有关的成果、未完成项和阻碍，通常不超过三条；未完成项重新评估，不自动全部顺延 |
| 今日约束 | 固定日程、今天到期、已逾期且影响今天的事项 | 日程写本地时间与必要准备；截止与计划投入时间分开；无关的历史逾期不占据正文 |
| 今日工作建议 | 至多三项关键成果及执行顺序 | 每项包含完成后的结果、优先理由、第一步、估时或估时未知；可安排的时间有依据才给时间块 |
| 待决定事项 | 冲突、过载、等待依赖和必要选择 | 只问会改变今天安排的关键问题；没有取舍就不凑问题，已决定且事实未变的不再询问 |

正文以一至两分钟可读完为初始目标。时间使用主人的时区，例如「10:30–11:00」，全天事项单独标明。重要来源可以就近链接；同步详情集中在末尾。影响判断的缺失直接写在相关建议旁边，语音也保留这类限制。

项目统计、待审笔记、已审笔记和等待项，只有影响今天的安排时才进入晨报。天气、资讯等未进入本轮内容范围。

## 内容样稿

以下全部为虚构示例，用于讨论内容和表达。假设工作时段、会议、截止和估时均已核实；不代表主人今天的真实安排。

> 早上好。今天建议先完成客户方案评审稿，再推进产品验证。10:30 和 15:00 各有一场会议，方案需要在 16:00 前交付，上午的完整时间先留给它。
>
> **昨天接到今天**
>
> 昨天已确定方案结构，还差报价和风险说明。产品验证仍有两个问题待核实，可以接着推进；合作方的回复仍在等待，暂时不计入今天能确定完成的工作。
>
> **今天已经定下的安排**
>
> - 10:30–11:00：项目同步会。
> - 15:00–16:00：产品评审，需提前整理验证结果。
> - 16:00 前：提交客户方案评审稿。
>
> **建议这样推进**
>
> 1. **先把客户方案补成可评审版本。** 昨天已完成主体，今天有明确交付承诺。第一步核对报价依据，再补风险说明；预计 90 分钟，建议放在 9:00–10:30。
> 2. **午后完成产品验证，形成评审结论。** 这是近期重点，也直接服务于 15:00 的评审。先核实剩余两个问题；预计 60 分钟，建议放在 13:00–14:00。
> 3. **评审后整理产品方案的修订清单。** 先合并会上确认的意见，再标出尚待决定的部分；预计 45 分钟，建议放在 16:15–17:00。若评审延长，先保留结论记录，详细修订另作安排。
>
> 会议之间的零散时间留给会前准备、消息和临时事项。以上是今日建议，采纳后作为今天的工作计划。

实际晨报只表达有依据的事实；样稿中的时间、耗时与成果不得作为运行默认值。

## 与现有能力的衔接

- 复用 [工作方法实施计划](24PA-工作方法-实施计划.md) 的近期重点、每日建议、主人采纳和日终复盘；继续保留建议与采纳的区别。
- 复用 `WorkPlanning.context` 获取当天日历、已登记来源的待办、近期重点、当日建议与采纳、交办和等待项。智能排序与自然表达由任务 Skill 完成，日期、权限、来源与保存版本由代码核验。
- 已有采纳计划时，晨报以采纳项为基础检查变化。新的建议独立保存，不能覆盖主人已采纳的安排；没有实质变化就不重新安排一天。
- 只保存当日建议；创建日历块、修改任务、采纳计划和更新长期记忆仍按各自现有授权流程办理。

### 昨日进展需要补齐的读取

当前 `previousReview` 返回此前最近一次复盘，不一定是昨天。新晨报须读取明确的前一日期及其采纳版本，才能把复盘中的事项编号还原成当时的成果和下一步；若最近复盘来自更早日期，应显示实际日期。

完成时间与最后同步时间分开。昨日复盘及其完成依据、明确的本人说明可以支撑昨日进展；只有当前完成状态时只能说「目前已完成」，不能推断为昨天完成。没有昨日复盘或足够依据时，说明缺少昨日记录，继续使用已核验的今天数据安排工作。

## 已确认运行方式与切换

**采用智能工作晨报。** 复用 `daily-planning` 的规划能力和保存流程，结合上述内容结构生成晨报；既有 `digest-morning` 为固定模板，不调用模型。两者的现状与限制见 [晨报内容重构现状调研](../research/2026-11-02-晨报内容重构-现状调研.md)。

智能方案会产生模型用量，支持优先级判断和承接昨日进展；固定模板方案可重排内容、改善时间与字段表达，但不能把固定列表冒充个性化判断。

当前工作方法契约明确「原模板不自动换绑，不自动开启定时服务」。新建晨报预设选择 `builtin:daily-planning`，表单明示模型用量和建议／采纳关系。既有 `digest-morning` 保持固定模板身份和执行方式；已有通用计划先暂停，再点击「改用智能工作晨报」修改同一计划，再选择「核验新 Skill 并启用」确认能力和投递目标，保留名称、时间、时区、投递与历史。旧简报先按原 Skill 完成既有迁移，再走同一路径，不另建重复计划，不直接放宽旧入口绑定限制。

## 验收场景

| 场景 | 应观察到的结果 |
|---|---|
| 昨日有复盘且存在未完成项 | 说明实际进展和今天的承接理由，未完成项不全部自动顺延 |
| 最近复盘是更早日期 | 标出真实日期，不称作昨日；缺失昨天记录不阻止今天建议 |
| 到期待办很多，但有一项无截止的重要成果 | 结合近期重点与承诺说明取舍，不直接使用列表前三项 |
| 会议占满大半天 | 根据已确认工作时段及会议占用安排，保留缓冲，过载时给出可选取舍 |
| 工作时段或估时未知 | 给先后顺序及下一步，缺少依据的时间块和耗时标未知 |
| 当天已有采纳计划 | 保留采纳项，只对实质变化提出调整建议 |
| 某个来源失败 | 标明影响范围；不把读取失败解释为没事或空闲 |
| 模板改为智能运行 | 明示模型使用和必要放行，不静默改变既有计划 |
| 文字或语音阅读 | 保持相同的事实、关键缺失和取舍，语音不读技术字段与长链接 |

实现时覆盖受影响的单元行为、SQLite/PostgreSQL 持久化及真实 Loader；模型输出质量另用完整场景样本评估，不能用代码测试代替真实使用验收。
