# 官方连接器依赖：自建对接面盘点与迁移计划

2026-11-26，实施前研究。插件基线：`0.2.3-alpha.2.1`（`main` 提交 `be4518f`，`engines.dsh`＝`0.2.3-alpha.2`）。宿主路径与行号对应标签 `dsh-v0.2.3-alpha.2`（提交 `4b399c39a`，本机 `~/DSH-Space/deepseek-harness`），官方连接器 npm 包为 `0.2.3-alpha.2`。

实施跟踪：#302（工单 #303–#310）。主人于 2026-11-26 对「裁决」一节的六项全部按建议落定。

主人定的原则：

1. 飞书的连接必须依赖官方 `@deepseek-ai/dsh-feishu`。
2. 企微的连接必须依赖官方 `@deepseek-ai/dsh-wecom`。
3. 其他第三方工具的连接（腾讯文档、腾讯会议等）同样依赖官方，不重复造轮子。
4. 官方插件实现不了、需要本产品自己实现的，先识别清楚，再判断是否自研。

证据边界：本文读了宿主与插件源码、npm 清单和官方文档，并在隔离 profile 里启动了官方 alpha.2 CLI（见「隔离环境实测」）。启动宿主时使用隔离的 `HOME`；装包阶段用真实 `HOME`，只用到 pnpm store。全程没有读取、登录或变更任何飞书、企微、微信、腾讯账号，没有改动生产 8010，没有提交。标为「未验证」的项见文末。

## 结论

1. 24私助里与官方插件重复的自建实现只有两类：**CLI 供给**（按 PATH 找 `lark-cli`／`wecom-cli`、指南要求在服务器安装并保证宿主 PATH、`--version` 探测）和**账号授权引导**（飞书的 `config init` 与 `auth login` 三步、企微的 `auth init` 扫码）。两类都可以移除，改依赖官方插件。
2. 官方插件没有对应物、24私助必须继续自持的：飞书入站长连接、账本化业务工具、主人身份证据、资源核验、企微服务级授权与续期提醒、微信入口、语音合成。原因是官方插件的形态是「装好官方 CLI，在插件页授权，由模型在 Shell 里跑 CLI」，不向其他插件提供业务接口；`ctx.cliAccounts` 只有 `register`，没有查询。
3. 腾讯文档、腾讯会议：24私助没有任何自建实现（代码里的 `meeting_*` 是日历日程）。要用官方的，腾讯文档差一处白名单放行，腾讯会议按官方设计装上即可在本地会话使用。
4. 隔离实测成立：24私助与官方飞书、企微、腾讯文档连接器在同一个 profile 登记并全部激活；官方托管的 `lark-cli` 1.0.97、`wecom-cli` 1.3.4 的帮助文本含24私助传递的全部命令与参数；24私助包所在位置能定位官方连接器及其托管 CLI；本地24私助会话收到的运行时上下文带官方 CLI 的绝对路径，并能经 `skill` 工具加载官方 `feishu`、`wecom` 技能。
5. 约束：官方连接器只有 0.2.3-alpha 线版本，生产所在的 rc 线装不了；官方文档写明只支持 macOS 与 Windows x64。本迁移只能在 `0.2.3-alpha.2.x` 线做。
6. 飞书入站长连接可以改走官方 CLI 的事件订阅，从而去掉 `@larksuiteoapi/node-sdk` 与 App Secret，但平台确认的语义会变。这一项单列为评估项，不在本迁移的默认范围。

## 官方连接器的能力与边界

| 包 | 固定的 CLI | 注册到 | 插件页账号操作 | 不提供 |
|---|---|---|---|---|
| `@deepseek-ai/dsh-cli-account` | — | `ctx.cliAccounts`（基座服务） | 账号区块与执行器 | 按名查询；`CliCommandExecutor` 不从包入口导出 |
| `@deepseek-ai/dsh-feishu` | `@larksuite/cli` 1.0.97 | `ctx.cliAccounts`、`ctx.skills` | `check`（`auth status --verify --json`）、`link-app`（`config init --new`）、`sign-in`（`auth login --json`）、`sign-out` | 入站消息、业务接口 |
| `@deepseek-ai/dsh-wecom` | `@wecom/cli` 1.3.4 | `ctx.cliAccounts`、`ctx.upstreamSkills` | `check`（`auth show`）、`connect`（`auth init --noninteractive --no-browser`） | 服务级授权探测、撤销授权、入站消息 |
| `@deepseek-ai/dsh-tencent-docs` | 托管 MCP `https://docs.qq.com/openapi/mcp` | `ctx.mcpManager`、`ctx.mcpAccounts` | OAuth 连接、退出 | 远程浏览器授权（回调只到 Host 本机） |
| `@deepseek-ai/dsh-tencent-meeting` | `@tencentcloud/tmeet` 1.0.18 | `ctx.cliAccounts`、`ctx.upstreamSkills` | `check`、`sign-in`、`sign-out` | — |

要点（`packages/connector/*/src`、各包 `README.zh.md`）：

- 连接器让模型**在 Shell 里按绝对路径运行 CLI**，配一份入口技能索引子指南。业务动作由模型完成，没有给插件代码调用的接口。
- 账号操作经 `ctx.cliAccounts` 一次只跑一个。执行器忽略 stdin、stdout 上限 1 MiB、stderr 只留末尾 4 KiB、cwd 为用户主目录、非交互命令截止 30 秒（等用户的 10 分钟）。24私助的网关是 16 MiB 并支持 stdin（`docs +create --content -`），数据面调用不能改走这个执行器。
- 连接器只用 CLI 的**当前生效配置**，与用户自己终端共用，命令不带 `--profile`。`link-app` 会替换默认配置里的应用与登录，`sign-out` 同时退出用户终端的登录。
- 账号区块由 Web 应用的 `connectorAccounts` 注册表显示；基座组合包已挂载 `cli-account`、`upstream-skills`、`skill` 三个服务（`packages/bundle/base/cordis.patch.yml:241,319,330`），Web 组合包挂载 `mcp-manager`、`mcp-account`、`ui-connector-account`。
- 官方 README 的已知限制：三个 CLI 连接器均写「仅支持 macOS 和 Windows x64；其他平台未经验证」。npm 清单里 `@larksuite/cli` 声明 `linux`，`@wecom/cli` 有 `linux-x64`、`linux-arm64` 平台包。
- npm（2026-11-26）：`dsh-feishu`、`dsh-wecom`、`dsh-tencent-docs`、`dsh-tencent-meeting`、`dsh-cli-account`、`dsh-upstream-skills` 的版本都只有 `0.2.3-alpha.1`（`latest`）与 `0.2.3-alpha.2`（`alpha`），没有 rc 线版本。
- `@deepseek-ai/dsh-tencent-meeting` 的安装脚本会执行 `tmeet auth logout`，退出这台电脑上 tmeet 的登录。

## 迁移计划

目标形态：连接层（CLI 供给、账号授权）全部来自官方插件，业务层（入站、账本化工具、身份证据）留在24私助。按[交付流程](../agents/delivery.md)逐阶段走 Issue → 分支 → PR → `code-review` 双轴 → 合并；本计划取代[宿主升级研究](2026-11-25-dsh-0.2.3-alpha.2-宿主升级研究.md)阶段二的 2.2 与 2.3，并把 2.1、2.4、2.5、2.6 并入 M3、M4。只在 `0.2.3-alpha.2.x` 线实施。

### M0 前置核验（不改产品代码，#303）

- [x] M0.1 「装了官方连接器的 profile 里，本地会话收到官方 CLI 路径并能加载官方技能」已实测成立（见上表），固化为 e2e 守卫并入 #304 的验收；飞书、微信接入会话的工具面在同一用例里断言。
- [ ] M0.2 插件页账号操作在24私助 profile 里走通（关联应用、登录、连接企业微信）：由主人在隔离实例用测试应用操作。另含腾讯文档授权后的真实读写。
- [ ] M0.3 `lark-cli --profile default` 与官方的「当前生效配置」是否同一份：隔离实例配好测试应用后核对。
- [ ] M0.4 上游需求草稿已写在 #303 的评论（`ctx.cliAccounts` 按名查询或连接器导出 `resolveCliExecutable`；连接器是否进 rc 线；Linux 是否验证），是否提交由主人决定。

### M1 CLI 供给改依赖官方连接器（F1、W1，#306）

- [ ] M1.1 新增 CLI 定位模块：显式 `larkCliBin`／`wecomCliBin` 覆盖优先（测试桩与自建目录），其次官方连接器包内的托管 CLI 绝对路径。删除 `src/feishu.ts` 的 PATH 搜索。

## 裁决（2026-11-26，主人对六项均按研究建议落定）

1. **安装形态：官方连接器保持独立安装**（插件页或 `dsh plugin add`），24私助在提供 `cliAccounts` 服务的宿主线上运行期硬依赖，缺席即拒绝激活对应渠道。未采用的替代做法是24私助把两个连接器声明为依赖并在自己的 patch 里插入 `feishu`、`wecom` 行：构建脚本审批会并入24私助安装，企微连接器会被强加给只用飞书的实例，主人再从插件页安装同一连接器时行 id 可能重复（宿主如何处理未验证）。
2. **`larkProfile`：缺省 `default` 时不再传 `--profile`**，与官方同语义。设了具名 profile 的实例保留该字段，readiness 提示「官方插件页只管理当前生效配置」。存量实例若用非默认 profile，需本人到插件页重新登录一次；生产 8010 的取值未读取。
3. **入站通道保留 SDK 长连接。** 未采用的替代是用官方 CLI 的 `lark-cli event consume`（`im.message.receive_v1` 与 `card.action.trigger`，均为 `--as bot`），它能去掉 `@larksuiteoapi/node-sdk`、App ID／Secret 两项密钥和 `feishu.ts` 的事件映射，但平台改由 CLI 的总线进程确认，24私助「先落账再确认」的保证不复存在；`card.action.trigger` 是单消费者，会占住主人终端里的同一事件；卡片回调的即时提示无法同步返回；消费进程崩溃时事件是否丢失未知。
4. **只在 `0.2.3-alpha.2.x` 线实施。** rc 线（含生产 8010）保持现状，等官方连接器进入 rc 线并验证 Linux 后再迁。
5. **保留24私助的账本化业务工具。** 官方只让模型在 Shell 里跑 CLI，没有确定性调用、幂等与回执，飞书接入会话也没有 Shell；改走官方方式等于重做产品。
6. **工作区密钥库维持暂不立项。** 裁决 3 保留 SDK，飞书 App ID／Secret 两项随之保留。
