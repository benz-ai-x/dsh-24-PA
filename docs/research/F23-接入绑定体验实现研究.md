# F23 研究：接入绑定体验（飞书/企微 CLI 绑定的多轮对话收敛）

日期：2026-10-08。来源：用户真机体验反馈（主流程跑通，但「跟24私助对话多轮才把环境装起来」，痛点定位在**与飞书 CLI、企微 CLI 的绑定事项**，非宿主环境部署）。用户裁决范围：速效三件先行（批量操作单＋自动验收＋wecom 到期主动提醒），面板承载 QR/Secret 输入列为后续迭代。

## 一、现状结构与根因（两份向导实测结构分析）

**飞书（feishu-setup.md，6 阶段）**：本人手工环节分散在阶段 1（控制台建应用 6 步，无公开 API 不可代办——F15 定性）、阶段 2（本人终端 `config init`＋浏览器授权确认）、阶段 4（启动环境填 Secret＋重启宿主）；每阶段之间夹 agent 的 `check` 验证。「顺序铁律」真实存在依赖链（App ID → CLI 配置 → 授权 → 资源标识 → env → 重启），但**向导形态把人工环节切成 3~4 次「你去做→我验证」往返**；实际对话中助理逐条吐操作、check 不通过再定位，轮次成倍放大。

**企微（wecom-setup.md，4 阶段）**：本人环节＝阶段 1 企微 App 内扫码绑定＋阶段 2 逐项服务授权；**服务级授权会过期**（F16 实测 850003，过期周期未知）——绑定是持续性摩擦，失效靠用户撞错码才发现。

根因归纳：①逐阶段放行的向导形态（人工环节碎片化）；②验收靠用户回话触发（无自动收敛）；③wecom 授权健康无主动监控。

## 二、设计取舍（速效三件）

1. **批量操作单＋一次验收**：向导重构为「先全量、后集中」——配置开始时一次性交付本人操作清单（标注依赖块：A 控制台 → B 终端 config init＋浏览器授权 → C 启动环境 Secret＋重启），agent **提前发起 Device Flow 并把授权 URL/二维码随清单一并交付**（不等阶段 2 到来）；本人一口气做完回报一次，agent 集中验收。目标往返：N 次 → ≈2 次。安全红线不变（授权点击、Secret 填写永远本人；agent 只发起、转交、验证）。
2. **自动验收循环**：本人报「做完了」后，agent 以 `check`/`wecom_check` 循环收敛（按 nextSteps 逐项定位剩余卡点，一次性汇总反馈），写入两份向导的执行纪律；是否给 `pa24_connection` 增加批量/循环形态（如一次返回双通道全量检查＋差异）在实施时按篇幅裁决。
3. **wecom 授权到期主动化**：用现成提醒引擎或健康面板轮询做定期 `wecom_check`；发现 850002/850003 即经 notifyChannel 主动推送续期链接（wecom_check 的 nextSteps 已含平台授权链接，转交即可）。把「过期」从被动撞墙变为主动通知。

## 三、后置项（用户裁决本轮不做）

- 面板承载人工环节：QR 码（lark-cli `auth qrcode`／wecom-cli `auth init`）显示在 web 面板；Secret 输入框本地直达启动环境（不进对话）。涉及 client.js 与新安全边界，单独立项。

## 四、未决 / 实施期待验

- Device Flow 设备码/授权 URL 的时效窗口（决定「提前发起」能提前多久，需实测 lark-cli 行为）。
- 自动验收循环的节奏与上限（避免高频外部探测；check 为只读探针，风险低但要有频率纪律）。
- wecom 到期监控的周期与「授权链接时效」（链接过期需重新 wecom_check 取新链接）。
