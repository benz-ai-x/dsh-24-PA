## 一、需求定位与规格约束

1. 用户需求：晨报（当日计划）与晚间复盘以语音形式送达飞书。两者即 F09 周期服务的 morning/evening digest（已交付），本票是**投递形态扩展**，不是新服务。
2. 规格定位：规格 1.8 新增（用户 2026-10-07 提出，用户故事 126）；本票 F19 / P51，单票单 PR。
3. 边界：仅出站 TTS（24私助→主人），不涉及入站语音转写（设计方案已声明不假装具备转写）；提醒（F05）等其他出站内容暂不语音化，挂点相同可后扩。

## 二、既有链路（源码核验）

- **触发与生成**：`digestEnable`（runtime.ts:3136-3178）支持 kind morning/evening/weekly/once，经 dsh 原生 Schedule 到点唤醒；`digestBuild`（runtime.ts:3356-3380）幂等抢占 occurrence → `planningFacts` 聚合日历/任务/等待/待审 → `renderDigest` 模板渲染纯文本（**正文不过模型**）。
- **投递**：`digestBuild` → `notifyOwner`（runtime.ts:966-989）→ outbox 入队（`kind` 仅 `'text'|'card'`，repo.ts:226-248；DDL 无枚举约束，pg.ts:72-86）→ `sendOutbox`（runtime.ts:5331-5376）→ feishu 走 `transport.sendText/sendCard`（feishu.ts:33-40，SDK `im.message.create`）。
- **网关**：`runLarkCli`（lark.ts:31）已支持 `cwd`（lark.ts:12）与 stdin；`im +messages-send` 已有调用先例（runtime.ts:2715，`--as user` 对外联络）。`digest_plan` 表无选项列（pg.ts:373-384），语音开关需加列迁移。

## 三、真机实测（2026-10-07，本机 macOS + lark-cli 1.0.87 profile 24PA）

**发送侧**：`lark-cli im +messages-send --as bot --user-id <ownerOpenId> --audio ./test.ogg --idempotency-key <key>` —— **成功**，返回 `ok:true`、`message_id: om_x100b6350ae8340a0c006d0c246f7e13`（bot 身份，语音气泡送达主人单聊）。契约要点（`--help` 与内置技能文档 `lark-im-messages-send.md`）：

- `--audio` 发**原生语音消息**，本地路径自动上传；仅收 Opus（`.opus`/Ogg Opus `.ogg`），mp3/wav 需转码或走 `--file` 附件。
- 本地路径必须 **cwd 相对**（绝对路径与 `..` 拒绝）→ spawn 设 `cwd` 即可，`runLarkCli` 已支持。
- `--as` 默认 bot；幂等键 ≤50 字符、同键 1 小时去重——与 outbox dedup 键语义对齐。

**合成侧**：macOS `say`（新一代中文语音 Eddy/Flo zh_CN 等）＋ ffmpeg 8.1.2（libopus）：

```
say -v 'Eddy (中文（中国大陆）)' -o out.aiff '<正文>'
ffmpeg -y -i out.aiff -c:a libopus -b:a 32k out.ogg
```

实测两个样例：9.4s/33KB、约 18s/64KB，格式与时长均被飞书接受，合成耗时毫秒级。Ops-Space 正式实例宿主即本机，`say`/ffmpeg 生产可用。

## 四、设计取舍

1. **合成时机＝投递时**：outbox 行新增 `kind:'audio'`，`content` 只存正文文本（自包含、可重放、无 blob 存储）；outbox worker 发送时现场合成（确定性渲染），重启/重试天然可用。kind 为 text 列无枚举，代码层类型联合扩展即可，无 DDL 变更。
2. **TTS 模块接口化**：首版 macOS 适配器（say＋ffmpeg）；预检两命令存在性并纳入诊断（缺失时降级发文本＋告警，不中断服务）；将来迁 Linux 换适配器（云端 TTS 备选，首版不引凭据依赖）。
3. **开关落 `digest_plan` 新列**（`voice boolean default false`，迁移 vN）：per-plan 粒度支持「早语音晚文本」；`digest_control` 扩展 voice on/off；`pa24_work` 的 digest_enable 入参带 voice。
4. **双轨兜底**：voice 开启时先发语音、紧跟一条全文文本（数字/专名听不清时可查）；语音正文用口播变体（剥离 syncedAt/数据缺失清单等元数据行），快照测试守护。
5. **长文上限**：语音版截断（建议 ≤1200 字并在语音内播报截断提示）；平台未文档化时长上限，实施时以真机长样例回归。
6. **免打扰语义不变**：digest 走 Schedule、不经 ReminderEngine 的 silencePolicy 扣留，维持现状。
7. **wecom 通道**：`notifyChannel='wecom'` 时语音降级为文本＋告警；wecom-cli aibot send 支持语音（F16 研究:19，未实测）作为后续 parity。
8. **前置依赖写入指南**：初始化指南补 macOS 宿主（say）＋ ffmpeg 两项；面板/连接诊断后续可挂预检结果。

- 音色与语速默认值（Eddy/Flo、`-r` 语速）由主人试听样例后定（样例 message_id `om_x100b635…` 已发）。

## 六、2026-10-17 生产真机 A/B 与双引擎修订（取代第四节第 2 条的 say 适配器决策）

在 ali_code_agent 生产实例（Ubuntu arm64）上做了四轮同文 A/B，样例均经 `lark-cli --as bot --audio` 送达主人飞书：

| 轮次 | 引擎 | 结论 |
|---|---|---|
| 1 | Piper（huayan-medium.onnx，本地） | 拒——机械感明显 |
| 2 | MeloTTS（sherpa-onnx int8，本地 /DSH/melo-tts） | 较好但仍偏机械；合成实时率约 1.4×（晨报 22s 音频约 31s CPU），异步投递可接受 |
| 3 | edge-tts（Azure 神经声，云） | 预览样例，未深测 |
| 4 | 火山豆包 Seed-TTS-2.0（云） | 听感最佳；中英双语音色（灿灿/云舟）样例已发 |

**用户裁决（2026-10-17）：不做淘汰式二选一——TTS 引擎成为工作区配置（`tts.engine: none/melo/volcengine`，默认 none），豆包云需配密钥环境变量引用＋音色，Melo 需配部署目录；macOS say 适配器废止（SPEC 2.3，故事 126 修订）。**

### 6.1 豆包（火山引擎）三接口实测事实

- **三条接口，职责不同**：①HTTP 一次性 `/api/v3/tts/unidirectional` 的姊妹接口 `/api/v3/tts/create`（model `seed-audio-1.0`）是**音频生成**模型而非语音合成——喂普通文本会当成「声音场景提示词」即兴生成（实测产出噪声）；②WS 双向流式 `/api/v3/tts/bidirection`（二进制帧协议，官方 zip 有协议实现）；③**HTTP 单向流式 `POST /api/v3/tts/unidirectional`——晨报场景的正解**，请求响应最简单。
- **鉴权与资源**：唯一鉴权头 `X-Api-Key`（新版语音控制台 API Key 管理页创建的 UUID Key）；**方舟平台 `ark-` 前缀 Key 被拒**（401 `45000010`）。资源与 Key 双独立：`volc.service_type.10074`＝Seed-Audio 资源，**Seed-TTS-2.0 是另一个独立开通项**——错误阶梯：401/45000010＝Key 类型错；403/45000030＝资源未开通；55000000 "resource ID is mismatched with speaker related resource"＝TTS 服务未开通（该资源下无音色）。
- **unidirectional 协议要点**：请求头 `X-Api-Key`＋`X-Api-Resource-Id: seed-tts-2.0`＋`X-Api-Request-Id`（uuid 必填）；请求体 `{req_params:{text, speaker, audio_params:{format, sample_rate, speech_rate, loudness_rate…}, enable_subtitle?}}`；响应＝HTTP chunked **行分隔 JSON** `{code, message, data, sentence, usage}`——**`code:0` 与 `code:20000000` 都是成功码**；`data` 为 base64 的 OGG 分页，按序拼接即完整 ogg；`ogg_opus` 仅支持 48000Hz；`enable_subtitle:true` 返回逐句朗读文本＝**发送前的内容自验手段**（字幕文本与输入逐字一致＝真朗读）。
- **音色**：2.0 音色为 `zh_*_uranus_bigtts` 系（**2026-10-17 五款经生产 unidirectional 真机合成验证**：灿灿 `zh_female_cancan_uranus_bigtts`、知性女声 `zh_female_zhixingnv_uranus_bigtts`、云舟 `zh_male_m191_uranus_bigtts`、Vivi `zh_female_vv_uranus_bigtts`、小何 `zh_female_xiaohe_uranus_bigtts`）；中文音色具备英文能力（英文晨报样例已验证）。`*_jupiter_bigtts` 四款（SDK 的 S2S 主打线）在 unidirectional 下报 55000000 资源不匹配——属 S2S 资源线，**不可**混入 seed-tts-2.0 音色清单；小天无 uranus 代 ID。
- **WS 协议要点（备查）**：官方二进制帧（4 字节头＋事件 int32＋会话 id＋payload 长度前缀）；payload JSON **必须带 `namespace:"BidirectionalTTS"`**，缺了＝服务端静默丢弃文本（TTSSentenceStart 空、无报错）；文本经 TaskRequest 且携带完整 req_params。晨报场景无需流式输入，unidirectional 已覆盖。
- **时延与配额**：晨报长度合成约 15–30s，偶发 >60s（适配器超时预算按 300s 设计，outbox 异步投递无感）；curl 坑：`--data-raw @file` 不解析 `@`，须 `-d @file`。
- **密钥管理**：密钥本体只进宿主环境（配置块存 `volcKeyEnv` 环境变量名，沿用「秘密只引用环境/凭据」红线）；生产服务器过渡期存于本地 600 文件，正式接入后迁移为环境变量并吊销过渡文件。

### 6.2 Melo 生产部署形态（meloDir 指向的目录约定）

`/DSH/melo-tts`：python venv（sherpa-onnx）＋ `model.int8.onnx`（zh_en，53.5MB）＋ lexicon/tokens/dict 全套；模型经 hf-mirror.com 下载（HF 直连与 GitHub release 在生产网络不可用）。sherpa-onnx Python API 三坑（实测）：构造须 `OfflineTtsConfig(OfflineTtsModelConfig(vits=…))`（误用 ASR 的 OfflineModelConfig 报参数错）；`audio.samples` 是 [-1,1] 浮点列表，须 ×32767 夹取后按 int16 打包（直接 `map(int)`＝全零静音）；全角标点 OOV 警告无害。产物为 wav，需 ffmpeg libopus 转 ogg（宿主须装 ffmpeg）。
