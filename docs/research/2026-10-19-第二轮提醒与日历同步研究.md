# 第二轮：提醒日程化与日历同步契约研究

日期：2026-10-19（Asia/Shanghai）。实现基线：main `b78dcbb`。范围：第二轮架构修复 03/04；对应规格 2.12 的故事 54/145、T09，以及日历投影与来源跟随行为。本文只记录研究与本地验证，不修改业务源码或测试，不创建真实远端对象。

## 结论与实施顺序

1. **企微原生支持 daily/weekly 周期日程**。本机官方 `@wecom/cli` 1.3.4 的 schema 已给出准确结构，两个本地 dry-run 通过；当前24私助只漏传了周期字段，不应把周期能力判为平台不支持。
2. **日程化提醒先固定意图，再执行渠道写入并恢复备份**。相对延时不能在重试时重新取当前时间；取消使用已存渠道和日历归属。此前探针在真实 ExternalOperations＋内存 SQLite 上复现了备份失败后同一输入产生两个远端 mock 对象。
3. **日历完整性不等于拿到一个数组**。飞书 v1.0.87 的 `+agenda` 已在 CLI 内按窗口拆分，并非需要24私助自行追加 cursor；但返回的嵌套时间对象与当前 mapper 不匹配。企微查询公开文档有当前时刻前后30天范围限制，超界部分不能视为完整空集合。
4. **消失判定必须带观察范围**：渠道＋被查询日历/聚合集合＋时间窗＋完整性。只在完整范围内取消不存在的投影和跟随提醒；核验旧事件时读取事件自身日历的同步水位。

上述修复保持 [ADR-0001](../adr/0001-workspace-session-boundaries.md) 的提醒日程化决定：原生 App 送达，账本只作备份，不恢复账本计时投递。

## 03：企微周期、时区与提醒字段

本机 `wecom-cli calendar schedules create --schema` 的 `ScheduleRecurrence` 指定：`is_repeat` 为 boolean，`repeat_type` 使用 `daily`/`weekly` 字符串，周内日期使用 `MO`～`SU`；weekly 的 `repeat_day_of_week` 必填，多选时 `is_custom=true`；`repeat_interval` 省略或1均为默认间隔1；`repeat_until="0"` 表示永不结束。创建不支持 `exception`。以下最小请求已在本地 dry-run 保真输出到 payload：

```json
{"is_repeat":true,"repeat_type":"daily","repeat_interval":1,"repeat_until":"0"}
```

```json
{"is_repeat":true,"is_custom":true,"repeat_type":"weekly","repeat_interval":1,"repeat_day_of_week":["MO","WE","FR"],"repeat_until":"0"}
```

对应 CLI 参数是 `--repeat-rule '<JSON>'`。映射现有 F45 规则即可：`FREQ=DAILY;INTERVAL=1`→daily；`FREQ=WEEKLY;BYDAY=...`→weekly。不要为任意 RFC5545 规则伪造兼容：超出本轮支持范围的规则应在任何远端写入前明确拒绝。创建投影的 `recurring` 应依据已提交规则；查询投影依据返回 `repeat_rule.is_repeat`，不能恒定 false。

`ScheduleTimezone` 的 `timezone_id` 是优先使用的 IANA 标识，`timezone_offset` 只在标识为空时使用。24私助已把绝对时间格式化为工作区墙上时间，因此还必须传同一时区，例如 `--timezone '{"timezone_id":"Asia/Shanghai"}'`；如果提醒指定了另一 timeZone，应在固定意图中保存并贯穿格式化和提交，不能又改用当前配置。官方参考说明省略时区会使用授权用户时区，不能假定它与工作区相同。

`ScheduleRemindersReq` 是对象，形状为 `{"is_remind":true,"reminder_time":[秒差]}`；负数代表提前。1.3.4 schema/doc 给出的默认值是 `[-900]`，即提前15分钟；本地 dry-run 接受 `[0]` 并原样放入 payload。**dry-run仅证明本地组装通过，不证明服务端最终接受0或手机实际到点提醒。** 如果保持现行提前5分钟的产品回执，需要显式传 `[-300]` 并在测试中断言；若采用各渠道原生默认，则回执必须如实区分，不能仍宣称两渠道默认5分钟。

可复验的本地命令（必须保留 `--dry-run`）：

```sh
wecom-cli calendar schedules create \
  --subject '24PA local dry run weekly' \
  --begin-time '2026-10-20 08:00:00' --end-time '2026-10-20 08:15:00' \
  --repeat-rule '{"is_repeat":true,"is_custom":true,"repeat_type":"weekly","repeat_interval":1,"repeat_day_of_week":["MO","WE","FR"],"repeat_until":"0"}' \
  --timezone '{"timezone_id":"Asia/Shanghai"}' \
  --reminders '{"is_remind":true,"reminder_time":[0]}' --dry-run
```

飞书 `calendar +create --rrule` 原样写入 `recurrence`，同版官方源码 `buildEventData` 第20–38行确认；它固定 `reminders:[{"minutes":5}]`，当前 shortcut 没有单独的 reminder/timezone 参数。此次 dry-run 与源码一致。不能声称飞书这个 shortcut 已支持任意提醒提前量；改变它需要另行选择已核验的原生调用方式。

### 稳定意图与恢复的最小修复

- 在第一次远端写入前，持久化本次提醒的稳定身份、固定起止时间、规则、时区、所选渠道及日历。重复请求的身份基于原始意图及既有 WorkItem 归属，不能包含重试时新算的 `Date.now()`。
- 为日程操作与备份使用可重取的稳定关联；备份恢复应是幂等补记。不要每次成功回执后再随机生成一份互不关联的 ruleId。
- 继续复用 ExternalOperations 的运行/unknown 阻断及远端回执恢复。飞书/企微都必须允许使用同一稳定业务操作身份；缺失回执时仍停止待核对，不能把未知结果当作可重试失败。
- 取消依据备份里的渠道与日历，成功确认后才停止备份。旧备份缺 calendarId 时优先使用已存日程投影；若无法确定，明确待核对，不能猜当前日历。
- 修复不要求支持企微日程 update、任意重复规则或跨平台迁移旧对象。

## 04：真实日历返回、分页与完整性

### 飞书1.0.87

[calendar_agenda.go](https://github.com/larksuite/cli/blob/v1.0.87/shortcuts/calendar/calendar_agenda.go) 第21–111行表明：`+agenda` 调用 `events/instance_view`，超过40天先拆窗口；遇193103时间范围限制或193104超过1000实例继续拆分，过密且已缩至2小时则失败，递归深度上限10；任一子请求失败则整次 shortcut 失败。它没有要求调用者消费 page_token；因此本轮无需给 `+agenda` 再拼自创分页参数。成功后会去重、过滤 cancelled，再输出数组（213–259行）。

**不能继续使用当前只接受平面时间字符串的 mapper。** 同版源码227–250行保留 `start_time/end_time` 对象，把其中 `timestamp` 转成 `datetime`（RFC3339，含设备时区偏移）；全天则保留 `date`，并把结束日期由平台半开区间转换成包含最后一天的日期。应覆盖：

- 定时：`start_time.datetime` / `end_time.datetime`；必要时兼容原生 timestamp 和已有桩的平面ISO，不能把对象转字符串再解析。
- 全天：`start_time.date` / `end_time.date`；若从 `+agenda` 的包含尾日格式归一成账本半开区间，需要在正确时区把结束日推进一天。不能将其混同原生接口的 exclusive end。
- 空标题不等于损坏时间或身份；CLI显示层自己用 `(untitled)`，业务 mapper 不应因此把合法事件排除后当作消失。
- 请求传完整带时区的 ISO 起止，不能先 `slice(0,10)` 丢掉实际观察窗口。完整性只覆盖实际成功观察范围。

当前 mapper 遇坏条目 `continue` 后仍执行 `markCanceledExcept` 并标记 complete；这会把“无法识别”误当“不存在”。最小修复先解析/校验完整集合，若任一必要身份或时间不可确定，则记录不完整、保留旧投影，不做缺失删除或来源消失通知。合法空数组与坏条目数组必须分开测试。

### 企微1.3.4及当前官方查询说明

本机 `calendar schedules list --schema` 请求只有 `begin_time/end_time`，响应为 `schedule_list` 和 `schedule_list_count`；没有 cursor/has_more 字段。全局 `--page-count` 是通用框架选项，并不能证明这个方法有分页。不要启用 NDJSON 分页输出后仍交给单 JSON 信封解析器。

当前[官方 agenda 参考](https://github.com/WecomTeam/wecom-cli/blob/4c74ff28838d8fba267eaab5179d9d56f9ca61ae/skills/wecomcli-calendar/references/calendar-agenda.md) 明确：list只返回当前时刻前后30天以内的日程，超出部分服务端不返回。保守实现应在调用前检查窗口，超界就返回不完整/可查询范围，保留旧投影；不能把截断的空结果记为完整并取消历史或未来来源。这里属于官方文档契约，未通过生产查询重新实测。

每条 `ScheduleInfo` 包含 `schedule_id`、`cal_id`、`timezone`、`repeat_rule`、`is_all_day`。当前 WECOM_CALENDAR_ID 是24私助对“企微授权用户可见日程集合”的逻辑聚合身份，并非真实 `cal_id`；list 没有 calendarId筛选参数。因此观察范围至少限定企微渠道＋这个聚合集合，不能拿它的 liveIds 裁决飞书事件。原始 cal_id 可保留在 raw/归属数据中，不能伪称合成ID是平台日历ID。

### 同步范围与跟随裁决的最小修复

- 将 channel、calendarId/聚合集合、from/to、complete 一同传入对账；`linkedEventIdsInWindow` 限定同一范围。窗口内其他渠道或其他飞书日历均不得被本次同步裁为消失。
- 成功同步的有效空集合，才有权标记本范围内缺失事件取消。信封未知、条目解析失败、服务端范围截断、子请求错误，都保持不完整，不触发删除。
- `sourceVerdict` 根据已存 event.channel/event.calendar_id 读取匹配同步状态；还需判断水位覆盖事件所需范围，而非只看到某个 complete=true就当作有效。
- 本轮不凭字符串格式假设两平台 eventId 永远不会碰撞。修改repo查询时保留渠道/日历范围；是否迁移现有全局event_id主键，应根据实施方案记录兼容策略，避免静默重写旧身份。
- 来源通知失败不能被 complete=true遮盖。已有外部写后本地补偿继续保留；同步路径应保证下次重试仍可完成被欠下的来源裁决。

## 补充核查：飞书周期日程必须显式提交 IANA 时区

2026-10-19 继续核对已安装 `lark-cli 1.0.87` 的本机 `calendar +create --help`、`calendar events create --help`、`schema calendar.events.create`，并复核上述 v1.0.87 官方源码。**结论：`+create` 的 ISO offset 只能确定第一次实例的绝对时刻，不会把 IANA 时区送给平台；不能以此保证指定时区的周期日程在 DST 前后保持同一墙上时间。**

### 已证事实与尚未实测部分

- [同版 `calendar_create.go` 第19–40、167–171、235–250行](https://github.com/larksuite/cli/blob/v1.0.87/shortcuts/calendar/calendar_create.go#L19-L40)：开始和结束经 `ParseTime` 转换后，body 只组装 `start_time:{timestamp}` 和 `end_time:{timestamp}`，`--rrule` 另放 `recurrence`。flag 表（117–126行）没有 timezone；设置进程 `TZ` 或输入 `-04:00` 不会令这个 body 新增 IANA 字段。
- 本机 `lark-cli schema calendar.events.create` 的 `inputSchema.properties.data.properties.start_time/end_time.properties.timezone` 均明确使用 IANA 名称；非全天默认 `Asia/Shanghai`，全天固定 UTC+0。`timestamp` 是秒级字符串，不能与全天用的 `date` 同传。这是已安装版本携带的官方契约；对应[官方创建日程文档](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/reference/calendar-v4/calendar-event/create)。
- ISO offset 不是 IANA 标识：同一个 `-04:00` 无法表达将来何时改为 `-05:00`。RFC5545 把 TZID 放在 DTSTART 等日期时间属性上，而非 RRULE 的规则字段；其纽约每周09:00示例跨 EDT/EST 仍保持09:00。不要把 `TZID=America/New_York` 私自塞进 `--rrule`，也不要给当前 shortcut 拼不存在的 `--timezone`。[RFC5545 §3.2.19、§3.8.5.3](https://datatracker.ietf.org/doc/html/rfc5545#section-3.8.5.3)
- 据此可确定请求缺失时区，**尚未真实创建飞书事件或查询跨 DST 实例，不能写成已验证服务端未来每次触发时间**。真实 App 提醒验收同样未执行。

### 最小安全调用形状

只将需要保留时区的创建路径改用同版原生命令 `lark-cli calendar events create`：向 `start_time.timezone` 和 `end_time.timezone` 一起传本次已固定的 IANA 时区；与固定的首个实例 timestamp、recurrence、reminders 放在同一次创建请求中。不要先用 shortcut 建错时区，再发第二次 patch 补正，否则会多出一个部分成功状态。

例如已固定意图是纽约时间2026-10-30 09:00～09:15、每日重复，原生 body 为：

```json
{
  "summary": "每日提醒",
  "start_time": { "timestamp": "1793365200", "timezone": "America/New_York" },
  "end_time": { "timestamp": "1793366100", "timezone": "America/New_York" },
  "recurrence": "FREQ=DAILY;INTERVAL=1",
  "reminders": [{ "minutes": 5 }]
}
```

上述 timestamp 已用本机 Python `zoneinfo` 验算，分别等于 `2026-10-30T09:00:00-04:00` 和 `09:15:00-04:00`；它只是首个实例的转换验证。重复规则仍由日历平台依据 IANA 时区展开，24私助不逐日重算或代投递。

本机 help 已确认的命令参数如下；以下仅为调用模板，本次没有执行它：

```sh
lark-cli calendar events create --as user \
  --calendar-id '<已固定的实际 calendar_id>' \
  --idempotency-key '<同一提醒意图持久化的稳定 UUID>' \
  --data @event.json --dry-run
```
