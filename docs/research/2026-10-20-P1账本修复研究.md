## V05：原生 SQLite 快照

现有 `checkpoint → read DB → read WAL` 不持有跨文件一致性保证。正式失败回归通过公开 `WorkspaceBackup.create`，在真实 reader 退出、WAL 截断及另一张业务表新提交的交错下，恢复出的备忘表为空，源库仍有原备忘。摘要和 SQLite 完整性检查不能发现这种逻辑遗漏。

选用 Node 内建 `sqlite.backup()`，不再复制在线 DB/WAL 文件。它在 Node 22.16 加入，包最低 Node 22.19 已支持；通过私有临时目标生成独立快照，再读取快照字节。成功或失败后均清理临时文件。备份参加账本串行队列，避免与本连接未提交事务交错；事务内部调用须明确拒绝，不能排到自身之后死锁。关闭必须等待已接纳的备份结束。

- 固定版本契约：[Node 22.19 SQLite backup](https://nodejs.org/download/release/v22.19.0/docs/api/sqlite.html#sqlitebackupsource-db-destination-options)。备份返回 Promise；其他连接写入会使原生复制重新取得一致视图。当前包不需要升级 engines 或新依赖。
- 一致性依据：[SQLite Online Backup](https://www.sqlite.org/backup.html)。由 SQLite 管理源读取及目标提交，避免应用自行拼接不同 WAL 代次。
- 已执行隔离能力探针：Node 22.19.0 / SQLite 3.50.4、Node 24.0.0 / SQLite 3.49.1、Node 26.4.0 / SQLite 3.53.4 均在 checkpoint busy=1 时生成可恢复快照；源随后换 WAL 代次，快照保留原已提交行；目标为目录时拒绝，源数据不变。
- 未选 `VACUUM INTO`：它也可生成一致快照，但这里已有受支持的增量原生备份能力；无须引入同步重建整个数据库的路径。参见 [SQLite VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause)。

联合备份的承诺需要区分：业务账本是 SQLite/PG 的一致快照，工作区、Host 会话及附件仍在线收集，不能声称所有介质共享同一时间点。旧 SQLite 混合文件备份不能仅凭摘要重新认证为一致快照；实施时补充格式与恢复说明，并保留读取旧 PostgreSQL 备份的兼容性。

本项不修改 schema 或主人数据。V21 的重叠目录凭据问题另列 P2，V05 不自动关闭它。验收完成于 `b44648fa355ce389928eb864371786d773cc99e3`：Node 22.19 / 24.0 各 40/40，Node 26 初组 38/38、并发补测和关闭交错补测各通过。Node 26 与旧 Vitest 2 组合出现原生异步操作的额外等待；同版本直接产品探针快照约 3ms、联合备份约 4ms，未复现该运行器延迟。

初审发现事务内部在外部关闭排队后再次关闭会自等待；先固定失败回归，再把事务归属检查前置，真实恢复确认未提交行回滚、已接纳备份与关闭都完成。
