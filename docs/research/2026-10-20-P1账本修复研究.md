## V05：原生 SQLite 快照

现有 `checkpoint → read DB → read WAL` 不持有跨文件一致性保证。正式失败回归通过公开 `WorkspaceBackup.create`，在真实 reader 退出、WAL 截断及另一张业务表新提交的交错下，恢复出的备忘表为空，源库仍有原备忘。摘要和 SQLite 完整性检查不能发现这种逻辑遗漏。

选用 Node 内建 `sqlite.backup()`，不再复制在线 DB/WAL 文件。它在 Node 22.16 加入，包最低 Node 22.19 已支持；通过私有临时目标生成独立快照，再读取快照字节。成功或失败后均清理临时文件。备份参加账本串行队列，避免与本连接未提交事务交错；事务内部调用须明确拒绝，不能排到自身之后死锁。关闭必须等待已接纳的备份结束。

- 固定版本契约：[Node 22.19 SQLite backup](https://nodejs.org/download/release/v22.19.0/docs/api/sqlite.html#sqlitebackupsource-db-destination-options)。备份返回 Promise；其他连接写入会使原生复制重新取得一致视图。当前包不需要升级 engines 或新依赖。
- 一致性依据：[SQLite Online Backup](https://www.sqlite.org/backup.html)。由 SQLite 管理源读取及目标提交，避免应用自行拼接不同 WAL 代次。
- 已执行隔离能力探针：Node 22.19.0 / SQLite 3.50.4、Node 24.0.0 / SQLite 3.49.1、Node 26.4.0 / SQLite 3.53.4 均在 checkpoint busy=1 时生成可恢复快照；源随后换 WAL 代次，快照保留原已提交行；目标为目录时拒绝，源数据不变。
- 未选 `VACUUM INTO`：它也可生成一致快照，但这里已有受支持的增量原生备份能力；无须引入同步重建整个数据库的路径。参见 [SQLite VACUUM INTO](https://www.sqlite.org/lang_vacuum.html#vacuum_with_an_into_clause)。

联合备份的承诺需要区分：业务账本是 SQLite/PG 的一致快照，工作区、Host 会话及附件仍在线收集，不能声称所有介质共享同一时间点。旧 SQLite 混合文件备份不能仅凭摘要重新认证为一致快照；实施时补充格式与恢复说明，并保留读取旧 PostgreSQL 备份的兼容性。

本项不修改 schema 或主人数据。V21 的重叠目录凭据问题另列 P2，V05 不自动关闭它。验收完成于 `b44648fa355ce389928eb864371786d773cc99e3`：Node 22.19 / 24.0 各 40/40，Node 26 初组 38/38、并发补测和关闭交错补测各通过。Node 26 与旧 Vitest 2 组合出现原生异步操作的额外等待；同版本直接产品探针快照约 3ms、联合备份约 4ms，未复现该运行器延迟。

初审发现事务内部在外部关闭排队后再次关闭会自等待；先固定失败回归，再把事务归属检查前置，真实恢复确认未提交行回滚、已接纳备份与关闭都完成。

## V11

### 接纳依据与生命周期

V05 已逐项验收及复审。V11 先通过公开 Runtime 复现不同主人工作区共用 PG 的接纳缺口。决定用工作区 `.24pa/ledger-identity.json` 中随机 UUID 识别逻辑工作区；它与 schema 17 的单行账本归属、已登记主人共同匹配，DSN 和当前路径均不充当身份。

1. 身份文件以同目录完整临时文件加原子 link 安装，竞争创建者读取赢家；文件损坏或丢失不会从有归属账本中反向静默认领。该文件随联合备份保存；复制它表示恢复同一逻辑工作区，不是创建新工作区。路径搬移保留 UUID 与主人，可重新绑定；旧会话/业务记录不自动改写。迁移前停止原 Host，禁止同一恢复副本多活。
2. 接纳、必要 schema 迁移及归属声明在一个事务内完成。PG 在读归属前取固定事务 advisory lock；SQLite 取 `BEGIN IMMEDIATE` 写锁。冲突在迁移及业务初始化前拒绝；失败回滚整次迁移，不停止现有实例。adapter 负责原生事务/元数据，repo 负责共同接纳规则，Runtime 仅交付候选身份。
3. 未声明的库只有在业务表及绑定状态都为空时自动声明（schema 元数据和未使用的 SQLite 序号初值不算业务）。非空旧库须恰好一个历史工作区路径且等于目标规范路径，历史绑定的非空主人集合恰好为当前主人；缺证据、混合多个路径/主人均拒绝，交由离线核对和导出，不自动重分配数据。
4. 初次本地使用可尚未配置飞书主人；同一 UUID 允许从空主人登记第一个主人，登记后不能用重载/重新绑定清空或改成另一主人。后者使用独立工作区及空账本；需要保留历史时先停机备份、离线核对和导出，不由配置补丁迁移归属。

### 固定版本与验证

- 本机隔离 PostgreSQL 16.13（非超级用户 app role），现有 `pg` PoolClient 事务可承载接纳与共享迁移；[PG 16 事务 advisory lock](https://www.postgresql.org/docs/16/explicit-locking.html#ADVISORY-LOCKS) 在事务结束释放。原型两个连接同时首次声明，仅一个成功，另一个在锁内看到已登记身份而拒绝；故意冲突后的 DDL 回滚。探针 `/tmp/pa24-v11-lock-probe.mjs` 和结果将在验收时归档。
- SQLite 使用现有 Node 原生库与串行 adapter；[BEGIN IMMEDIATE](https://www.sqlite.org/lang_transaction.html) 先取得写事务，其他写者只能等待或得到 busy。跨进程竞争由真实测试验证，不能以进程内队列代替数据库锁。
- 宿主绑定接口不变，沿用 `2026-10-19-第二轮工作区归属研究.md` 的先准备后激活边界。归属失败发生在会话准备、工作区业务状态保存和恢复输入前。

验收将覆盖：公开写/读与错误绑定、同工作区重启、独立库及 SQLite 对照、两个进程竞争、旧 schema 可证/混合/不明、迁移故障回滚与重试、路径迁移、主人首次登记与拒绝转让、身份文件丢失/复制及备份恢复。


### A 组配套复审：身份文件是恢复必需件

Spec 复审在 `c53c287` 复现：已接纳工作区的身份文件缺失后，备份仍 `complete=true`，恢复后无法重新绑定。新增缺失、损坏、错身份的公开备份失败回归均在旧实现失败。修正后，schema 17 联合备份记录账本声明的工作区 UUID，校验已复制集合中的身份文件必须有效且匹配；不能以在线原文件存在代替备份内的证据。SQLite/PG 的快照与工作区一起恢复后，均通过公开绑定和备忘检索。schema 16 以前不要求新文件；旧 PG 格式兼容保留。
