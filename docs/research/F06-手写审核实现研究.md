# F06 手写笔记整理与人工审核：实现前研究记录

日期：2026-10-06。范围：P28/#26、P29/#27、P31/#28、P32/#29。装配、PG、lark-cli 信封、Transport 接缝等通用结论来自 [M0-F01 研究](M0-F01-兼容性与装配研究.md)；本文只记录 F06 新核对的一手事实与落地契约。

## 一手核对结论（本机 dsh 0.2.1-alpha.1 / lark-cli 实测）

1. **图片进入子 Agent 的原生路径**：`subagents.startContinuable` 的 `request.prompt` 支持内联 `{type:'image', mediaType, data:base64}` 块，**但 startContinuable 本身不做图片准入**——e2e 实测（2026-10-06）发现未准入的内联块会原样持久化进子会话日志，随后 llm-deepseek 适配器按 `block.attachment` 引用读取时抛 TypeError、被包装成 `DeepSeek Messages transport failed`。图片准入只存在于两条路径：`sessionController.prompt`（`packages/api/session-controller/src/commands.ts:336-346`，先校验模型图像输入模态再 `attachments.admitPromptContent`）与 `subagents.prompt` Remote（`packages/subagent/subagent/src/index.ts:441-449`，浏览器向已存在 child 追加投递）。**结论：插件在 `startContinuable` 前必须自己调用宿主 `ctx.get('attachments').admitPromptContent(prompt)`**，把内联图片换成持久附件引用后再投递；e2e 以 mock LLM 收到的 `{type:'image',source:{type:'base64'}}` 线块数断言「请求真的包含图片」。适配器对目录外未知模型直接拒绝图片（`packages/llm/llm-deepseek/src/images.ts:46` 要求 connection.models 声明 image 模态），因此测试视觉路由用目录内 `deepseek-official/deepseek-flash`（`packages/llm/llm-deepseek/src/models.ts` 声明 `inputModalities:['text','image']`）。原型 agent.js 传内联块「可用」是因为原型模型边界是夹具，未走真实适配器。
2. **lark-cli 文档命令面**（`lark-cli docs --help` 实测）：`+create`（XML/stdin，F01 已用）、`+fetch --detail full`（含 revision_id，F01 已用）、`+update --command str_replace --pattern X --content Y`（定向改文本，用于审核状态块刷新）、`+media-insert --file <本地路径> --type image --doc <id>`（把原稿图片插入文档）。均为固定 argv + `--json` 信封，可走现有 `runLarkCli`。
3. **卡片动作回路**：SDK `card.action.trigger` 已在现有 dispatcher 注册（feishu.ts），`action.value` 原样回传；返回 toast 后由服务端另行核验——与「点击只提交意图，结果以通知为准」的工单要求一致。`transport.sendCard` 已具备（F01 起即有 kind:'card' 的 Outbox 分支）。
4. **图片/文件下载**：SDK `im.messageResource.get({path:{message_id,file_key},params:{type:'image'|'file'}})`；原型已验证 image 路径，F06 增加 type 参数以覆盖「图片文件」消息。

## 设计决策（落地契约）

1. **收集（P28）**：非引用的图片/图片文件消息 → 新建笔记 `N-<seq>`（PG sequence），第 1 页入 `pa24.note_page`（sha256、字节数、media_type 魔数判定、来源 message_id/image_key），原稿字节存工作区 `.24pa/originals/<note>/p<no>-<sha8>.<ext>`；回执消息登记 message_route→note。**引用回执再发图 → 同一笔记追加页**；不按时间窗自动合并（不自动合并不同讨论）。同笔记同 sha 页识别为重复页并拒绝重复保存；魔数未知/超限（10 MiB/50 页）记为 rejected 并反馈。收取与下载中断可重试：下载失败不入页，重新发送即可。
2. **识别（P29）**：Lead 委派 handwriting 时携带 `noteId`；**委派强制要求 `workerModels.handwriting` 视觉路由**，缺失时明确报错（能力缺项不臆造）。Worker 子会话 prompt 附原稿图片块；Worker 调 `pa24_work action=note_submit` 提交结构化结果（transcript/summary/suggestions/unknowns/candidates/relativeDates 分离）。运行时以 staged 操作 `note.publish:<note>:v<n>` 发布：`docs +create`（模板含【24PA·系统】状态块+摘要+正文+疑点+候选行动+转写+原稿索引）→ `docs +media-insert` 原稿 → `docs +fetch` 回读全文+revision → 计算 fingerprint → `pa24.note_version`（含不可变快照）→ Outbox 发审核卡。docId 在创建后立即落操作回执，重试不重复建文档；正文/资源回读完整才发待审通知。
3. **审核（P31）**：审核卡按钮携带不透明随机 token（`pa24.review_token`：绑定 note、version、action、owner_open_id、fingerprint、7 天有效期）。卡片事件 → Inbox（kind=card，先持久化）→ 校验：token 存在且未用/未过期、发送者=owner、版本仍为 pending_review、**重新 fetch 文档核对 fingerprint**（matches 才允许批准；changed/unknown 拒绝并说明）。裁决在 PG 事务内：`review_decision` + version/note 状态同交；文档状态块刷新（str_replace 系统【24PA·系统】行）作为同步意图随后执行并记录 synced/failed（失败=凭证已保存、文档标识同步中）。重复点击返回原结果（幂等）；worker 无 approve 能力（role actions 只有 note_submit）。
4. **失效与再审核（P32）**：fingerprint 覆盖正文文本（按块顺序）、结构顺序与原稿资源摘要（页 sha 列表+图片块位置标记）；**已登记的系统块（【24PA·系统】前缀行）排除在指纹外**——状态块自更新不触发失效循环。`pa24_notes verify`（Lead 工具）有界重读文档并给出 matches/changed/unknown；changed → 最新版本标 stale（已批准版本保留 approved 历史身份）、note 转 needs_rereview 并通知；`republish` 以当前文档为 v(n+1) 候选重发审核卡（差异=按行集合统计增删+样例）。不可解析回读 → unknown，阻止整稿批准。
5. **F06 边界**（如实拒绝）：多页笔记可收集与核对原稿，但识别发布仅支持单页（P29 单页闭环；多页/裁片增强属 F07/P30），多页笔记委派时明确说明。模糊/方向等需解码判定的质量问题不在 F06 判定（无法确定时不臆造，F07 增强）；真实中文手写识别质量另实测。

## 测试边界
