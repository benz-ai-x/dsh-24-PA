## 1. 建议与确定事实

**24PA 新增业务通过驱动和有界连接池直接使用现有 Docker PostgreSQL，不采用 SQLite。dsh 自有域/Session/附件沿用现成非 SQLite 后端，不把开发通用 PG provider 作为首版前置。** dsh 的非 Session KV、Session 日志、全文检索、凭据是四个不同接口，不能因为一个 PostgreSQL 连接已经存在就宣称四者都已支持。

**调度按工作性质复用。** 晨报、复盘、会议准备等需要推理的周期任务，完整复用 `ctx.schedule` 的 Host 定时器、规则与原 Session 唤醒；会议提醒、明确时间提醒等确定性通知，复用同一包公开的时间规则函数，只补 PostgreSQL 到期实例与飞书投递 Outbox。当前源码没有可以把 `ctx.schedule` 到期出口配置成“直接发飞书”的公开 delivery provider；不能在方案中把这个扩展点当成现成功能。[公开时间规则函数](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/index.ts:29) [当前到期出口](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/runtime.ts:101)

如果服务器版本已经增加可等待确认的 typed delivery provider，应优先使用它，从而复用同一个 Host 定时器。若没有，首版建议保持外部插件，不为飞书通知替换 Agent driver，也不把 `agent/pre-step` 当可靠消息队列。将来可向 dsh 提出一个小型通用 delivery seam；这是待实现的上游改进，不是本地已有组件。

### 2.1 现成的无 SQLite 查询模式

需纠正一个容易从包名产生的误判：本地 base 虽挂载 `@deepseek-ai/dsh-session-query-sqlite`，却显式配置 `openAt: never`。这个模式**不会导入或打开 SQLite**，不创建内存库或磁盘库；`ctx.sessionQuery` 的精确读取、标题、过滤、Session 列表与关系追踪仍可用，全文搜索调用才会明确拒绝。它不是“临时用内存 SQLite”。[默认组合及解释](/Users/pc2026/DSH-Space/deepseek-harness/packages/bundle/base/cordis.patch.yml:141) [拒绝入口](/Users/pc2026/DSH-Space/deepseek-harness/packages/session-query/session-query-sqlite/src/index.ts:333)

源码测试还验证了 list/trace 可用、调用 search 返回 `SESSION_QUERY_SEARCH_DISABLED`，以及挂载、使用、卸载均不产生数据库文件；本文阅读了测试，没有执行测试。[现有测试](/Users/pc2026/DSH-Space/deepseek-harness/packages/session-query/session-query-sqlite/tests/sqlite.spec.ts:260)

未发现独立命名为 `jsonl-only` 或 `session-query-fs` 的现成 provider。不能写一个不存在的包名到部署清单。如果用户将“不使用 SQLite”进一步要求为“发行包里也不出现 SQLite 相关依赖”，则需要提供一个复用 `SessionQueryEngine` 的 exact-only provider，或复用服务器 PG provider；这与“不打开/使用 SQLite 数据库”是不同的额外约束。

### 2.2 PostgreSQL 不会自动赋予 storageDomain 跨表事务

`storageDomain.open()` 启动时 `loadAll()`，校验记录后建立内存表；之后的同步读直接访问内存。每个域在本进程有一条写链，先等待 backend 写入持久化，再更新内存和发出 `domain/changed`。域的 `update` 只保证该写链内的单记录变换顺序。[加载过程](/Users/pc2026/DSH-Space/deepseek-harness/packages/storage/storage-domain/src/index.ts:103) [内存与写链约定](/Users/pc2026/DSH-Space/deepseek-harness/packages/storage/storage-domain/src/domain.ts:1) [单记录 update](/Users/pc2026/DSH-Space/deepseek-harness/packages/storage/storage-domain/src/domain.ts:82)

底层 `KvUnit` 仅规定每个单独调用原子、返回后持久化；没有 transaction、批量跨表提交、数据库 CAS、行锁或跨进程变更通知接口。因此把 backend 换成 PG，不会使两次 `put` 成为一个事务，也不会让两台 Host 的内存投影自动同步。[KvUnit 约定](/Users/pc2026/DSH-Space/deepseek-harness/packages/storage/storage/src/backend.ts:76) [现有存储的后续边界](/Users/pc2026/DSH-Space/deepseek-harness/packages/storage/README.md:49)

建议明确两类所有权：

- dsh 自己的 `schedule`、workspace、投影缓存等继续通过 `storageDomain`，首版沿用已有非 SQLite backend，后续才考虑将域路由到 PG；它们仍只有一个运行中的写入 Host。不从旁路 SQL 修改已经加载到该 Host 内存里的域记录。
- 24PA 需要多表事务的业务对象由单一 PG repository 所有。例如“接受审核决定＋更新版本状态＋插入文档同步和通知 Outbox”在一个 PG 事务中提交；飞书网络调用在事务外执行。不要一边通过 `storageDomain` 写该对象，一边通过旁路 SQL 修改同一记录。

首版采用一个常驻 24PA Host，避免把私人助理扩展成不必要的分布式系统。PG 唯一约束保存业务幂等键；Outbox worker 通过短事务领取消息、记录租约与尝试次数，再在事务外调用飞书，最后落回执。将来并发 worker 可使用行锁配合 `SKIP LOCKED`，但它适合队列领取，不是一般业务查询的一致性机制。[PostgreSQL SELECT 锁说明](https://www.postgresql.org/docs/current/sql-select.html) 数据库事务也不能让数据库提交与飞书 HTTP 发送组成同一个原子操作；响应丢失必须保留 `unknown` 并按飞书实际幂等能力核对，不宣称端到端 exactly-once。

Session 日志与 24PA PG 事务同样是不同提交边界。`SessionPersistence.flush()` 是 Session 的持久化屏障，`open(write)` 必须原子取得单写者所有权；未来实现 PG Session provider 也必须满足这些原有语义，不能只往一张 events 表追加 JSON。[SessionPersistence 要求](/Users/pc2026/DSH-Space/deepseek-harness/packages/session/session-persistence/src/index.ts:116)

## 3. schedule 实际可以复用什么

| 能力 | 已有行为 | 使用限制 |
|---|---|---|
| 创建与修改规则 | after、at、every、daily、weekly、五字段 cron；标题、规则校验和时区语义 | 不支持秒级 cron；every 最短 60 秒。 |
| 时间运算 | 公开 `create*ScheduleRecord`、`resolveRecurringOccurrence` 等纯函数，显式传入当前时间 | 使用包根公开导出；不复制内部函数或深引未发布 runtime。 |
| 重启恢复 | Host 启动扫描 active 任务，安排最近定时器 | 必须持续运行；不是外部系统级定时服务。 |
| 误点和补发 | 周期任务只取最新错过的一次，推进到未来；同 Session 的到期周期任务批量投递 | 不能承诺补发每一个漏掉的 occurrence。 |
| 原 Session 续跑 | `sessionController.resolveAgent()`，然后 `followup()`、`sessions.flush()` | 唤醒的是创建任务时绑定的原 Session；不是当前聊天选择的会话。 |
| 成功记录 | 持久化 inbox 后更新任务状态和 delivery history | 只确认内部收件箱，不确认模型完成、外部发送或人已读。 |
| 故障 | 失败保留任务并记 warning；重启、另一次唤醒或管理变更可再次驱动 | 没有自动失败重试定时器；Session 与任务写入之间可能重复。 |

### 3.1 建议的两条执行路径

**需要模型的工作**：`ctx.schedule` 到期 → 原自动化 Session → 24PA 工具读取日程/任务 → 生成晨报、复盘或准备材料 → 已提交结果进入统一 PG Outbox → 飞书发送。自动化使用专用业务 Session，发给用户时标明来源；不切换用户当前会话。原生 schedule 的重复唤醒用业务 occurrence key 去重，模型执行失败与外部发送失败分别保存，不能以 schedule delivery history 充当业务成功表。

智能任务关联 delivery history 不能无限等待：runtime 先 flush Session 再提交历史，后者失败时原 messageId 的历史可能永远不存在，后续重投又会换 ID。采用有限等待后 `delivery_unconfirmed`，暂缓无归属输出/外部写入，核对持久 Session、规则与 PG 工作记录；无法证明则过期或转待处理，不按当前时间猜 occurrence。[提交窗口](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/runtime.ts:122)

**确定性提醒**：用户的明确请求形成 PG 提醒规则 → 使用 dsh 导出的规则创建函数得到 `scheduledAt` → 到期时在短 PG 事务内锁定该业务提醒，调用 `resolveRecurringOccurrence`，同时插入唯一发生实例/Outbox 并推进下一次时间 → worker 按安静时段、过期策略、限流与重试发送固定消息。一次性提醒无需模型运行。Cron 解析、DST 和 next occurrence 全部调用 dsh 已有实现；24PA 只新增业务可靠投递需要的领取、去重和回执逻辑。[返回 occurrence 与 next target](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/domain.ts:1098) [统一 recurring 分派](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/domain.ts:1124)

这是对当前公开接口的最小补充，不应包装成“另造一个全功能 ScheduleService”。直接提醒和原生 schedule 不能同时拥有同一个提醒的到期发送权。修改或取消直接提醒时检查业务 revision，取消尚未发送的旧发生实例；飞书日历实例时间优先采用飞书返回的具体 occurrence，不能把飞书复杂重复日程自行转换成近似 cron。

若复用服务器已有 delivery seam，建议其承载明确结构的 `scheduleId / occurrenceAt / originSessionId / deliveryKind / payloadRef`，在 PG Outbox 已持久化后才返回“已接收”；只有接收方持久化成功，schedule 才推进规则。它确认的仍是入队，不是消息已送达。若源码需增加该 seam，应先明确兼容旧任务、注册/卸载、错误传播、存储格式与真实组合测试，再列入经过审核的开发范围。

### 3.2 为什么不把 Agent hook 当主路径

`agent/pre-step` 确实可改变进入步骤的消息，技术上可以把特殊提醒写入 Outbox，移除该批提醒，再让空消息步骤结束，从而不调用模型。这比“必然要模型”更准确；但它不是等价的 schedule delivery adapter。[pre-step 约定](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/runtime-types.ts:309) [首步为空可不发模型请求](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent-loop/src/agent.ts:321)

不建议首版选它的具体原因：

1. 消息在 hook 执行前已经被 inbox claim；系统上下文 assembly 也先运行。直接返回 reject 会让 turn 变为 blocked，不会把已 claim 的输入自动送回 inbox；混合用户消息必须完整保留，不能整批误吞。[claim 与 hook 顺序](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent-loop/src/agent.ts:267) [reject 语义](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/runtime-types.ts:289)
2. schedule 在 `followup()` 后等待 Session flush，**不等待此 hook 或 PG Outbox 提交**。二者可以交错；需要另做日志回放与补偿，才能覆盖“任务被推进、已 claim 消息落日志、Outbox 尚未持久化就崩溃”的窗口。一个简单 `await outbox.put()` hook 不足以证明无丢失。[schedule 提交顺序](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/runtime.ts:122)
3. 当前 schedule 消息 source 只携带 `kind: schedule`，occurrence 在格式化文本中。依赖解析模型消息文本作为业务事件协议会增加格式耦合；不能因为文本包含 schedule id 就假定它是独立持久队列接口。[消息构造](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/runtime.ts:114)
4. `agent/inbox/inserted` 是 emit 观察事件，不是可等待的投递确认入口。[事件定义](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/runtime-types.ts:281)

同样，没有一个可并排注册的公开 `AgentDriver` 插槽。当前公开接口是 `AgentFactory`；registry 同时只允许一个 factory，默认由 agent-loop 提供。自定义 factory 需要承担 Agent 创建、恢复、所有权、scope、停止/清理和 inbox 行为，不是为通知换一个函数。对 24PA 而言成本和侵入都明显超过必要范围。[AgentFactory](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/index.ts:165) [唯一 factory 检查](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/index.ts:346)
