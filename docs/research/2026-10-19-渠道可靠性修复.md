# 渠道可靠性修复研究

日期：2026-10-19。基线：main `c36e464`，规格 2.12，沿用 [F03](F03-任务清单实现研究.md)、[F12](F12-运维与恢复实现研究.md)、[F16](F16-企微日程待办实现研究.md)、[F25](F25-SQLite默认存储实现研究.md) 已验证的渠道与存储契约，不扩大平台能力。

## 本地证据与约束

- 当前源码的 `stagedOperation` 对已有 running 行重新放行；外部成功后的投影失败又会被普通 catch 标成 failed。企微无平台幂等键，因此不能靠重复调用恢复。
- 当前 `sendOutbox` 将发送、sent 回执、回复路由放进同一 catch；纯内存故障注入验证路由写入失败会把已 sent 行退回 pending。claim 后的 sending 行也缺少启动核对。
- Task 修改的幂等键漏掉 plannedAt/estimateMinutes；对象已有 channel 必须决定后续读写，不能随当前 todoChannel 迁移。

## 实施落点

外部操作 module 集中认领、未知结果阻断和远端回执保存；已有远端回执只补本地投影，不再执行远端。远端确认与本地保存之间仍无法跨系统原子提交，缺回执的 running/发送中行停在 unknown，提示核对，绝不盲重发。沿用 action_operation.receipt 保存内部阶段信息，无结构迁移。

持久投递 module 在远端确认后立即保存 message_id；发送后的本地回复路由可独立补记，不能降级为待重发。重启将无回执 sending 转 unknown，有回执发送只补路由。存储沿用 SQLite/PostgreSQL 两个 adapter，传输沿用飞书 SDK/fake、企微 CLI/stub。

任务生命周期 module 统一按对象 channel 查阅/刷新/完成/删除；创建才采用当前 todoChannel。本地计划/估时独立修改不制造空的远端 update；操作身份包含显式本地字段，同时保留旧键对默认参数的兼容。

## 验证范围

使用隔离 SQLite/PG 账本与本地传输 adapter，在 module interface 测试重复、崩溃遗留、远端成功后本地失败、unknown 禁止重试、对象渠道和计划字段；保留既有 e2e。未访问生产或向真实主人发送消息；真实平台故障窗口不以本地模拟宣称已验。

已执行：渠道可靠性故障注入测试覆盖持久回执、并发认领、未知发送、原发起入口、工作区切换前排空；共享 repo 场景在 SQLite/PostgreSQL 两端验证认领与投递恢复。既有 f03/f04/f08/f16 共 18 项端到端测试通过。外部操作结果缺少回执仍保留待核对限制，不承诺跨系统 exactly-once。
