## 1. 建议结论

推荐 **24PA 飞书入口与现有 dsh Web 运行在同一 Host 进程，复用同一 SessionController、Agent Registry、Session Persistence 与 Workspace Registry**。飞书中的“当前会话”只是一条保存在 PostgreSQL 中的路由指针；切换指针不停止旧 Agent，不复制历史，也不把全部会话内容拼进主会话。普通日常事务、项目专题、手写笔记处理可以拥有各自的 Session；业务事实、审核记录、提醒与任务状态独立保存，不依赖某一会话是否正在打开。

首版核心是在飞书中创建、查看、切换和恢复 24PA 的 A–E 等真实 dsh Session，固定使用同一个飞书 CLI profile。输入“切换到 B”只将 PG active_session_id 从 A 改为 B，展示 B 的进展；A 继续运行，结果通知不改当前指针。“查看 B”只读 B 状态，不切换当前 A。任意非 24PA coding 会话的接入是额外扩展，须检查 owner allowlist、preset 与执行策略，不作为五会话切换的前置。

这是利用已有公共服务的设计建议。其依据是：SessionController 已有普通 Session 的创建、收养、恢复、prompt、历史、fork、cancel；Registry 的 `get/list` 只表示在线 Agent；持久历史由独立服务维护。[SessionController](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/index.ts:221) [Agent Registry](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/index.ts:561)

## 3. 可直接复用的精确 API

下表以同 Host 的 `ctx` 公共服务为准。远程 Client 对应的 namespace 通过生成的 Remote 接口调用；Remote unary 返回 `RemoteResult<T>`，需要检查 `ok`，不能按同进程 Promise 的异常模式编写调用方。[Remote 返回语义](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/gateway/README.md:48)

| 目的 | 现有调用 | 前提、效果与限制 |
|---|---|---|
| 新建或收养 | `ctx.sessionController.create({ sessionId?, workspaceId?, cwd?, agentPreset? })` | `workspaceId` 与 `cwd` 二选一。显式 ID 可以收养 live Session 或恢复冷 Session；既有 cwd、preset 必须匹配。新建时记录绝对 cwd；不传 ID 则新建。没有 `owner` 鉴权参数，由 24PA 在调用前执行 |
| 继续冷会话 | `ctx.sessionController.resolveAgent(sessionId)` | 返回 `{agent}` 或 `{error}`；同 ID 并发恢复共用 Promise。只用于普通 Session；子 Agent 有专门 ownership 路径，不能当普通主题会话恢复 |
| 普通消息 | `ctx.sessionController.prompt({ requestId, sessionId, mode:'queue', content, clientTimeZone:'Asia/Shanghai' }, signal)` | 非空文本或附件；返回 `{accepted:true}` 表示准入，不是最终完成。需要稳定 requestId 和外层 durable ingress |
| 补充当前工作 | 同上，`mode:'steer'` | 交给最近的 step 边界；不承诺立即中止当前模型/工具。空闲时会启动新 turn |
| 直接宿主投递 | `agent.followup(message)` / `agent.steer(message)` / `agent.send(message,target,wakeup)` | 公共 Agent 能力；默认首选 Controller 完成图片 admission 与 requestId 路由。`followup` 没有每条消息的完成 Promise |
| 查会话 | `ctx.sessionController.list({},signal)` | 冷安全摘要；返回 `sessionId/running/agentAvailable/cwd/projections` 等。24PA 再按 allowlist 筛选。request 类型有 cursor，但当前实现忽略 request，不应承诺服务端分页 |
| 查原始历史 | `ctx.sessionController.inspect(id,signal?)`；或 `ctx.sessionQuery.readSession(id)` | 冷读取，不启动 Agent。`inspect` 返回 header、事件与继承事件数；查询服务还提供 surface、event、trace |
| 分页历史 | `ctx.sessionController.page({address:{kind:'session',sessionId},throughSeq,beforeSeq?,maxMessages?,turnWindow?},signal)` | `throughSeq` 是读取切点；返回按时间顺序的页面。打开 UI 时先获得精确 cursor，再取旧页 |
| 订阅事件 | `ctx.sessionController.follow({address:{kind:'session',sessionId},maxMessages?,assistantStream?:true},signal)` | opening snapshot + 后续事件。**对冷普通 Session，opening 后会异步激活 Agent**；不能作为无副作用的后台列表查询 |
| 在线状态 | `ctx.sessionController.control(signal)`；同 Host 可监听 `agent/status`、`session/event` | control 是进程 generation 的完整基线与更新；连接重建时替换基线。瞬态 token/状态不能代替持久事件回放 |
| 读投影 | `ctx.sessionController.projections({sessionId},signal)` | 不激活 Agent；可读 inbox、title 等已注册投影，缺失会话返回 null |
| 改名 | `ctx.sessionController.rename({sessionId,title})` | 需挂载 sessionTitle；可能恢复冷 Agent；返回规范标题与 event seq |
| 编辑排队消息 | `ctx.sessionController.updateQueue({sessionId,itemId,action})` | `action` 为 edit/remove/steer；edit 只接受非空文本；已被领取的消息不可再编辑；steer 只允许把 running Agent 的 next-turn 项移到 next-step，不是冷态唤醒按钮 |
| 停止当前 turn | `ctx.sessionController.cancel({sessionId})` | 只对 live 普通 Agent；实现为 `agent.cancel({kind:'user'},{keepInbox:true})`，保留待处理 inbox；这不是清空所有工作 |
| 创建分支 | `ctx.sessionController.fork({sessionId,atSeq?})` | 默认截至最近已完成 turn；明确 atSeq 可以在开放 turn 内截取并合成 closers。返回新 Session，继承原 preset 与历史，**不会复制真实外部业务结果** |
| 归档/恢复显示 | `ctx.workspaceRegistry.archiveSession(id,{stopActivity?})` / `unarchiveSession(id)` | 对应 Remote 是 `workspace.archiveSession/unarchiveSession`。归档是 Host 全局状态，会影响 Web，默认有工作则拒绝；恢复显示不等于恢复执行 |
| 持久性确认 | `await ctx.sessions.flush(agent.session)` | 等待持久化 listener 成功，返回是否有 listener；24PA 必须要求存在后端，不能把 `false` 当可靠落盘 |

### 三个容易写错的 API 事实

1. 普通多会话没有独立 `session.switch()`。切换是 24PA 路由指针的变更；需要执行时才解析目标 Agent。不能为“切换”dispose 旧 Agent。
2. 没有通用 `session.get()` Remote 读取全部状态；选择 `list/projections/page/follow`，或同 Host `inspect/sessionQuery`。`follow` 当前请求类型没有客户端 `afterSeq` 参数；断线追赶使用 opening cursor、分页与客户端保存的持久水位，不能捏造 `follow({afterSeq})`。[follow 类型](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/types.ts:486) [cold promotion](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/history.ts:179)
3. SDK stdio 并非这个 Remote API。SDK wire 只有 `initialize/session-prompt/shutdown` 三个请求；没有 cancel、history、fork 或 resume 请求。其遇到 SDK 未知 ID 时调用 `agents.create`，不会自动恢复既有持久 Session。故第一版不要用每消息启动 SDK 子进程实现机器人多会话。[协议方法](/Users/pc2026/DSH-Space/deepseek-harness/packages/sdk/protocol/README.md:33) [SDK 创建逻辑](/Users/pc2026/DSH-Space/deepseek-harness/packages/sdk/server/src/server.ts:261)

## 4. 飞书中的交互与确定性路由

以下是 24PA 建议实现的产品行为，底层使用上一节已有服务。

| 用户动作 | 推荐行为 |
|---|---|
| `新建会话：旅行安排` | 先生成绑定的 dsh 会话与稳定 Session ID，create 成功、flush 后绑定；成功后将其设为当前目标并显示名称 |
| `我的会话` | 列出允许访问的最近会话、当前标记、运行/等待/失败状态；支持按名称搜索与分页卡片 |
| `切换到旅行安排` | 名称唯一时切换；同名则用选择卡。旧会话继续执行，卡片明确当前会话名称 |
| `回到上一个会话` | 恢复 PostgreSQL 保存的最近指针；不靠模型猜测“上一个” |
| 对旧回复引用回复 | 使用原消息绑定的 `hostId + sessionId`，默认只影响这条输入，不静默改变当前会话 |
| 点击笔记审核/延期/继续按钮 | 按钮固定绑定 owner、对象 ID、版本和会话；即使已切换会话也处理原对象；检查一次性 token、有效期与状态版本 |
| `这个会话先放着，帮我查下午安排` | 创建或切换到日常助理会话；原任务按原会话继续，输出有明确会话标题 |
| `补充：第二页日期其实是周四` | 用户明确补充当前工作时走 steer；普通下一件事仍走 queue |
| `停止当前处理` | cancel 当前 live turn，说明其余排队项仍在；“全部取消”才取消 24PA 工作单并清理 pending inbox |
| `归档这个专题` | 展示运行与原生计划清单；存在 active Schedule 也默认拒绝归档。明确“停止并归档”才用 stopActivity，并删除 active 原生计划；PG/飞书提醒另行决定 |
| `恢复已归档专题` | unarchive 后查看摘要；需要继续时再 prompt；不把恢复显示等同于自动执行旧任务 |
| `从这里另开一个方案` | fork 到新 Session；不把 fork 当合并操作，也不重复已经创建的飞书任务或文档 |
| `继续 dsh 的 XX 会话` | 先从已授权清单唯一定位；显示原 workspace、preset、执行模式，再绑定。未在 allowlist 的目标不可直接控制 |

路由优先级建议固定为：**已验证按钮目标 → 显式指定的会话或引用消息映射 → 当前指针 → 首次默认日常会话**；显式目标和引用目标冲突时先澄清。目标写入 PostgreSQL ingress 记录后不可因之后切换而改变。未知旧消息、过期按钮或歧义名称返回可操作的选择提示，不自动转投当前会话。

每条跨会话主动结果都带“会话：名称”与“查看/继续此会话”入口。后台任务完成通知不改变当前会话；用户正在安排日程时，不会因为笔记处理完成而突然把下一句话发给笔记会话。

## 5. PostgreSQL 只保存 24PA 必要状态

建议最小数据集合如下；名称仅是设计草案，不是已实施 schema。

| 数据 | 关键字段/唯一约束 | 目的 |
|---|---|---|
| `pa_conversation` | owner、channel、chat、host_id、session_id、display_alias、binding_mode、preset_hint、fixed_lark_profile、allowed_workspaces | 身份与访问授权；preset_hint 只是展示快照，使用前核对真实 preset |
| `pa_chat_cursor` | `(owner,channel,chat)` 唯一；active_conversation、previous_conversation、revision | 稳定当前指针；事务/CAS 切换 |
| `pa_ingress` | 平台事件/消息 ID 唯一；固定 conversation、request_id、原始输入引用、处理状态 | 防止 webhook 重投、重启丢消息和切换后误投 |
| `pa_message_route` | `(channel,chat,message_id)` 唯一；conversation、business_object、request_id | 引用回复和旧卡片正确路由 |
| `pa_session_cursor` | `(host_id,session_id,consumer)` 唯一；last_observed_seq | 断线/重启后补齐持久事件；不保存进程内 token 游标为永久事实 |

不另造完整 dsh transcript、不复制 compaction fold、不在 PostgreSQL 再维护一套 live Agent 状态机。业务队列与 Session inbox 用途不同：前者记录用户已授权待办与交付承诺，后者控制当前 Agent 接下来处理什么。二者通过稳定 requestId、messageId、event seq 关联。

这是 24PA 的持久化建议。dsh 默认 Session 日志位于 `$DSH_HOME/sessions`，默认非会话域为 JSON；JSONL 持久化与 SQLite 搜索索引不是同一组件。[基础组合](/Users/pc2026/DSH-Space/deepseek-harness/packages/bundle/base/cordis.patch.yml:130)

## 6. 同 Session 并发、准入与结果关联

推荐 PostgreSQL ingress 唯一键先接住飞书事件，再由短期的会话准入锁串行执行 `prompt → flush → 更新已准入状态`。锁只保护准入，不占用整个模型 turn；不同 Session 可并行，按配置限制全局活跃数。同一个 Session 内让 dsh inbox 接管顺序：queue 是逐条普通 turn，steer 在后续 step 被接纳。飞书主动提醒直接发送到正确 chat；只有需要推理的工作才进入相应 Agent。[Agent 投递语义](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/runtime-types.ts:204)

`requestId` 防重是重要的第二道保护，但不是独立的 exactly-once 保证。实现先检查 pending inbox 和已记录的 `user/message`，随后跨过附件准入的 await，且未在准入后自动 flush；因此同时重投、已领取但尚未记录 user/message、取消后重试等情况不能只凭这一检查解决。24PA 应保存原始输入、接纳轨迹与取消原因，串行处理自己的重复请求，失败后对账再决策。[防重检查](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/commands.ts:602) [准入顺序](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/commands.ts:311)

一条消息的完成状态不能由 `agent.status === 'idle'` 或 `whenIdle()` 推断。多个 queue/steer 可能共享同一 running 区间。24PA 用 `source.rpcId` 找到消息及持久 `agent/inbox/spliced`、`user/message`、turn/step 结果关系；按最终 assistant/业务对象结果建立 outbox。无法精确归因时标记为该会话运行区间的结果，不伪称某条 followup 的独立结果。[whenIdle 范围](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent/src/runtime-types.ts:185) [防御规则](/Users/pc2026/DSH-Space/deepseek-harness/docs/defensive-patterns.md:13)

Web 与飞书同时对同 Session 输入时仍由同一 Agent/inbox 执行；24PA 展示目标正在工作并默认排队。除用户明确要求补充/停止外，不因新消息中断既有工作。24PA 的锁不能宣称覆盖 Web 所有输入，但同 Host 避免了第二个 Agent 写同一日志的问题。

五个 Session 使用相同飞书身份，会修改同一批外部资源。24PA 对相同任务/日程/文档的操作按资源 ID 协调、写前检查版本、完成后刷新投影；独立资源仍可并发，不能将“一个 profile”误解成“只能一个 Session 工作”。这只覆盖 24PA 内的写入，不能替代对用户直接在飞书修改的检测。重复提醒按业务来源和 occurrence 合并；CLI 自己管理同一 profile 的令牌刷新。

归档和原生 Schedule 已有整合：`schedule` 向归档 admission 报告 active 计划，默认阻止归档；`stopActivity:true` 会逐个删除该 Session 的 active 计划，可能部分成功后报错。归档后的模型 step 由 ArchivedSessionGate 拒绝。不能声称原会话的智能计划在归档后照常运行，也不能假定 unarchive 自动重建删除的计划；外部 PG/飞书提醒属于另一层。[Schedule 归档钩子](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/index.ts:184) [停止并删除](/Users/pc2026/DSH-Space/deepseek-harness/packages/schedule/schedule/src/index.ts:430) [归档门禁](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/archived-session-gate.ts:23)

## 7. 重启与断线恢复的真实范围

dsh 冷恢复会先获得持久写句柄，再读取日志；未闭合 turn 会追加 `interruptedTurnClosers`，包括缺失工具结果与 turn/step 终止。它恢复历史和 inbox 投影，**不会从崩溃时的模型 token、JavaScript 栈或工具进程指令位置继续**。已经记录工具调用但没有结果时，结果被标为 `TOOL_OUTCOME_UNKNOWN`；源码明确要求先核对副作用，不能盲目重试。[恢复实现](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent-loop/src/index.ts:840) [工具恢复语义](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/session/src/repair.ts:14)

另一个重要限制是：正常 `AgentHandle.dispose()` 会调用 `cancel({kind:'disposed'})`，未传 `keepInbox`，因此会清理并记录取消剩余 inbox。优雅停机不等于保留所有排队工作。24PA 不能把自己的已接纳承诺只保存在 dsh inbox。[dispose 实现](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent-loop/src/index.ts:523) [cancel 默认清队列](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent-loop/src/agent.ts:175)

建议恢复顺序：

1. PostgreSQL 可用、owner 绑定与必要 dsh 服务就绪后，先读取 24PA 未完成 ingress/job/outbox；不启动所有历史会话。
2. 每个待恢复绑定的 dsh 会话先按 `hostId + sessionId` 核对存在性、allowlist、归档、preset 和最近持久事件；只读检查使用 inspect/query/projections，避免批量 follow 意外激活。
3. 尚无已接纳证据的输入可以用原稳定 requestId 重试；仍在 inbox 的输入保留原身份，按显式恢复策略唤醒，不能重复插入。
4. 已被领取/运行中但中断的工作创建独立 recovery 请求，引用原工作 ID 与已完成动作。只读或受幂等保护的步骤可续办；飞书写操作先按外部 ID/内容版本对账，结果不明则进入待核对状态。
5. 用户主动取消的工作不因重启复活；服务停机清除的已授权工作由 24PA ledger 区分并恢复。已完成但未发送的结果只补 outbox，不重跑任务。
6. 恢复后保持原当前会话指针；只对受影响工作发送一次“已恢复/需处理”通知，不把每个冷会话都提示为故障。

恢复规则属于待实现的 24PA 逻辑，应作为验收点。dsh 无公开 wake-only 控制方法；仅调用 resolveAgent 不应被当作“保证 drain 旧队列”。恢复唤醒需要明确的新控制输入或已有合法调度路径，并验证不会重复原 prompt。`updateQueue({action:{kind:'steer'}})` 要求 Agent 已 running，不能用于唤醒冷恢复后的 idle Agent。[恢复后的初始化](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent-loop/src/index.ts:753) [Agent send](/Users/pc2026/DSH-Space/deepseek-harness/packages/core/agent-loop/src/agent.ts:154) [queue steer 条件](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/commands.ts:477)

## 8. 既有 dsh 会话与隔离部署

| 方案 | 能力/代价 | 建议 |
|---|---|---|
| 同一 Host，24PA 与 Web 共享服务 | 可引用同一个 live Agent、持久 Session 和 Controller；排队、取消、历史与恢复走统一路径 | 第一版首选；24PA preset 与工具策略仍需独立约束 |
| 同 DSH_HOME，两套 Host 进程 | 能看见同一批文件，不代表可共同执行；live/idle Agent 只要持有 write handle 就会占锁 | 不作为集成方案；不要尝试删除锁或强抢 Session |
| 独立 DSH_HOME，独立 Host | 24PA 自己的数据隔离良好，默认看不见既有 dsh Session | 只在用户确实需要隔离时选择；接入既有会话必须走原 Host 的授权 Remote 接口 |
| 将旧 transcript 复制到新会话 | 可以保留上下文片段，但不是恢复原会话；会失去原身份、执行关系与 live 状态 | 仅用于明确的摘要导入，显示来源及捕获版本 |

JSONL backend 的写锁覆盖 write handle 生命周期，POSIX 使用内核 flock，进程退出才自然释放；同一 Session 两个进程写入会被拒绝。Controller 将争用映射为 `session/writer-held`。收到此错误应转向会话所属 Host 或报告当前持有者仍在工作，而不是创建一个同 ID 替代会话。[写锁](/Users/pc2026/DSH-Space/deepseek-harness/packages/session/session-persistence-jsonl/src/lease.ts:1) [错误映射](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/agent.ts:218)

独立 Host 的远程桥接若以后需要，应使用原 Host 的鉴权 Connection/API Gateway/生成 Session Remote，保留明确 endpoint 与 host identity；现有 Web Remote 是受信任 Host 通道，不是拿飞书 open_id 即能自动变成多租户授权系统。24PA 的 allowlist、输入来源限制与事件过滤仍由 24PA 实现。Remote 不是 SDK stdio，两者不能混用。[Gateway 与 Connection](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/gateway/README.md:27)

## 9. 跨 preset 与执行权限

现有 dsh 会话可能使用编码 preset，具有 Shell、文件写入或其他工具能力。Controller 收养时检查 preset 一致性，恢复时重装持久 preset；`agentPresets.select` 只允许第一个 turn 前更换 preset，开始过的会话会返回 `agent-preset/locked`。fork 也继承源 preset。不能把已有 coding 会话“换成 24PA preset”当作安全隔离措施。[收养检查](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/agent.ts:463) [preset 锁定](/Users/pc2026/DSH-Space/deepseek-harness/packages/preset/agent-preset-registry/src/index.ts:341) [fork 继承](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/commands.ts:267)

建议绑定模式区分为：

- **只读查看**：允许列标题、状态、历史摘要；禁止 prompt、cancel、fork、archive 等操作，且只有 allowlist 会话可见。
- **摘要引用**：新建 24PA preset Session，把用户选择的来源作为有界只读背景；不移交原会话工具权限。
- **原地继续**：仅对用户明确绑定且 Host 执行策略已验证的会话开放。显示原 workspace/preset；保持原规则，并在真正工具执行入口检查来源和授权。若原会话需要的审批通道无法从飞书完成，拒绝相关写操作并提供在 dsh Web 处理的入口。

所有平台消息、引用、按钮、Session ID 与文档审核动作都必须重新验证 `tenant + owner + chat + conversation` 对应关系。不能仅验证机器人签名，也不能仅使用 `chatId → sessionId` 全局 Map；签名证明平台事件来源，不证明该人拥有目标会话。模型提示词和工具列表过滤不能代替执行器鉴权。

这些是 24PA 的安全设计要求，不是 dsh 自动提供的 per-owner ACL。尤其 `sessionReferenceResolver` 明确假定宿主有权读 query 暴露的所有会话；接入时必须过滤候选，并检查用户提交的原始 `dsh-session:` mention，防止绕过选择列表。[引用信任范围](/Users/pc2026/DSH-Space/deepseek-harness/packages/context/session-reference/README.md:138)

## 11. “不使用 SQLite”对会话方案的影响

Session 日志默认是 JSONL，可继续复用，与 SQLite 无关。24PA 的业务持久化使用 PostgreSQL。需特别核查的是：SessionController 强依赖 `sessionQuery`；`dsh-session-query` 是抽象服务，不能单独挂载，目前源码的出厂 provider 是 `dsh-session-query-sqlite`。base 将其设为 `openAt: never`，源码保证此配置不导入或打开 SQLite，只保留继承的 exact/list/filter/trace，搜索返回 disabled。[依赖](/Users/pc2026/DSH-Space/deepseek-harness/packages/api/session-controller/src/index.ts:104) [provider 抽象](/Users/pc2026/DSH-Space/deepseek-harness/packages/session-query/session-query/src/index.ts:98) [禁用 SQLite](/Users/pc2026/DSH-Space/deepseek-harness/packages/session-query/session-query-sqlite/src/index.ts:98)

如果验收要求连 SQLite provider 包也不加载，不能简单删除插件导致 Controller 不启动。需在获批开发时补一个极薄的非 SQLite provider，继承现有 SessionQueryEngine 的完整 exact/read/filter/trace 行为，仅处理两个 abstract search 方法，或对接服务器已有且符合该接口的 PostgreSQL provider；不要重写历史读取、日志迁移与 lineage。M0 应检查服务器实际组合，明确采用哪个路径；用户已说明是 Docker PG、应用直连，本方案不依赖额外 PG 查询插件。

## 12. 多会话验收清单

- A 会话处理多页笔记时切换到 B 查询日程，A 继续完成，结果卡仍归 A，当前指针保持 B。
- 在 B 引用回复 A 的旧消息，输入仅投递 A；过期/越权旧卡无法作用于任何当前对象。
- 同一飞书事件连续/并发重投，只有一条逻辑 ingress；输入附件准入期间切换会话仍送原目标。
- 同 Session 从 Web 与飞书各发一条消息，普通输入排队、明确补充才 steer；取消当前 turn 不被误报为清空所有队列。
- 新建会话、prompt、flush、模型执行、外部写操作、结果出站各阶段强制重启，恢复后不丢未完成承诺，也不重复创建飞书文档/任务/日程。
- 优雅关闭造成 inbox 被清理时，区分服务停机与用户取消；用户取消不能被恢复 worker 重新提交。
- 冷历史列表不激活全部 Agent；明确继续才恢复；错误 preset/cwd、损坏日志、未知版本与 writer-held 均给出明确可操作状态。
- 归档含运行 turn/job/active schedule 的会话时默认拒绝；明确停止并归档会删除原生计划，部分失败须对账；恢复显示不自动重建计划，外部 PG 提醒另行处理，影响同步到 Web。
- 绑定已有编码会话不改 preset；无执行策略的会话只能只读/摘要导入，无法通过拼接 Session URI 绕过 owner allowlist。
- SQLite 不建立、不打开；若禁用整个 SQLite provider，替代 query provider 的 Loader 组合必须实际通过。

以上为待开发验收要求；本次只完成源码核查与设计修订依据。
