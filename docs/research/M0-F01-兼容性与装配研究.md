## 2. 装配事实（原型已验证流程 ＋ 源码复核）

原型 `scripts/prototype.mjs` 已在本机用官方 CLI 验证过的安装链，正式版沿用：

1. `dsh --profile <name> --from-default-profile web --dump-config` 初始化独立 profile；
2. `dsh plugin --profile <name> add <bundle-dir> --ignore-scripts --store-dir <store>` 登记插件（有 `dsh.bundle.patch` 声明的包会把 patch 行并入 profile bundles）；
3. `dsh --profile <name> --host 127.0.0.1 --port <port> --no-open` 启动常驻 Web Host。

源码依据：bundle 声明字段 `package.json.dsh.bundle.patch`（`packages/util/package-manifest/src/types.ts:29-39`）；安装后 reconcile 追加 patch（`packages/boot/plugin-manager/src/operations.ts:88-113`）。peer 依赖兼容闸在安装时校验（`apps/cli/src/plugin.ts:17-62`），因此正式包声明 `@deepseek-ai/dsh: 0.2.1-alpha.1` 等 peer 范围与原型一致。

preset 行：`@deepseek-ai/dsh-agent-preset` 的 `PresetDefinition { id, name, description, order, plugins }`（`packages/preset/agent-preset-registry/src/definition.ts:5-11`）。工具白名单两层：preset 行只挂需要的工具行；运行时按角色 `ctx.tools.restrict({ allow })`（`packages/core/tools/src/index.ts:1097-1135`，原型 agent.js 已用此法按 Lead/Worker/维护会话分权，验证可行）。

正式版标识：插件名 `pa24`、preset id `pa24`（显示名「24私助」）、工具前缀 `pa24_`、PG schema `pa24`、状态目录 `dshHomePath('24pa')`。原型（`pa24-prototype`）是一次性体验件，不迁移其数据；正式版是新命名空间。

## 3. 会话与子 Agent 面（F01 关键路径）

以下 API 均被原型在真实 Host 中使用过，本轮源码复核签名未变：

- `ctx.sessionController.create({ sessionId?, workspaceId?, agentPreset? })`：幂等创建/收养；原型的 `agent-preset/conflict` 处理（旧会话被改成其他 preset 时保留历史并新建入口）来自 `packages/api/session-controller/src/agent.ts:444-495` 的收养检查，符合 P03 验收。
- `ctx.sessionController.prompt({ requestId, sessionId, mode:'queue', content, clientTimeZone }, signal)` → `accepted`（≠完成）；随后 `await ctx.sessions.flush(session)` 持久化。`resolveAgent` 并发恢复共用 Promise（`agent.ts:166`）。
- `ctx.subagents.startContinuable({ provider:'spawn', childId, request:{ parent, prompt, persona, toolFilter, maxDepth } })` 建 continuable child；`sendMessage(parentAgent, childId, content)` 继续；`interrupt(childId, {kind:'user',parentSessionId})` 停止；`drainContinuableDescendants(parents)` 卸载排空。父子关系＝Session header `parentSession`（`packages/core/session/src/types.ts:107-119`）。
- turn 完成监听：`ctx.on('session/event', (session,event)=>…)` 过滤 `turn/end`，用 `event.data.turn` 对齐 assistant 消息（原型 runtime.js `onTurn` 验证可行）。`whenIdle()` 不能当单条消息完成信号（既有研究结论不变）。

## 4. 飞书接入面（P02/P14）

- SDK 长连接 `WSClient + EventDispatcher`：handler 内 `await` 短小耐久写后再 ACK 是官方支持路径（dispatcher 等待 handler，源码核实见[飞书研究](飞书接入与审核机制.md) §2.1）。3 秒预算内只做 PG Inbox 最小写入。
- 原型 FeishuGateway 已验证：`im.message.receive_v1`/`card.action.trigger` 注册、`client.im.message.create` 发送（带 uuid）、`im.messageResource.get` 下载图片、owner open_id 过滤。
- lark-cli 受控执行：固定 argv 数组 + `--json` 信封（`ok`/退出码判定，`partial_success`/warnings 视为需核对），原型 feishu.js `cli()` 验证可行；文档创建 `docs +create --doc-format xml --content -`（stdin）+ 回读 `docs +fetch --detail full` 校验 warnings/revision。
- 正式版差异（新要求）：入站先写 PG Inbox 再 ACK（原型是内存去重，明确不满足生产）；出站走持久 Outbox 保存 message_id 与状态（原型直接发送）；这些是 F01 新增的 PG 业务层，不在 dsh/SDK 现成能力内。

## 5. 测试与隔离验证设计（本轮新增结论）

**主测试形态＝真实 Loader 子进程**，与 dsh 自身 profile 集成测试同构（`packages/test-support/loader-smoke/src/index.ts:213`、`apps/cli/tests/profiles/web/tests/default-web-process.ts`）：

1. 临时 `DSH_HOME` + `dsh plugin add` 安装正式包（走真实 profile/patch/Loader 解析）；
2. `--patch test.patch.yml` 叠加测试层：插入 mock LLM 适配器插件（`ctx.llm.registerAdapter(['pa24-test'], adapter)`，`stream()` 每次从控制文件读脚本，产出 `block-start/text-delta/tool-call-delta/usage/finish` StreamChunk——协议见 `packages/llm/llm/src/types.ts:452-464`，可照抄 `apps/cli/tests/profiles/acp/tests/fixtures/control-surface/control-surface-llm.ts`）；并把 `agent-default-model` 行的 provider/model 覆盖为 `pa24-test/mock`。模型边界即被替换，Agent/工具/会话全部真实。
3. lark-cli 边界＝桩可执行文件（配置指向桩路径）：真实 spawn＋JSON 信封解析保留，飞书侧响应由桩给出（外部网络替换）。
4. 飞书长连接边界＝Transport 接缝：生产实现 SDK WSClient；测试实现由管理端点注入事件（同进程内走真实 Inbox→ACK→派发→Outbox 管道）。
5. 隔离 PostgreSQL＝本机 Homebrew PG `initdb` 临时 cluster（随机端口/socket 目录）＋`pg_ctl start/stop`；真实连接、真实迁移、真实事务。
6. 驱动 Host＝启动 stdout 捕获带 token 的 URL → 换 cookie → 调本插件 `/api/24pa` 管理端点（dsh web 鉴权流已核实：`apps/cli/tests/web-auth.e2e.ts:173-190`；环回 Host + `dsh-auth-*` cookie）。断言以 PG 数据、原生会话事件和端点返回为准，不以模型自述为准。

**单元/组件测试**（vitest，进程内）：配置校验、AGENTS.md 解析、Outbox/Inbox 状态机、PG repository、lark-cli 信封解析。PG 组件测试直接连临时 cluster。

**时钟**：提醒类（F05）用 vi.useFakeTimers 或受控注入；F01 不依赖定时精度。

该设计满足工单验证边界：真实 Loader、原生 Session/Agent、隔离 PG，仅替换模型/外网/时钟。

## 6. 方案取舍

- **不做通用 dsh PG provider**：24PA 业务库独立 schema `pa24` 直连（沿用既有研究结论）；dsh 会话/附件/Schedule 保持原生非 SQLite 持久化，不重写。
- **插件单包**：一个 npm 包 `@benz-ai-x/dsh-24pa`（bundle＋agent 插件＋web client 半部），模块按 src/ 目录划分；不提前拆多包。
- **Host 单实例**：Web Host 无进程级单例锁（仅 Electron 有）；正式版在插件层用状态目录锁文件（O_EXCL＋pid 存活检查）拒绝第二写 Host，满足 P01「第二活跃 Host 被拒绝」。
- **preset 统一**：一个 `pa24` preset；Lead/维护/Worker 权限全部靠宿主核验的入口＋父子关系＋`tools.restrict`（ADR-0001）。
- **TypeScript＋tsc 构建**：正式包用 TS 编译到 `lib/`（区别于原型的无构建 JS）；包 exports 指向 lib，安装/加载流程不变。
