## 05：周期计划的可靠协调

### 已验证的宿主契约

| 操作 | 一手事实 | 对本轮的约束 |
|---|---|---|
| `create(sessionId, request, signal?)` | 每次分配 `schedule-${randomUUID()}`；request 没有调用方指定 ID 或幂等键。生成完整 record 后进入串行队列，持久写入成功才返回。取消只在持久写入前检查，已经开始的写入不会被回滚。 | 不能把抛错/取消当作“肯定没建”；不能用相同参数重试来获得幂等。 |
| `list({sessionId})` | 只返回该会话的 active records。 | 一次性计划若已执行而 inactive，不能用 list 查创建回执。 |
| `catalog()` | 返回所有未删除的 active/inactive records，附 `sessionId`、`status`、可选 `lastDelivery`；保留原 record 的 `prompt`。不激活会话。 | 可按持久的唯一操作标记与会话精确查回，不能只按标题或时间猜测。 |
| `delete({sessionId,id})` | 已删/不存在/不属于该会话返回 `{deleted:false,code:'schedule_not_found'}`；成功返回 `{deleted:true}`。删除表行与投递历史，**已经入队的消息不撤回**。 | 保留 ID，允许幂等清理；业务状态仍须拒绝迟到消息。不能把空历史当作从未投递。 |
| `update({sessionId,id,expected,change?,title?,prompt?})` | 请求字段是 **expected**，不是 previous；需要完整观察到的 ScheduleRecord。只更新 active 计划，同一 ID、原会话与已有投递记录不变。当前 record 与 expected 深比较不一致返回 conflict；存储/生命周期失败会抛错。 | 活跃计划调时优先比较更新，避免 delete→create 的空档和双计划；结果未知仍需恢复。 |

来源：[create/list/catalog](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/index.ts#L228)、[delete/update](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/index.ts#L314)、[请求与结果类型](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/types.ts#L369)、[expected 比较及更新结果](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/update.ts#L152)。

补充两个会影响正确性的细节：

1. `catalog()` 不进入 create/delete/update 使用的串行队列。旧 create 还在写时的一次空 catalog，不能证明旧操作没有发生。未知态且零匹配时不可立刻重建。宿主整体重启后旧调用不再运行，但“以前创建后已被人删除”也与“从未创建”无法仅靠 catalog 区分。[catalog 实现](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/index.ts#L285)
2. `catalog()` 的元素比 `ScheduleRecord` 多 `sessionId/status/lastDelivery`；作为 `update.expected` 前须取得或还原严格的 record，不能把整个 catalog 元素直接送入。宿主 `decodeScheduleRecord` 对各类 record 使用精确字段校验；`expected` 无效会返回 `invalid_rule`。[record 校验](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/domain.ts#L548)、[expected 校验](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/update.ts#L159)

### 现有缺口与最小方案

当前 create→insert、delete→update 的顺序存在于 [DigestService](../../packages/24pa/src/digest-service.ts) 的 enable/control/supervise，以及 [runtime](../../packages/24pa/src/runtime.ts) 的会前准备与关联日程清理。内存故障探针已确认：create 成功而 insertPlan 失败留下无账本原生计划；delete 失败仍清空 `schedule_id`，第二次 pause 已不能再尝试删除。

建议由一个周期计划 module 持有以下完整过程；不把这些顺序规则继续分散给调用方，也不往现有交付事务内塞宿主调用。

1. **先存意图。** 在本地事务记录计划 ID、固定 sessionId、用户目标状态、完整规范化配置、操作 ID/代次、原有 Schedule ID、尚待清理的 ID 和阶段。新计划在原生创建前就能恢复；同一计划只允许一个未完成的配置操作。面板发起不一定有 WorkItem，不应伪造事项来借用 `action_operation.work_item_id not null`。可用计划专属持久意图或计划附属记录；最终表形由实施统一决定。[现有 action_operation 约束](../../packages/24pa/src/db.ts)
2. **固定创建身份。** 将无秘密的唯一意图标记作为完整 prompt 的一部分保存；marker 由工作区/计划/操作代次确定，用户可见标题不是身份。入调用前先记录 creating/unknown 的可恢复阶段，再调用原生 create。收到 record 立即保存原生 ID 与 record，最后提交计划 active 和完成意图；后续本地失败只补账。
3. **创建未知先查回。** 精确匹配 `sessionId + 持久 marker/完整 prompt`：一条匹配则恢复其 ID，包括已经 inactive 的一次性记录；零匹配保留 unknown 并给出可操作状态，不盲重 create；多条匹配保留所有 ID 并报告歧义，不任意选一条继续。新鲜 pending、尚未进入宿主调用的意图才可首次调用 create。caller 能证明原调用仍在运行时，应等待同一 promise，不能并发恢复。此方案保证不盲目重复，但不承诺在宿主缺少幂等键时自动消除所有未知结果。
4. **暂停/停止先落业务目标状态。** 本地先使计划不可继续生成/交付，再按保存的 ID 清理原生计划。delete 成功或确证 not_found 才移除待清理 ID；失败保留 ID、错误与待重试状态。即使计划已 paused/stopped，清理仍会被重启恢复读取；不能只扫描 active。已入队消息依旧由既有计划状态核验拒绝。
5. **活跃计划调整用宿主比较更新。** 保存 desired 配置和新的意图 marker，读取当前 record，把新的 marker 与 timing 放进同一个 update；检查返回 union，而不是只看 promise 是否 resolve。`schedule_conflict` 保留冲突，不自动覆盖宿主界面的新改动；`schedule_ended/not_found` 不擅自当成成功或重建。成功后提交本地配置。结果未知时按 ID/marker 与目标规则查回；scheduledAt 可能因实际投递而推进，不能仅因其变了就认定操作没应用。
6. **恢复/重新开启是新的明确意图。** 先收敛上一代待清理 ID，再创建新代次。`after_seconds` 在意图接受时固定成绝对 `at`，重启不能从恢复时间重新计时；已过期的一次性目标如实结束/要求重设，不自动延后。历史生效的 window/occurrence 仍不改写。
7. **装载后恢复再受理新的变更。** 工作区资源就绪后恢复未完成意图；每计划串行与数据库条件更新防止两次请求同时操作。运行中切换工作区须沿用本轮工作区归属方案，不能在远端返回后通过动态 `this.repos` 写入新工作区。无需扩展为分布式调度系统；本轮首先保障当前单宿主运行模型。

原生 `update` 的成功 union 是 `{id,updated,record}`；`updated:false` 且带 record 可以是合法 no-op，不能等同失败。内容改动本身不重置 committed target，等价 timing 也保持它；实际 timing 改动重新计算目标，但保留 ID。[更新规则](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/update.ts#L88)

当前本地 `NativeScheduleService` 只声明 create/delete/history。实施时应按已验证的公开类型补充 catalog/update 及结果判别，检查宿主能力；缺能力须明确不可执行恢复，不得伪造 catalog 结果或回退盲重建。[本地 interface](../../packages/24pa/src/host.ts)

## 06：任务 skill 的一次定义观察与持久选择

### 已验证的宿主契约

- `list()` 是调用中立的目录摘要；`toSummary` 明确不带 metadata/content。`snapshot()` 的 complete 表示目录发现完成且目录 revision 稳定，**不是正文和 metadata 的执行快照**。[list/snapshot](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/skill/skill/src/index.ts#L462)、[摘要字段](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/skill/skill/src/index.ts#L769)
- `get(name,{cwd,signal,scope?})` 从当前获胜 candidate 装载一次完整 definition，校验必需字段和名称一致性后返回；返回 undefined 或抛错都不是可执行正文。它并未承诺跨多次 get 的内容不变，也不冻结返回内容。[get 实现](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/skill/skill/src/index.ts#L500)
- 文件 provider 的一次 get 只 parse 一次文件，然后从这次 parse 一起返回 content、metadata、invocation；source 来自选中的 candidate。可以把**同一返回值的副本**作为24私助这次执行的事实。[文件 provider.get](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/skill/skill-filesystem/src/index.ts#L209)
- 来源和优先级由宿主决定；工作区 `.dsh/skills` rank=100，全局用户目录是不同 source。24私助执行面仍需限制自身支持的来源，不能把名字以 `digest-` 开头当作内置身份。[来源定义](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/skill/skill-filesystem/src/index.ts#L35)、[工作区/用户根](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/skill/skill-filesystem/src/index.ts#L249)

### 实施落点

当前 [SkillCatalog](../../packages/24pa/src/skills.ts) 先 list/find 判轨，再 get 正文，再 get metadata；list 富化失败回落 summary，使缺失 track 被误认为 agent。故障探针已确认：第一次 get 失败、后续两次返回模板定义时，`resolveForAgentRun` 成功返回模板正文。修复应移除这种“分次读取再拼事实”，不是仅补一个分支。

建议规则如下：

1. 执行解析直接进行**一次完整 get**；从同一返回值取得 name/source/track/content/tools/params/kind。只有成功载入完整 definition 后，才对未声明 track 使用既定缺省 agent。读取失败或 undefined 明确拒绝；registry 存在但读取失败时不偷偷回落内置，避免覆盖工作区定义的加载故障。完全未挂 registry 的既有场景才使用已知内置定义。
2. 目录展示可以单独观察摘要与加载状态，但摘要不能为执行发许可证。周期服务的模板/agent 分派和通用 skill_run 复用同一个执行解析判断；模板种类必须有对应确定性实现，不能把任意 `kind` 默默交给默认晨报/复盘渲染。
3. 委派的选择必须成为 **WorkItem 的持久输入**。在准入事务保存明确的 skill 名；不要只校验 `args.skill` 然后丢弃，也不要藏进会被投影覆盖的 `result_ref`。历史 skill 事项没有选择时明确要求重新委派，不从自由文本猜名字。[目前委派与启动](../../packages/24pa/src/runtime.ts)、[WorkItem 记录](../../packages/24pa/src/repo/work.ts)
4. 为防止排队/重启时换了执行轨，可在首次准入或首次执行前将已校验的完整定义快照与 WorkItem 一起持久保存，再开始模型回合；保存 name、来源、track、正文与工具声明即可，摘要/哈希用于追溯。继续同一事项使用该次快照；下一次新委托读取新定义。**至少必须持久选择，是否在准入还是首次执行固定正文须在实施中统一，不能有两个入口各自决定。**
5. 持久快照不冻结授权：每次开始/继续仍校验当前 enabledWorkers、extraBusinessSkills 和当前角色工具面；撤销授权后拒绝继续。工具声明仍只能收紧既有工具集合，不能因旧快照或 persona 获得更多工具。归属与权限沿用 ADR-0001。
6. 真实工具 schema 必须能承载执行所需字段。当前 `pa24_work` 使用 `additionalProperties:false`，缺少 skill_run 的 `skill` 和 digest_deliver 的 `report`；探针真实执行 `tools.apply` 后确认。这一修复与本轮动作契约单源项协作完成，避免只在直接调用 runtime 的测试里传入 schema 不允许的字段。[工具声明](../../packages/24pa/src/tools.ts)

`SkillRegistryLike` 已是生产宿主与可变测试 registry 之间的真实 seam，不需另建通用插件框架。module 的 depth 来自把同次定义、执行轨与选择身份藏在内部；不是新增更多 find/content/meta 调用方法。

## 07：IANA 本地日与时间块占用

### 可复用能力和不可复用的假设

宿主 Schedule 使用 Temporal 0.5.1 解析显式 IANA 时区：local at 要求真实 ISO 日期、严格时钟；夏令时缺失时刻拒绝，重复时刻取较早那个 instant。每日递推按本地日期加一天，不是固定加 24 小时。[时区/本地时刻解析](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/domain.ts#L367)、[本地日期递推](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/domain.ts#L826)

但公开根导出只提供 `createAtScheduleRecord`、`createDailyScheduleRecord`、`resolveDailyOccurrence` 等 Schedule 纯函数；**不导出** `parseAtInput`、`canonicalizeTimeZone`、`localDate`。`createAtScheduleRecord` 强制目标在 now 之后，不能假装通用“任意本地日→instant”转换。不要导入宿主 `lib/types/domain.js` 私有路径，也不要传假 now 绕过约束。[公开导出](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/index.ts#L47)、[createAt/parseAt](https://github.com/deepseek-ai/deepseek-harness/blob/1600d8a1e140dcde43a1a0941940a0480712c011/packages/schedule/schedule/src/domain.ts#L1294)

本地现有 `util.parseZonedRange` 只是解析已经带时区的 from/to 并限制查询长度，没有提供 IANA 本地日期转换。因此不能只因函数名含 Zoned 就把它用于本地日计算。[现有工具](../../packages/24pa/src/util.ts)

建议规划 module 显式使用 `@js-temporal/polyfill@0.5.1`，作为自身直接生产依赖而不是依赖宿主传递安装的偶然可达性；复用宿主已经使用的库与时区语义，避免再造易错的 Intl 偏移猜测算法。若不添加依赖，则应先落实等价、充分验证的转换方案，不能用 UTC 字符串拼接作为替代。

### 最小时间语义

1. 用工作区 timeZone 从 now 取得本地 date。指定 `YYYY-MM-DD` 表示这个时区的日；绝对 instant 先转这个时区再选日期。无效日期明确拒绝，不用 JavaScript Date 的自动纠正作为校验。
2. 每一天使用 `[本地日开始, 下一本地日开始)`；下一日通过日历加一天，不能按毫秒加 24 小时。全天事件按与该区间交集计入，容量计算裁剪到实际范围；不把昨天或明天全部日程都算作今日忙碌。
3. 09:00 候选是在工作区本地日上构造当地 09:00；不是 UTC 午夜加九小时。显式本地候选时刻沿用宿主“gap 拒绝、overlap 取较早”的选择；一天起点应使用 Temporal 的该日期开始语义，覆盖午夜发生偏移变化的时区。
4. 采纳前先验证整批 start/end，并同步覆盖所有选块的范围；不能仅按第一块的 UTC 日期同步。保持现有渠道范围上限，需要时按日拆查询。先建立已有日程的占用集合，成功采纳一个块后立刻加入集合，后续块检查同批冲突；写失败不算占用。重试仍使用现有渠道操作幂等性。
5. 预览与采纳共享时间判断；外部写入仍由现有 calendar adapter 负责，规划 module 不复制外部操作阶段或远端回执处理。

### 无副作用验证结果

此次实际导入安装包公开根并调用纯 record builder；同时用 Schedule 依赖的 Temporal 读取下列日期。未调用 ScheduleService 实例。
