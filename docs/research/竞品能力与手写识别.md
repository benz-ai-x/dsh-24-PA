# 24PA：竞品能力与手写笔记识别研究

研究日期：2026-10-05（Asia/Shanghai）。范围：能力与技术方案，不包含实现、安装、个人数据读取或实际模型测试。已知输入以中文手写为主，混有英文、待办和简单图示；用户已有运行 dsh 的服务器。

本文把官方资料支持的事实、为 24PA 提出的设计建议、必须在开发阶段验证的假设分开。产品宣传不代表识别准确率或稳定性承诺。

## 1. 结论与建议

1. **主线应是“收到笔记 → 有证据的整理稿 → 提醒审核 → 用户审核特定版本 → 可追踪地归档/生成行动”。** 手写识别成功只是中间步骤；审核状态可信、错误易发现，才是核心产品价值。
2. **第一条评测路线优先复用 dsh 已有 DeepSeek 图像能力。** 当前官方 API 已支持图像输入，本地 dsh 也有对应图像模型路由。无需为了“视觉”先新增一整套模型基础设施。
3. **保留可替换的识别适配器。** 视觉模型负责转写和理解；云 OCR 或本地 OCR 可以补充文字框定位、逐字结果和疑难区复核。供应商选择应以用户真实样本评测决定。
4. **识别审核与执行许可分开。** 文档人工审核通过表示该版本内容经过审核，不能自动推导为允许向同事发消息、预约会议或执行所有提取出的任务。
5. **主动服务借鉴竞品的日程预览、到期风险和上下文简报。** 第一版以飞书已授权数据、用户提交内容和确定性到期条件为触发依据，优先提供会议提醒、待办提醒、审核待办和每日简报。

24PA 的差异点建议是：**飞书中的个人工作闭环 + 中文手写证据与人工审核**。无需第一版复制完整项目管理平台、跨团队会议优化器或企业知识库。

## 3. DeepSeek 与本地 dsh 的视觉能力核验

**官方事实（2026-10-05 核验）：** DeepSeek 的 Vision 指南明确 `deepseek-flash` 接收文字和图片，支持 JPEG、PNG、GIF、WebP，以及 base64、图片 URL、Files 引用。Anthropic 兼容接口也支持图像内容块。官方 2026-09-10 更新说明最新 Flash 原生支持多模态，旧视觉实验模型名已作为兼容别名路由到新模型。[Vision 指南](https://api-docs.deepseek.com/guides/vision/)、[发布更新](https://api-docs.deepseek.com/updates/)

**本地源码事实：** `packages/llm/llm-deepseek/src/models.ts` 中默认 `deepseek-flash` 声明 `inputModalities: ['text', 'image']`。README 描述图像归一化、请求像素预算、Files 上传与 inline 回退；文本路由只收到附件占位内容。[默认模型目录](/Users/pc2026/DSH-Space/deepseek-harness/packages/llm/llm-deepseek/src/models.ts:8)、[图像传输说明](/Users/pc2026/DSH-Space/deepseek-harness/packages/llm/llm-deepseek/README.md:94)

**对 24PA 的设计含义：** 接入必须确认实际选中的路由具有图像能力，不能只检查模型名称。将视觉任务走 dsh 的模型与附件服务，记录模型标识、路由、提示模板版本和处理版本。服务器实际启用的 profile、版本与权限尚未核验。

**关键实现约束：** dsh 当前默认会为请求缩放/重编码图像。这有利于控制体积，但密集中文手写的小字可能在缩放后失去笔画。应保留原文件，先整页理解版面，再针对小字或疑问区域提供裁片；避免假设“上传了高清原图”就等于“模型看到了全部原始分辨率”。这属于需要样本验证的工程判断，不是已测出的质量结论。[dsh 图像预算与归一化](/Users/pc2026/DSH-Space/deepseek-harness/packages/llm/llm-deepseek/README.md:94)

本次核验使用官网索引正文与本地源码交叉检查；Vision 页直接抓取曾超时。未使用用户密钥发送图像请求，因此没有真实识别质量、延迟或价格测量。

## 4. 三条识别实现路线

| 路线 | 处理过程 | 优点 | 代价与待验证问题 | 建议用途 |
| --- | --- | --- | --- | --- |
| A. dsh 视觉模型直接识别 | 图像质检 → 整页/裁片输入视觉路由 → 结构化转写 → 摘要/候选行动 → 人审 | 最少新增服务；可以理解简单图示、箭头和文字上下文 | 潦草字、人名和数字仍可能错；模型生成的框坐标不保证准确；需防止摘要补写原稿没有的内容 | 首个基线；优先复用已部署 dsh 的图像能力 |
| B. 专业 OCR + 视觉/语言整理 | OCR 产出文字、定位和分数 → 按疑问区给视觉复核 → 结构化整理 → 人审 | 更适合把文字定位到图像；容易做逐行比对和疑难区复核 | 新增服务和调用费；两个模型可能犯同类错误；图示关系仍需视觉；数据传给新增供应商 | A 的证据定位或疑难字表现不足时引入；也可在选定高风险片段按需调用 |
| C. 服务器本地 OCR + 可选云视觉 | 本地 OCR → 本地结构化预处理 → 必要时发送允许的裁片到视觉 → 人审 | 原图可留本地；批量处理的资源和数据流更可控 | 需要模型部署、CPU/GPU和运维；本地并不自动等于更准；若仍用云视觉，不能宣称全流程离线 | 有明确本地处理偏好或较大处理量后评估 |

### 可选适配器的官方依据

- **阿里云手写 OCR：** `RecognizeHandwriting` 声明支持中文、英文、数字手写；接口可返回文字块位置、单字信息与分数，图片需要符合其格式/尺寸限制且不直接接收 PDF。其旋转输出坐标针对校正后的图像，必须保留坐标变换才能准确回到原图。这里只把官方能力作为候选依据，不将页面的总体准确率宣传转成 24PA 承诺。[官方接口](https://help.aliyun.com/zh/ocr/developer-reference/api-ocr-api-2021-07-07-recognizehandwriting)
- **其他云 OCR：** Azure Read 提供词的边界多边形、分数与手写样式信息；Google Enterprise Document OCR 提供质量检测、文字布局和手写相关输出。中文手写的具体版本、区域与混写表现要单独评测。[Azure Read](https://learn.microsoft.com/zh-cn/azure/ai-services/document-intelligence/prebuilt/read?view=doc-intel-4.0.0)、[Google OCR](https://docs.cloud.google.com/document-ai/docs/enterprise-document-ocr)
- **本地 OCR：** PaddleOCR 官方 PP-OCRv5 文档覆盖简繁中文、英文及复杂中英手写场景；它可以作为本地基线，官方内部评测不能代替个人手写样本验收。[官方模型说明](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/algorithm/PP-OCRv5/PP-OCRv5.md)
- **避免按旧接口名锁供应商：** 腾讯 `GeneralHandwritingOCR` 当前文档已经标为旧服务，并推荐其高精度文字识别路线。开发时应重新核实接口生命周期与可用性。[腾讯官方旧版提示](https://cloud.tencent.com/document/api/866/36212)

**推荐决策：** 开发获准后先用 A 建立质量基线，同时统一识别结果格式；如果定位、数字或潦草字明显影响审核效率，再在同一套样本上比较 B。C 保留为后续选择。无论选择哪条路线，第一版的人工审核都不省略。

## 5. 手写输入到整理稿的完整流程建议

### 5.1 收集与原件

1. 同一消息的多张图片组成一份笔记；跨消息的多页上传提供明确的“收集这组笔记/发完了”边界。超时可提示补充，不静默猜测还有没有下一页。
2. 为每份笔记、每页、每个原始附件保存稳定标识、内容哈希、原始消息与接收时间。原稿书写时间单独记录，不与接收时间混为一谈。
3. 以附件次序作为默认页序；OCR 发现页码矛盾或重复页时提出疑问。允许人工调序；不要因为模型推测语义连贯就永久重排原图。
4. 检查模糊、反光、边缘被截断、旋转和过小文字；无法辨认时生成“需补拍”项。保留原图，旋转/裁切版本均可追溯到原图。
5. 对多个附件重发与断点恢复去重，但让用户能明确选择“这是更新版”。不要把相同照片里的第二份不同笔记误删。

### 5.2 识别结果分三层

| 层 | 内容 | 规则 |
| --- | --- | --- |
| 原样转写 | 按页、段、行保留原文；包含划掉、勾选、箭头和不确定字符 | 不把错别字悄悄改成推断值；无法识别写 `[无法辨认]` 或候选词 |
| 整理稿 | 标题、主题、结构化段落、摘要、决定、图示说明 | 可以重组表达；必须区分原稿事实和模型归纳，每项关联来源 |
| 候选行动 | 待办、日程建议、备忘条目 | 独立保存负责人/日期等未知字段；等待用户选择是否写入任务或日历 |

用一个大模型请求同时“转写、推理、排程、创建任务”，容易把识别猜测变成外部动作。建议在结构上分开识别与执行；允许同一供应商承担多个阶段，但阶段之间有可验证的数据边界。

### 5.3 中文夹英文与特殊信息

| 内容 | 建议处理 |
| --- | --- |
| 人名、项目名、英文缩写 | 原字符优先；个人词表给候选，不强行替换；“王/汪”“API/AP1”等歧义突出显示 |
| 相对日期 | 保留“下周二”等原文；只有笔记日期明确时才计算候选日期，同时显示基准日期和 Asia/Shanghai；基准缺失列为待确认 |
| 时间和金额 | “1/7”“0/O”“300/3000”等逐项核对；金额单位、币种和小数位缺失时保持缺失；不得把识别分数当付款或排期许可 |
| 待办框、划掉、圈重点 | 保存选中/未选中/划掉/不明等状态；划掉可能是取消或完成，不一律等同完成 |
| 简单流程图、框箭图 | 保留图像裁片；提取节点文字、箭头方向与关系的文字说明；模糊关系标记不确定，不先追求自动重绘成“完美”图 |
| 手写表格 | 保留单元格关系；空白不补零；跨行、合并格、涂改格与总计分别标记 |
| 多页延续 | 标记“续上一页”及证据；对页面缺失和语句未完提出问题，不编写缺页内容 |

### 5.4 统一证据模型

建议每个识别/整理单元包含：`note_id`、`page_id`、`block_id`、`source_asset_hash`、原始文字、整理文字、来源引用、疑问项、模型/模板版本。

定位信息分级：

- **确定区域：** OCR 或预处理产生的框，连同原始图、处理图和变换矩阵记录。
- **近似区域：** 视觉模型指出的候选框，只能标记为近似；超出图像范围或无效框直接降级。
- **页级来源：** 没有可靠定位时，仍必须保留页号与原图；第一版可以采用“页级引用 + 系统生成的疑问裁片”，不把模型坐标当精确定位。

`provider_score` 原样保存，`review_reasons` 记录“人名歧义/日期缺基准/双路结果不同/图像质量差”等可解释原因。不要把 VLM 自报 0.98 写成“98% 正确”；不同供应商分数也不直接比较。界面优先显示需要人处理的理由。

## 6. 人工审核闭环建议

### 文档应呈现的内容

文档开头固定展示：`AI 整理稿 · 待人工审核`、笔记标识、当前版本、原图页数、待确认项数量。正文包含整理稿、候选行动、疑问清单；附录保留原样转写和原图/页级引用。已审核后显示审核人、时间和被审核版本。

提醒示例：

> 你的 3 页笔记已整理成《项目讨论笔记》。当前为待审核，有 2 处需要确认：第 1 页的人名、第 3 页的截止日期。打开文档后可“审核通过”“退回修改”或“稍后提醒”。

文档内容审核通过后，再给单独行动确认：

> 本笔记可转为 2 条任务和 1 个日程。下面是标题、负责人和时间；请选择需要创建的条目。

### 审核状态的语义

| 状态 | 含义 |
| --- | --- |
| 待审核 | AI 完成整理，但该版本尚未由用户确认 |
| 修改中 | 用户退回或正在修订；旧审核链接不得审批新版本 |
| 已审核 | 指定用户明确确认指定正文版本 |
| 已变更待复核 | 上次审核后正文或来源发生变化；旧审核记录仍保存，但不代表当前版本 |
| 处理失败/需补充 | 上传、识别或写入未完成；保留材料，明确下一步 |

**审批必须绑定版本。** 审核请求保存正文快照/规范化正文哈希、来源哈希、审核目标用户、文档标识、到期/单次使用标记。正文哈希排除机器人管理的状态栏，避免自己写状态触发无穷变更。

**用户在飞书里编辑正文的情况要明确处理：** 审核动作触发时重新读取最新内容；若与审核请求快照不同，展示最新内容并形成新审核请求。系统对已通过文档检测到新编辑后，切换为“已变更待复核”。如果没有可靠编辑事件，使用定期校验及每次引用/执行前校验。飞书事件、版本和读写能力由集成研究进一步核验。

**状态栏是展示，持久审核记录才是依据。** 不能因为有人把标题改成“已审核”，就把它当作通过。也不能依赖模型判断“这看起来像我同意了”。自然语言确认至少要准确指向同一笔记版本；存在多份待审核文档时给明确选项。

**写入与通知可重试。** 只有飞书文档建立成功并可访问后才发送审核提醒。审核记录保存成功但状态栏更新失败时，记录待同步并重试；正文、状态栏和卡片不一致时不得输出“全部完成”。重复回调、按钮双击、超时重试只能产生一次审批或一次对应外部动作。

## 7. 主动提醒的产品原则建议

- 触发类别分为明确时间点（会议前、任务截止前）、状态变化（整理完成/审核退回/日期改变）和汇总窗口（每日简报、每周回顾）。不需要让大模型永久循环空想下一条提醒。
- 单独区分“通知已发送”“用户已看见”“用户已处理”。未回复不能当作同意、完成或已审核。
- 提醒引用当前版本；会议取消、任务完成、笔记删除或审核通过后，取消相应未来提醒。
- 会前提醒提供时间、地点/链接、需要准备的内容；会前资料只引用有明确来源和审核状态的笔记。
- 支持“稍后提醒、今天不再提醒、完成、暂停这类提醒”；安静时段、重要事项例外、频率上限由用户配置。
- 普通提醒合并，明确的重要截止时间独立通知。服务恢复后按有效期补发或放入汇总，避免一次性轰炸历史提醒。
- 第一版以提醒本人为主。“催同事、发群消息、邀参会人”是独立外部动作，需要来自用户的明确指令或已设规则。

这些是 24PA 的设计建议，不是飞书消息必达、移动端必响或 24 小时无故障的承诺。实际可达性依赖服务器、连接、授权和平台消息能力。

## 8. 评测与预算：开发后再决定供应商

### 样本与对照

先由用户提供允许处理的代表性笔记并确定供应商数据流。建议首轮约 30–50 页，覆盖清楚/潦草、中文夹英文、人名、日期、数字、待办框、简单图示、低照度、倾斜、多页和涂改。样本数量是评测建议，不是统计代表性的保证。

每页由人工建立对照内容；调参样本和保留验证样本分开。用同一套原图、页序和人工标注比较路线，不能只用“最漂亮的几页”演示。

| 维度 | 记录指标 | 目的 |
| --- | --- | --- |
| 转写 | 字符错误率、遗漏行/重复行、英文词和数字错误 | 区分文字识别问题与摘要问题 |
| 关键字段 | 人名、日期、时间、金额、待办状态的正确/错误/主动留空情况 | 衡量错误是否会变成错误行动 |
| 结构 | 页序、段落、表格、图示关系是否保真 | 防止文字都对但关系错 |
| 不确定性 | 被标为需确认的实际错误占比、未标出的关键错误 | 判断审核提示能否真的帮用户省事 |
| 人审 | 每页审核时间、修订次数、直接通过比例 | 以用户时间而非营销准确率选方案 |
| 工程 | 成功率、P50/P95 延迟、单页/单批费用、失败恢复 | 支撑可接受的体验和容量 |
| 闭环 | 重复事件、旧卡片、正文修改、重启后是否误批/重建 | 确保审核和任务不会串版本或重复执行 |

候选发布门槛应由样本基线后设定。确定性门槛可先约定：未审核稿不能标已审核；审批不得跨版本；原始证据不能丢；旧卡片不能创建新版本行动；存在关键字段未确认的条目不得自动写入日程。不得宣称一次小样本验收能保证未来识别零错误。

### 预算公式

不锁定当前套餐或给未经实测的人民币总价。先按下式估算：

`月成本 = Σ(每次请求输入 token × 对应单价 + 输出 token × 对应单价) + OCR 实际调用数 × 调用单价 + 附件存储/流量 + 本地计算与运维`

其中请求次数包含整页识别、裁片复核、整理、人审后重跑；图像 token 由实际传给模型的尺寸和供应商规则计算，最终以用量记录为准。以“月页数、每页平均裁片数、复核比例、重试率、保留期限”作为可调变量。给每日/每批费用上限、最大页数、最大重试和超限提示；不在超限后静默跳过页面。

DeepSeek 价格与模型别名会调整，部署时应读取当期官方定价并保留配置快照；本笔记不把查询当天的费率固化为长期预算。[DeepSeek 官方定价](https://api-docs.deepseek.com/quick_start/pricing/)

## 9. 尚待实测或集成核验的事项

1. 用户常见字迹在 dsh 默认图像预算下的质量；整页与局部裁片的收益；每批合理页数。
2. 专有名词词表能否减少修订，以及它是否会把不确定字强行改错。
3. 真实服务器上的模型 profile、附件路径可见性、访问外部 OCR 的条件、调用费用与保留策略。
4. 飞书对附件下载、文档原图插入、审核卡片回调、正文变更检测和权限归属的具体支持。
5. 开发首期是否需要 OCR 精确文字框，还是页级引用已经足够降低审核时间。
6. 图示自动重绘是否真的有价值；默认先保留原图加关系说明，避免增加额外误差。

在完成这些验证前，推荐的承诺是“有证据、可修正、明确等待本人审核”，不是“完全准确、自动理解并执行一切”。
