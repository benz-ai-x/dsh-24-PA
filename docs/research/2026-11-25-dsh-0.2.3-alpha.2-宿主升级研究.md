# dsh 宿主升级研究：0.2.2-rc.3 → 0.2.2-rc.5 / 0.2.3-alpha.2

2026-11-25，实施前研究。插件基线：`0.2.2-rc.3.1`（提交 `144b9a9`，`engines.dsh`＝`0.2.2-rc.3`），上一轮记录见 [rc.3 适配核验](dsh-0.2.2-rc.3-适配核验.md)。

证据边界：本文只读宿主与插件源码、官方升级指南和 npm 清单，没有启动任何版本的宿主，没有安装、提交或发布。标为「破坏」的结论来自读码，实施时须先用真实宿主复现。宿主路径与行号对应标签 `dsh-v0.2.3-alpha.2`（本机 `~/DSH-Space/deepseek-harness`），插件路径对应上述提交。

## 结论

1. `0.2.2-rc.3.1` 在 rc.4、rc.5 和 0.2.3-alpha 线上都装不上。`engines.dsh` 是精确版本，不兼容的 bundle 在启动时被整包跳过，安装被拒绝。
2. `0.2.2-rc.5`（npm `latest`）是纯元数据升级。标准预设与 rc.3 逐字节相同，Node、Cordis、Schemastery 门槛不变，24私助没有需要改代码的消费面。
3. `0.2.3-alpha.2`（npm `alpha`）有一处必改。进程内子代理的首条任务消息由 `user` 来源改为 `agent-message` 中继，24私助的起始输入识别只接受 `user`，新交办和业务 Skill 运行会在首个步骤被拒并落入 `needs_reconciliation`。其余是 Node 门槛、vendor 版本和标准预设新增一行。
4. 宿主新增的飞书／企微插件管的是 CLI 供给、账号授权和给模型的技能索引。宿主没有入站 IM 通道，也没有账本化的业务工具；24私助的飞书长连接、微信入口、业务工具和联合备份没有宿主对应物，继续自持。可复用的是 CLI 供给、授权操作、技能索引和 `ctx.subprocess`。
5. 不要用 `dsh plugin allow-version` 把 `0.2.2-rc.3.1` 豁免到 alpha.2 上运行。插件能装载，但第 3 条的拒绝照常发生。

### 必改项的机理

rc.5 及之前的宿主把子代理的首条任务记为 `user` 来源；alpha.1 起改为 `agent-message` 中继，并在内容前加一个 `Agent lead sent a message: ` 文本块：

```ts
// rc.3 / rc.5: manager.ts:409-411
? withResultDeliveryGuidance(spec.prompt) : spec.prompt,
{ source: { kind: 'user' }, ... }
// alpha.1 / alpha.2: manager.ts:406-412
const task = createAgentMessage(parent, agentAddress(...), spec.prompt)
? withResultDeliveryGuidance([...task.content]) : [...task.content],
{ source: task.source, ... }
// continuation-messages.ts:70-75
content: [{ type: 'text', text: `Agent ${senderName} sent a message: ` }, ...content],
source: { kind: 'agent-message', form: 'relay', senderSessionId: sender.id }
```

24私助三处只认 `user`：

| 位置 | 作用 | alpha.2 上的后果 |
|---|---|---|
| `packages/24pa/src/worker-runs.ts:95`、`:119` | 输入日志与 `agent/pre-step` 钩子认领起始输入 | 认领失败，事项写为 `needs_reconciliation`，步骤被拒 |
| `packages/24pa/src/work-completion.ts:79-80` | 完成判定核对起始输入 | 停在 `pending` |
| `packages/24pa/src/skill-run-host.ts:86-91` | 业务 Skill 的 `ownsInput` | 取消与恢复排除起始输入 |

标记块匹配用的是 `.some`，多出的前导块不影响。其余 `kind === 'user'` 判断针对的是24私助自己经 `sessionController.prompt` 发出的消息（带 `rpcId`），不受影响。

修法：起始输入接受「`agent-message` 且 `senderSessionId` 等于父会话」，同时保留 `user` 以读取升级前写入的会话。三处收拢为一个判定函数。宿主侧连带变化：子代理的首条任务不再展开 `$skill` 与会话引用，也不再生成兜底标题；24私助自行载入 Skill 正文并调用 `rename`，需在测试里确认。

连接器边界（`packages/connector/README.md`、`feishu/README.md`、`wecom/README.md`、`cli-account/README.md`）：

- 只在 0.2.3-alpha 线，走插件市场，不在出厂组合里。宿主 README 写「仅支持 macOS 和 Windows x64，其他平台未经验证」；`@larksuite/cli` 的 npm 清单声明 `linux`，`@wecom/cli` 有 `linux-x64` 与 `linux-arm64` 平台包。
- `ctx.cliAccounts` 只有 `register`，没有按名查询。24私助读不到宿主注册的可执行文件路径，同名二次注册会抛错。
- 连接器的命令不带 `--profile`，跟随 lark-cli 当前生效的配置，且与用户自己的终端共用。24私助固定 `larkProfile`（缺省 `default`）。`lark-cli profile use` 切换后两者不再是同一份配置。
- 连接器的命令执行器上限是 1 MiB stdout，`control.run` 不提供 stdin 入参；24私助网关是 16 MiB 并支持 stdin（`docs +create --content -`）。数据面调用不能改走连接器的执行器。
- 本机 `lark-cli` 是 1.0.99，高于连接器固定的 1.0.97。两者共用同一份磁盘配置与凭据时存在版本偏斜。
