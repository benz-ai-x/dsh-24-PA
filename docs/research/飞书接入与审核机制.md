# 24PA 飞书接入与手写笔记审核机制调研

调研日期：2026-10-05（Asia/Shanghai）。范围：方案研究，未读取账号业务数据，未创建应用、授权、发送消息、修改飞书内容或开发插件代码。依据为飞书官方公开文档、官方 CLI 源码、本机 `lark-cli 1.0.87` 静态帮助及配套 skill。服务器运行 dsh；首版只面向绑定的个人飞书账户；笔记以中文为主，含英文、待办和简单图示。

## 1. 关键结论

1. **事实：应用机器人可以通过长连接接收消息和新版卡片回调，主动私聊可以使用发送消息 API。** 不需要部署公网入站 Webhook。长连接回调仅支持企业自建应用；群自定义 Webhook 机器人不适合作为 24PA 的完整接入方式。[长连接回调](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/step-1-choose-a-subscription-mode/configure-callback-request-address.md)、[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)
2. **事实：CLI 已有用户/机器人双身份和文档、日程、任务、消息能力。建议：业务读写优先 CLI，服务器消息入口采用一个官方 Node SDK 长连接，由确定性的控制器处理审核。** 当前 CLI 事件目录没有日历、Drive 文件编辑事件，不能仅依赖 `event consume` 覆盖全部需求。[本地身份规则](/Users/pc2026/.agents/skills/lark-shared/SKILL.md:48)、[CLI 事件目录规则](/Users/pc2026/.agents/skills/lark-event/SKILL.md:61)
3. **事实：飞书文档有 revision，更新有幂等标识；本次未找到“仅当当前版本等于 expected_revision 才写入”的强 CAS 契约。** 必须把“某个确定内容版本经人工审核”与“当前可编辑文档是否仍等于该版本”分开。以文档顶部一句永久的“已人工审核”作为唯一状态会误导。[块批量更新](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document-block/batch_update.md)
4. **建议：审核通过绑定不可变内容快照、内容哈希、审核者和时间。** 飞书文档展示版本限定的审核记录；编辑后新内容重新进入待审核。可编辑文档上的状态只是投影，24PA 的受控审核记录才是判断依据。通知和任务生成不得从未审核笔记直接执行。
5. **事实：日程支持增量同步，但时间区间查询存在截断限制，部分事件细节仍处于灰度。** 需要持久化同步游标、定期补偿读取和发送前复查，而非收到一个变更事件就假定拥有全部最新日程。[日程列表](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/list.md)、[日程变更](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/events/changed.md)

## 2. 机器人入口、身份与服务器运行

### 2.1 入站链路

**已证实：**

- `card.action.trigger` 是新版卡片回传。官方长连接文档提供 Node/Go/Python/Java 示例；长连接内置传输鉴权，开发者无需额外对每条长连接消息进行 Webhook 的解密验签。若以后改为 Webhook，应按对应规范启用验证，不可把长连接的处理假设直接搬过去。
- 长连接只要求服务器能访问公网；最多 50 个连接；同应用多个客户端按集群模式投递，只有随机一个客户端收到消息，不广播。
- 回调需要在 3 秒内响应。应用应先保存事件并返回“已收到，正在核验”，异步完成文档读取、视觉识别和其他慢操作。不能等待大模型完成后才 ACK。
- CLI 本机 `event list --json` 确认有 `im.message.receive_v1`、`card.action.trigger`、`task.task.update_user_access_v2`；未列出 `drive.file.edit_v1` 与 `calendar.calendar.event.changed_v4`。此处是 **CLI 1.0.87 的封装边界**，不表示飞书没有这些事件。

来源：[官方长连接回调](https://open.feishu.cn/document/event-subscription-guide/callback-subscription/step-1-choose-a-subscription-mode/configure-callback-request-address.md)、[本地卡片说明](/Users/pc2026/.agents/skills/lark-im/references/lark-im-card-action-reply.md:8)、[本地事件说明](/Users/pc2026/.agents/skills/lark-event/SKILL.md:61)。

**建议：** 一个 FeishuGateway 统一接收消息、卡片、日历和文档事件，然后写入数据库 inbox。先校验 app/tenant/绑定用户，再用 event_id 去重；将耗时任务排入后台。该 SDK 连接成为应用唯一入站者，避免再启动同应用的 CLI event bus 或另一套不完整 handler 的连接，造成事件被其他客户端取走。横向扩展前先做 leader/lease 或所有实例完整处理器与共享持久队列。

**ACK 源码核实：** 官方 Node SDK 提交 `394c83092395a51402ee408b751d7f9fb05f5518` 中，`EventDispatcher.invoke` 等待注册的异步 handler 返回；`WSClient.handleEventData` 等待 dispatcher 返回后才发送响应，handler 抛错时响应码为 500。因此直接使用 `WSClient + EventDispatcher` 可以在 handler 中 `await` 短小的本地耐久写入，再返回接收确认；该路径不是无条件提前 ACK。不要将 CLI 的“自动响应”或其他高层 Channel 封装混同这一行为。固定安装版本仍需回归测试，不能把主分支代码当所有历史版本的保证。[dispatcher 源码第 123–135 行](https://github.com/larksuite/node-sdk/blob/394c83092395a51402ee408b751d7f9fb05f5518/dispatcher/event.ts#L123-L135)、[WS 响应源码第 714–734 行](https://github.com/larksuite/node-sdk/blob/394c83092395a51402ee408b751d7f9fb05f5518/ws-client/index.ts#L714-L734)

接收成功必须在持久化返回后才报告，磁盘失败不能假装接收成功；本地写入需在 3 秒预算内结束。平台重推和长连接重连不等于无限期事件日志：应维护断线时间水位，普通私聊消息在权限允许时补拉近期历史并按 message_id 去重；卡片动作若未耐久保存则不产生审核凭证，用户可查看状态再重试，不能从“卡片看起来点过”重建批准。SDK 未识别事件也可能返回响应，必须启动前验证 handler 完整性。

**服务器坑：** CLI 无界 `event consume` 把 stdin EOF 当作退出信号，systemd 默认 `StandardInput=null` 会导致立即退出；CLI stdout NDJSON 也不是耐久队列。若选 CLI 事件进程，需要父进程持续保留 stdin、读取 stderr ready 标记、持久化 stdout，并监测丢弃警告；不要将进程存在等同“机器人健康”。[本地事件子进程契约](/Users/pc2026/.agents/skills/lark-event/SKILL.md:67)

### 2.2 双身份分工

| 场景 | 建议身份 | 理由与边界 |
|---|---|---|
| 机器人接收消息、下载发给机器人的笔记、发送提醒/审核卡 | bot / tenant_access_token | 助理以自身身份服务用户，绑定同一 app 下的 open_id |
| 查询和管理用户自己的日程、任务、备忘文档 | user / user_access_token | 用户资源按用户的 ACL 和授权范围访问 |
| 获取个人笔记文档的编辑通知 | 优先 user 订阅 | 用户拥有其创建文档；逐文档订阅仍需管理权限 |
| bot 自有文档或其他共享资源 | bot，仅明确授权资源 | bot scope 不自动给予用户个人文档的访问权 |

每一条 CLI 调用显式指定 `--as` 和固定 profile。CLI 的身份优先级为显式参数、profile 默认值、凭证推断；不显式指定会使跨命令行为漂移。`open_id` 与应用关联，不可直接拿另一应用的 open_id 作为新应用绑定。user 操作需要应用后台开通权限和用户 OAuth 同意两层条件；scope 不足与某个资源 ACL 不足分别处理，不能靠静默换身份绕过。[本地共享规则](/Users/pc2026/.agents/skills/lark-shared/SKILL.md:57)、[官方消息接收 ID 说明](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)

**建议：首次绑定** 由服务器生成一次性随机绑定挑战，操作者在服务器授权界面和飞书机器人私聊中完成关联；验证 `app_id + tenant_key + owner_open_id` 一致后才启用个人数据工具。授权用户身份必须与绑定的主人一致。不可把“第一个给 bot 发消息的人”自动当主人。首版无需读取全部通讯录或所有群消息。

### 2.3 授权续期

**已证实：**

- 需要 `offline_access` 才能取得 refresh token。refresh token 单次使用；刷新会产生新的 token，需要保存轮换结果。access/refresh 的有效期必须按返回字段计算，不能硬编码“2 小时/7 天/30 天”。撤销、过期、用户离职、失去应用可用性等都可能要求重新授权。
- 截至本次调研，官方 v2 刷新页已标为历史版本，最新页为 `POST https://accounts.feishu.cn/oauth/v3/token`，推荐表单编码，兼容 JSON；规范还写明用户授权 365 天后需重新授权。
- 官方 CLI 主分支 `GetValidAccessToken` 会按 token 状态触发刷新；刷新链路有进程内和跨进程存储锁及持久化控制。这证明 CLI 已考虑刷新，不等于本机 1.0.87 已验证适配最新服务器全部行为。

来源：[官方最新刷新规范](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/refresh-user-access-token-v3.md)、[CLI 自动刷新源码](https://github.com/larksuite/cli/blob/main/internal/auth/uat_client.go)、[CLI token 锁](https://github.com/larksuite/cli/blob/main/internal/auth/token_lock.go)。

**建议：** 同一服务器由 CLI 作为用户凭证唯一管理者，24PA 调用其 API 命令，不复制 refresh token 给另一个自制刷新器。固定服务账号、profile、版本与凭证存储；健康检查只保存脱敏状态。将 user 失效与 bot 失效分开：user 失效时暂停私人资源同步，用仍可用的 bot 提醒本人重新授权；若 bot 链路也失效，只能靠服务器外部监控/管理员日志告警，不能声称会由坏掉的同一链路通知。

**待验证：** 在目标 Linux/容器服务器上无交互凭证存储、重启持久化、并行 CLI 刷新、最新 OAuth/DPoP 配置兼容性与灾难恢复。应以固定安装版本做验证，不以 GitHub main 代替部署版本。

## 3. 文档、图片、任务和日历的可用能力

### 3.1 笔记输入和文档生成

**事实：** 收到图片消息后，可用配对的 `message_id + image_key` 下载二进制：CLI `im +messages-resources-download --type image --as bot`，底层为 `GET /im/v1/messages/:message_id/resources/:file_key`。机器人须在该会话中，消息和资源必须匹配；保密/不可见/删除的资源会失败。当前官方规范：图片完整下载须小于 100 MB；文件大于等于 100 MB 可使用 Range 分片，单片不超过 32 MB。首版应另设较小产品上限，不能默认所有 CLI 封装都实现 Range。[官方资源接口](https://open.feishu.cn/document/server-docs/im-v1/message/get-2.md)、[本地下载命令](/Users/pc2026/.agents/skills/lark-im/references/lark-im-messages-resources-download.md:5)

**事实：** CLI `docs +create` 可从 XML/Markdown 创建文档，返回文档 ID、revision、URL、warnings；`+update` 支持按块替换/插入/移动以及局部更新；`+fetch --detail full` 返回内容、revision 和 reference_map。图片不能当普通文本占位符；`+media-insert` 将创建资源块、上传、设置 token 编排为命令。不要把消息用的 image_key 与云文档 file_token 混用。[创建](/Users/pc2026/.agents/skills/lark-doc/references/lark-doc-create.md:15)、[编辑](/Users/pc2026/.agents/skills/lark-doc/references/lark-doc-update.md:24)、[回读](/Users/pc2026/.agents/skills/lark-doc/references/lark-doc-fetch.md:77)、[插图](/Users/pc2026/.agents/skills/lark-doc/references/lark-doc-media-insert.md:6)

**建议：** 先保存接收到的源文件字节和 SHA-256，再产生视觉处理副本。这里的“原件”是平台实际传回的字节；飞书用户端是否压缩上传照片需实测，不承诺等于相机原始文件。重要笔迹建议支持以文件发送原图。首版只接 JPEG/PNG/WebP 图片，限定具体大小、页数和分辨率；PDF 留作后续扩展。混合多页需要用户确认顺序。照片倾斜、反光、裁切缺失应先提示补拍，不强行补全字句。

### 3.2 文档版本与变更

| 已核实事实 | 对 24PA 的影响 |
|---|---|
| `+fetch --revision-id`、`+update --revision-id` 存在，默认 -1 为最新 | 可以指定读取基准；不能据此宣称写入有 CAS |
| 官方 docx 更新接口有 `document_revision_id` 和 `client_token` | 前者是操作版本；后者为更新幂等，解决重复请求，不解决审核者看到的内容与最新内容一致性 |

**分页快照事实与方案：** 官方“获取文档所有块”接口每次请求可指定 `document_revision_id`，语义是查询指定版本；查询历史版本需要编辑权限，查询最新版本只需阅读权限。建议先读元信息取得 r，然后每一页均指定相同 r，完整耗尽 page_token 后再形成候选，不能每页都传 -1。此规范提供固定版本查询语义，但本次未见额外的“整组分页作为原子事务”承诺，M0 应验证并发编辑时每页行为。发布最新待审卡前再读元信息；版本变动则按策略重新采样、重新比较或保留为明确的旧版候选，不能拼接混合版本；历史过旧/权限失败/分页中断均不批准不完整快照。外部同步块、内嵌表格、可变引用不受当前文档 revision 自动冻结，首版出现这类块时应将依赖一并快照或拒绝完整审核，不能只取纯文本跳过。[官方文档全部块接口](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/list.md)

### 3.3 日历与任务

**日历事实：** `+agenda`、`+get`、`+suggestion`、`+freebusy`、`+create`、`+update` 可满足个人计划和会议安排。需区分全天日期、时区时间、重复日程实例与例外；只改某一次与整组重复日程不可混用。[本地日历技能](/Users/pc2026/.agents/skills/lark-calendar/SKILL.md:33)、[重复日程概念](/Users/pc2026/.agents/skills/lark-calendar/SKILL.md:113)

**同步事实：** 官方日程列表支持 `anchor_time + page_token` 拉取存量，分页完成后返回 `sync_token`；随后增量拉取。`start_time/end_time` 时间区间模式不能分页，受 page_size 限制截断，不能与 page/sync/anchor 混用。游标过期错误为 190008，应清空重建。日程变更订阅接口只接受 `user_access_token`，要求 reader/writer/owner；事件中的 `calendar_event_id/change_type/rsvp_infos` 标注灰度，不能假设必有。[官方日程列表](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/list.md)、[订阅日程变更](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/subscription.md)、[日程变更](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/events/changed.md)

**任务事实：** CLI 支持创建、更新、完成/重开、指派、提醒、子任务、任务清单；创建支持幂等 key。个人任务应明确指派给主人。需要 due 才能设置重复规则/提醒；日期型 due 与毫秒时间型 due 不应混用。`task.task.update_user_access_v2` 事件反映可见任务变动，但 payload 主要是 task_guid 与变更类型，还需按权限回读任务。[本地任务规则](/Users/pc2026/.agents/skills/lark-task/SKILL.md:38)、[创建参数](/Users/pc2026/.agents/skills/lark-task/references/lark-task-create.md:37)、[任务事件](/Users/pc2026/.agents/skills/lark-event/references/lark-event-task.md:13)

**建议：** 日历和任务事件均视为“需要同步”的信号；用增量/回读刷新本地投影，并定期对账。v1 日程默认只管理主人的日历、个人时间块和其明确授权的会议；邀请他人、移动已有多人会议、给别人指派任务单独确认。

## 4. 手写笔记人工审核：推荐核心方案

以下为 **设计建议**，不是飞书原生审核能力。飞书没有已证实可直接满足本需求的“AI 内容人工审核状态字段”，24PA 应自行管理，并在文档内渲染清楚。

### 4.1 文档结构

每份笔记显示：

1. 顶部状态栏：笔记编号、内容版本、待审核/退回/历史版本审核记录、最后核验时间和审核入口。
2. 整理版：保留原意的主题、要点、决定、待办；AI 推测单独标识。
3. 疑难项：页码/区域、原图裁剪、识别候选、需用户确认的日期/人名/数字，不用模型自报百分比冒充校准准确率。
4. 原文转写：逐页逐段，保留删改、不清晰处和英文缩写；未知文字使用明确标记。
5. 原件：页序、图像/文件、来源消息链接或 ID；简单图示保留原图，文字解释与图形重绘单独标识为 AI 整理。
6. 审核记录：谁、何时、通过哪个版本、内容指纹、是否产生后续新版本。

日期相对词需保留原文，不能把旧笔记里的“明天”默认解释为上传日期的明天；图示箭头含义不明时保留原图和问号。未确认的推断不得悄悄补为事实。

### 4.2 状态机与数据

笔记处理状态：`received → transcribing → draft_written → awaiting_review`；可进入 `needs_better_source / failed / changes_requested / archived`。

审核对象是独立的 `ReviewCandidate`：包含 `note_id、candidate_version、source_asset_hashes、source_order、document_id、observed_revision、canonical_content、content_hash、renderer_version、created_at`。候选提交后不可原地改变；任何正文更改生成新候选和新审核请求。

审核请求 `ReviewRequest` 绑定候选、目标用户、卡片消息、会话、过期时间、一次性 nonce 和状态。审核记录 `ReviewReceipt` 只追加：候选 hash、审核者 app/tenant/open_id、回调 event_id、审核时间、决定。通过唯一请求 ID 与受控的原子状态更新保证一个 request 最多产生一个有效决定；底层若只提供单记录原子更新，就将请求状态和审核凭证摘要放入同一聚合记录提交。

`approved_snapshot` 和 `current_content_verification` 分开保存。前者表示某份确切内容得到人的同意；后者取 `matches / changed / unknown` 并带核验时间。这样服务器断线时不会把“没收到变更”误当“没有变更”。

### 4.3 审核流程

1. **收件可靠落盘。** 校验绑定主人及媒体类型；消息去重；保存原件、来源和顺序；给出收件编号。多张照片先形成一个笔记批次，用户可完成/追加/重排。
2. **识别与整理分两步。** 视觉模型先忠实转写并定位疑难片段，再以转写和原件为依据整理。输出结构化候选，不具备执行 CLI 或批准自身结果的能力。
3. **写入草稿并回读。** 创建飞书文档、插入原件、校验 warnings/partial_success；拿到实际渲染后的正文和资源引用再建立候选，不对模型原始输出直接计算最终文档指纹。正文、标题、待办字段、图示、资源内容均纳入版本；排除受控状态栏和审核日志以避免回写状态引起无限自失效。
4. **发送审核卡。** 卡片明确“审核版本 vN”，展示摘要、疑难数量、文档链接，按钮至少为“通过此版本”“需要修改”“稍后提醒”。源文件缺失、页面未识别完、写入部分成功时不能发送可批准的完整稿卡片。
5. **可信回调入库。** 在 3 秒内完成来源、app/tenant、operator、message/chat、nonce、request状态和有效期的校验，耐久保存动作后 ACK；视觉/大模型不参与决定“谁点击了通过”。回调原生字段为 `event.operator.open_id`、`event.context.open_message_id/open_chat_id`，SDK/CLI 会做不同展开，适配层必须使用所钉版本的真实 schema。[卡片结构](https://open.feishu.cn/document/feishu-cards/card-callback-communication.md)
6. **核验当前文档并绑定版本。** 回读内容；若与卡片候选不一致，拒绝将旧卡用于新内容，创建新候选让用户重看。若一致，仅记录“候选 vN 内容 H 被此人批准”，再更新文档投影和卡片。即使核验与写入之间有人又编辑，也不能把批准扩张成“此刻及以后全部内容被批准”。
7. **编辑后失效。** 收到文件编辑事件、定时对账或再次使用笔记前回读发现正文 hash 改变，标记当前内容为待审核，旧审核仍保留为历史记录；新卡片取代旧卡。忽略自身状态栏回写应靠内容范围/hash判断，不能简单忽略“操作者是本人”，因为 user token 下的机器人和本人修改可能同一用户。
8. **批准内容不等于批准行动。** 提取出的 task/calendar/reminder 先作为建议显示。用户可在另一个明确的动作中批准“创建这 3 个待办”，该动作绑定所选条目、截止时间、身份和版本，防止一键审核转写意外向同事发邀请。

### 4.4 防止“改后仍显示通过”的真实保证边界

**不能承诺：** 在任意人在飞书客户端随时编辑、事件异步、网络可断的条件下，用普通可编辑文档实现一个零延迟、永久准确的绿色“当前全文已审核”章。前置读取 + 写后读取能缩小竞态，不能代替跨系统事务或服务端 CAS。

**v1 推荐语义：** 文档顶部始终写限定声明，例如：

> 待审核：当前整理稿 v4。历史记录：v3 于 2026-10-05 由你人工审核通过；该通过只适用于审核快照，后续修改需重新审核。最近同步核验：……

通过时可写“**版本 v3 已人工审核通过**”，同时给出审核快照与时间，明确后续编辑不在该通过范围内；不要仅写“本文已审核”。网络断开时旧的历史声明仍为真；“当前最新状态”经事件/轮询刷新，在用户再次依赖内容时强制重新核验。若要求任何时候读文档都绝不看到对最新内容的误标，采用 **独立审核快照 + 可编辑草稿**，批准始终指向不可变快照，而非活文档。

**实现边界：** 24PA 自有存储中的候选快照才是不可变记录；一个普通飞书副本并非天然不可变，即使设为仅查看，所有者/管理员仍可能改变权限或编辑。飞书版审核快照是展示副本，需 hash 校验。可以附加冻结 PDF/源内容包便于查证，但不把历史 revision API 当永久归档。

**模型隔离：** “批准”只能由可信入站控制器调用，不能作为 LLM 可调用的工具。模型工具只允许创建候选、提议修订、查询状态。模型应无审核账本写权限；保护 nonce、密钥和事件原始材料。若 dsh 的通用终端工具可直接改账本或绕过 CLI 策略，这个保证会失效，需由插件使用受限 preset/tool集合和独立文件/进程权限实现，不能只靠 prompt。

### 4.5 卡片时效

卡片回调 `event.token` 用于延迟更新，有效 30 分钟、最多两次；它不是业务审核授权凭据，也不是审核请求寿命。业务审核可设 7 天有效，到期重新发起。超出 token 时窗后，可在满足约束时使用 message_id 更新已发共享卡片；该 API 限 14 天内、同一发送身份、未撤回卡片，且更新前后 `update_multi=true`。再过期则发送新结果通知，旧按钮在后台仍须被拒绝，不能依靠按钮变灰保障幂等。[卡片回调](https://open.feishu.cn/document/feishu-cards/card-callback-communication.md)、[更新消息卡片](https://open.feishu.cn/document/server-docs/im-v1/message-card/patch.md)

## 5. 主动提醒的可靠实现

### 5.1 发送与幂等

**事实：** bot 发送给用户要求机器人能力已发布、用户在可用范围；群发送要求机器人在群内且有发言权。首版主动提醒统一发给已绑定主人的 open_id。官方规范未规定“必须在用户上次说话后 24 小时内”这样的发送时窗；不能将其他平台的会话窗口规则套到飞书。为消除 CLI 指引对私聊关系的额外要求，绑定时让用户主动向 bot 发一条消息，并在开发验证中核实实际发送路径。[官方发信](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)、[CLI 发信备注](/Users/pc2026/.agents/skills/lark-im/references/lark-im-messages-send.md:263)

**事实：** API `uuid` 最大 50 字符，相同 uuid 在 1 小时内最多成功一条；这不是跨天永久 exactly-once。CLI `--idempotency-key` 映射该能力。[官方发信](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)、[本地发信参数](/Users/pc2026/.agents/skills/lark-im/references/lark-im-messages-send.md:180)

**建议：** 持久化通知 outbox，唯一键由 owner、提醒对象、对象版本、提醒时点/渠道组成。一个业务通知只有一个稳定 uuid；重试同一通知复用，修改后的新通知换 uuid。保存返回的 message_id、尝试次数、首次尝试时间、下次重试时间、投递结果。处理“飞书收到了但HTTP响应丢失”为 `delivery_unknown`；尽量在平台去重窗口内重试，窗口外先对账，不盲目无限重发。不宣称绝对不丢不重。

### 5.2 调度与体验

**建议：**

- 可靠定时器只负责唤醒；每次从持久数据取到期项，不依赖内存 setTimeout 维持一天。使用租约锁防两个 worker 同时发，重启后补偿扫描。
- 日历事件变化后重新计算提醒；取消、拒绝、重复日程例外要使旧提醒失效。发送前再确认最新状态，避免已取消会议继续提醒。
- 超过新鲜度阈值的同步数据，不当作确定事实自动发出“即将开会”；可提示“最后同步的安排”，或暂缓并单独提示同步异常。
- 个人时区默认 Asia/Shanghai，服务器内部时间用 UTC；日程自身时区与全天日期独立保存。按用户的 quiet hours、优先级、暂停/稍后提醒、每日通知预算合并普通提醒。
- 首版范围：会议提前提醒、个人重要事项、任务截止/逾期、笔记待审核提醒、可选晨报/晚间回顾。日历/飞书 task 原生提醒与 24PA 不能默认同时多轮轰炸，先选主提醒源。
- 收到“我知道了”、完成任务、稍后提醒的卡片动作后，更新自己的状态和必要的飞书状态；送达和已读都不等于任务完成。
- 授权前明确提醒种类、对象只限本人、默认时段和频率；此后规则内自动发送，不为每次提醒弹确认。转发给他人、群公告、短信/电话加急不包含在该长期授权中。

## 6. 权限与工程封装建议

建议分阶段开通，不申请 `--domain all` 作为生产默认。以下是已核实接口的候选最小权限，不是已联调通过的完整 manifest；CLI shortcut 的实际底层权限需在批准后的安装验证中逐命令确认。

| 能力 | 已核实候选 scope / 条件 |
|---|---|
| bot 发信 | `im:message:send_as_bot` |
| 下载给 bot 的消息资源 | `im:message:readonly` 等三选一，且同会话 |
| 卡片回调 | 回调订阅本身无额外 scope；依赖机器人、订阅配置与绑定用户；需要回读消息时再按 API 授权 |
| 日程读取/日程变更订阅 | `calendar:calendar.event:read` 等三选一；订阅为 user 身份 |
| 云文档编辑通知 | API 订阅可用 `docs:event:subscribe`；事件接收可用 `docs:event.document_edited:read`；另需文件管理 ACL |
| 任务读写 | `task:task:read` / `task:task:write`；任务清单另有 scope |
| 长期用户授权 | `offline_access`，实际业务权限与用户同意另外授予 |

来源见各节接口与[任务权限表](/Users/pc2026/.agents/skills/lark-task/SKILL.md:150)。

CLI Adapter 应使用参数数组执行固定可执行文件，避免 shell 拼接；只允许已注册的命令/参数，raw `api` 只能由受控代码调用白名单端点。成功判定使用 CLI 的 `ok=true` 和退出码，同时看 `result=partial_success`/warnings，不按 OpenAPI 的顶层 code 格式误判 CLI 结果。输出中身份、文档 ID、版本、资源与返回路径要作类型校验；用户路径、OCR文字和回调 action_value 均不能直接变成命令参数结构。[CLI 返回契约](/Users/pc2026/.agents/skills/lark-shared/SKILL.md:185)、[文档更新返回](/Users/pc2026/.agents/skills/lark-doc/references/lark-doc-update.md:77)

云端超时后先对账，不能直接重跑整条“建文档→插图→发卡”。维护各阶段 operation ledger：对象已创建而链接回写失败时继续后半段；同一张图片重试不会反复插入；任务/日程创建按各 API 的实际幂等语义处理。遇到 CLI 的 high-risk exit 10，先核实当前具体动作、目标和参数是否已有有效的明确用户授权；已有授权时按 CLI 要求携带该授权执行，无需重复征求同一授权；没有授权才生成具体确认对象。不得做通用的自动追加 `--yes` 重试器绕过门禁。此规则用于开发后的实际业务操作，不改变本轮“只设计、批准后才能开发”的范围。[CLI 高风险门禁](/Users/pc2026/.agents/skills/lark-shared/SKILL.md:210)

## 7. 批准开发后必须先做的验证

1. **长连接全链路：** 固定 Node SDK 版本，同时接收消息、卡片、Drive、Calendar；断线重连、重复 event_id、乱序、服务器重启、多个连接抢占。检查 ACK 前持久化失败是否正确重试，3 秒内完成本地路径。
2. **服务器授权：** 固定 CLI 版本、服务账号和 profile；用户 OAuth、bot identity、凭证持久化、并发刷新、撤权/过期恢复；不读取或迁移用户本机私人凭证。
3. **手写样本：** 用户提供代表性中文夹英文样本（无需本轮提供），涵盖人名、数字、删除线、TODO勾选、表格和简单箭头图；评估字符错误、关键字段错误、疑难漏标和人工修改量。
4. **原件与文档保真：** 多页顺序、图像分辨率、PDF页转图、飞书上传压缩差异、图片 token/块关联、XML回读的结构和引用变化、partial_success；来源丢失时禁止当成完整稿。
5. **版本一致性：** 读取时并发编辑、点击通过前后编辑、更新状态栏时正文被改、延迟/漏事件、CLI写后revision变化、历史版本过旧；所有情况都只能批准特定快照，不能把新内容继承通过。
6. **审核鉴权：** 其他人点击、转发卡片、伪造action value、过期/重放nonce、多次点击、两张不同版本卡片并发批准；模型工具/终端不能绕过人工批准入口或直接写审核账本。
7. **提醒可靠性：** 会议取消/改期/拒绝、重复实例和例外、sync_token过期、时间区间截断、HTTP成功响应丢失、超过1小时去重窗口、夜间静默、重启补发、积压去重。
8. **准确边界：** 飞书不保证视觉识别准确率，也未在本次材料里提供文档原子审核CAS；不以“待验证”内容作为已经验收的能力。先完成上述技术验证再定生产SLO、数据保留策略、单笔页数和成本上限。
