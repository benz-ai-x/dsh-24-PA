## 核查结论

F51 值得保留，但建议改成“入口分层与实际界面减法”。四入口是可比较的候选布局，不能把“标签更少”直接当作使用成本更低。应保留今日工作附近的日常 Skill 执行、定时任务、异常处理，将包编辑和接入维护收进设置。现有“手写审核”实际已管理多种资料，应按“资料与审核”梳理，不能当成手写专用模块整体裁剪。

F51 没有等待 F49/F50 完成的技术硬前置。可先盘点、设计、清理无引用组件和调整导航；上线时对仍存在的语音/旧计划能力保持可达，后续功能退役再清理对应叶子视图。三个功能都修改 `client.js`，这是变更协调和整合测试要求，而非业务依赖。

## 当前产品界面究竟是什么

当前是一个 dsh 主面板和侧栏入口，顶部保留唯一的本地助理对话按钮；没有单独注入 dsh 设置页。一级为首页加四分类，分类下共有 16 张卡，再进入业务详情。当前卡片是统一注册表中的数据，每张卡主要负责归类、摘要、状态和详情组件绑定。[client.js L1–16、L671–677、L2705–2911、L3843–3848](../../packages/24pa/client.js)

```mermaid
flowchart LR
  H[首页：工作规划和业务摘要] --> N[内部导航函数]
  C[四分类与16张能力卡] --> N
  N --> V[现有领域详情组件]
  V --> R[面板 RPC]
  R --> S[原领域服务与账本]
```

## 对 F51 草案的具体修订依据

### 1. 常用 Skill 执行不能和包管理一起全藏到“高级”

**需调整。** 当前 Skill 页面并非单纯“开发者编辑器”。它同时提供目录、运行限制、参数、手工运行、试运行、运行记录和结果核验；`SkillsDetail` 的 overview 实际挂载 `SkillRunControls`。后端也已把只读管理、包变更和运行分开：`SkillManagement` 只读定义和包，`runtime.changeSkill()` 与 `runtime.runSkill()` 是不同入口。[client.js L2202–2376、L2507–2701](../../packages/24pa/client.js)；[skill-management.ts L36–95](../../packages/24pa/src/skill-management.ts)；[runtime.ts L799–810](../../packages/24pa/src/runtime.ts)

草案若整体移到“设置 → 高级 → Skill 管理”，所有操作技术上仍在，但用户发起常规任务必须经过维护层级。建议只将新建/导入/包编辑/版本发布/下载等完整管理放高级区，日常浏览可运行能力、预览、手工执行和查结果保留在今日工作。复用同一 Skill 身份、运行快照和权限，不额外做一个执行引擎或第二套目录。

### 2. 定时任务已经统一到一个主要界面，不宜再当“系统设置”

**需调整描述与落点。** 现行 `digest` 卡已经绑定 `TaskPlansDetail`，新建晨报/晚间复盘/周回顾按钮写的是通用计划表单；旧 `DigestDetail` 只挂载在“兼容与历史”折叠区。旧控制还活跃，不能说“旧简报页面已完全退役”，也不能把新建统一入口再开发一遍。[client.js L1693–1754、L1817、L2776–2787](../../packages/24pa/client.js)

这个页面处理的是任务的启停、运行、重新授权、目标绑定和异常，不只是静态参数。首页已有“下一次定时任务”及“管理定时任务”，可直接进入指定计划；此路径值得保留并增强。[client.js L3502–3517、L3751–3753](../../packages/24pa/client.js)

建议 F51 把“周期服务/定时任务放设置”改为“日常计划管理与启动入口留在今日工作；接入、默认参数及高级定义管理收进设置”。F50 负责旧控制的收口，F51 负责可发现性与布局，两者验收分开。

### 3. “手写审核”现在是多来源资料审核，不是只有 OCR

**需要显式保护通用链路。** `ReviewView` 使用 `materials` API，列表区分 `images / transcript / minutes / quick-note`；详情包括原稿/来源、识别、草稿、冻结版本、候选行动，允许保存草稿、发布待审、核验、重发审核入口、授权执行行动。听记详情也直接跳转这个页面。[client.js L378–489、L1072–1096](../../packages/24pa/client.js)

`runtime.materialSnapshot()` 同样返回 materialType，`changeMaterial()` 承接 save_draft / verify / resend 及其他资料动作，而非仅手写识别。[runtime.ts L3942–3967](../../packages/24pa/src/runtime.ts)

因此建议把展示名收敛为“资料与审核”，保留手写和听记两个来源标签。D01 若未来决定不再投资图片识别，仍需单独确认图像入口、识别流水线与通用资料审核各自范围；不能从当前卡片名称推导整个审核流程可删。

### 4. QwenNote、Wiki 和来源登记只能合并导航，不能合并数据模型

**方向合理，需补非目标。** 两张卡当前已在“接入与设置”分类；本轮是减少独立卡片和重复说明，不是将原业务入口首次移到设置。

- QwenNote 是本地对话按需读取的外部工具，页面显示放行、挂载和调用回执；普通刷新不读取听记。[client.js L1072–1096](../../packages/24pa/client.js)；[runtime.ts L3932–3939](../../packages/24pa/src/runtime.ts)
- Wiki 是备忘/待审文档的输出节点，可回退 folderToken，不是一般检索资料源。[client.js L1054–1068](../../packages/24pa/client.js)
- 现有 `SourceConfiguration` 的领域只有 `calendar | todo`，身份和资源核验也按这两个领域组织。没有“所有连接器共同来源注册表”。[source-config.ts L3–35、L70–109](../../packages/24pa/src/source-config.ts)

建议设置按“平台接入 / 日历与待办来源 / 听记工具 / 文档落点”分组。明确本票不扩展 SourceDomain，不把 Wiki 塞入日历/待办来源结构，不改变 QwenNote 的本地权限。不要把这张减法票扩大为通用连接器框架建设。

### 5. “旧深链迁移”应准确限定现有内部跳转

**需澄清验收对象。** 当前没有面板 URL 路由、hash 路由或可复制的对象深链。`tab/detail/detailPreset` 是 React state；`openCard/openRuns/openPlan/openTodos/openCalendar/openRepair` 携带内部 ID、筛选和配置锚点，切换页签由 setState 完成。[client.js L3634–3755](../../packages/24pa/client.js)

实际持久化的是浏览器 `localStorage['pa24.panelCards.hidden']`，按分类保留卡片显隐，`CATEGORY_MIGRATION` 已按卡片 ID 迁移分类；其并非服务端工作区数据。计划、运行筛选和编辑状态主要存在 Panel 的 Map/组件 state，不能把它描述为已有跨刷新持久路由。[client.js L671–692、L1482–1494、L3634–3652](../../packages/24pa/client.js)

建议改成“保持内部导航目标、筛选、计划/运行身份和有效配置锚点；旧卡显隐偏好按能力 ID 解释。新布局无卡片时保留旧偏好记录，不把隐藏偏好转为能力停用”。不要顺带要求建设全新的 URL 路由或服务器端偏好迁移。所有待处理入口必须能从首页摘要进入，不受隐藏卡片影响。

### 6. 只有改导航不足以形成可证实的代码减法

**可落实的优化。** 当前 `WorkDetail`、`ActivityDetail` 在整个客户端只有函数定义，无组件挂载引用；实际待办和运行卡已经分别使用 `TodoDetail`、`RunHistoryDetail`。`client.test.mjs` 仍以文本包含断言要求旧函数存在。这是清理无引用代码的候选，不是删业务能力。[client.js L760–823、L2712–2741](../../packages/24pa/client.js)；[client.test.mjs L48–74、L225–232](../../packages/24pa/tests/unit/client.test.mjs)

`useExtra` 在挂载和首页 30 秒刷新时并行读取 `home` 以及 `minutes / memory / health / budget / roles / reminders / digests`；切换卡片分类或隐藏卡片不改变这批读取。其中 `extra.roles` 只在无挂载的 WorkDetail 中使用。把 16 卡挪入设置，仍保留这一加载结构，不会减少这些请求。[client.js L694–721、L760–788、L3683–3688](../../packages/24pa/client.js)

建议在 F51 中列明有限清理项：复核后删除无引用旧视图；移除已无消费者的 `roles` 补充读取；设置详情按需读取完整内容；首页保留业务摘要与明确需要的阻断信息，不为了减少请求删掉异常。这里不声称这些本地只读请求造成生产性能瓶颈，真实耗时仍未测。

### 7. 四入口不是必须同时改所有内部契约

`PANEL_RPC` 的查询与动作独立；导航通过组件注册和内部跳转选择详情。其首页组合快照重用日历/待办/审核/计划/运行/规划查询，普通读取与主动核验已经分开。[panel.ts L17–188、L228–288](../../packages/24pa/src/panel.ts)；[runtime.ts L474–538](../../packages/24pa/src/runtime.ts)

因此 F51 没有技术理由要求 F49/F50 已合并才开始或才能交付所有导航改进。建议取消原生硬阻塞；保留共同文件修改协调、整合后复验，以及退役后的入口/文案最终清理清单。F49 管语音路径、F50 管旧计划行为、F51 管入口和加载，不在三票同时重写同一套计划/权限/运行服务。

## 建议写回 #272 的目标契约

1. 四入口暂作为候选信息架构：今日工作、工作对象、运行记录、设置。先用当前已实现流程比较导航前后，明确每个入口是直接业务视图还是另一层卡片；确认后冻结布局，防止“四个标签 + 原16卡原样堆叠”。
2. 今日工作沿用现有计划建议/采纳/复盘及业务摘要，提供常用 Skill 执行、定时任务管理、待处理事项和异常直达。高级包管理与接入参数放设置。
3. 工作对象包含待办、日程、资料与审核、记忆查阅。待办、助理交办、定时任务、资料版本和长期记忆继续是不同对象，不随导航合并改变权威。
4. 运行记录直接进入既有执行/交办/未执行事件三视图，保留旧历史定位、停止、补充、接续、核对、补投与结果核验。
5. 设置合并卡片组织和重复说明，区分平台连接、日历/待办来源、听记工具与文档落点；复用原配置保存、生效回读、权限和未知结果机制。
6. 保护全部内部跳转、配置锚点、选中对象、有效筛选、未保存草稿及工作区归属；新增 URL 深链不属于本票。
7. 给出具体删除清单与按需加载清单，以活跃调用者和可观察网络请求证明，不以界面隐藏证明代码退出。
8. F49/F50 没有合并时仍可保留原兼容叶子视图；它们退役后按事实移除对应控制，历史视图仍可达。只有共同文件整合与最终回归有顺序约束。

## 验收应补充的具体场景

| 场景 | 必须验证的用户结果 |

| 从今日工作执行一个已允许 Skill | 找到能力、预览参数与权限、明确启动、查看原运行；包编辑不成为必经步骤。 |
| 管理周期计划及旧迁移问题 | 从首页下一次计划或阻断摘要进入原计划；暂停、启用和迁移问题不因收进设置而丢失。 |
