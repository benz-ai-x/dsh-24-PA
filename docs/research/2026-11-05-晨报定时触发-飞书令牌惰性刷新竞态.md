## 接口行为（实测）

- 飞书用户 access token 有效期 **2 小时**，lark-cli **惰性刷新**：只在下次调用发现过期时才调 `/authen/v2/oauth/token`；夜间无使用则令牌隔夜必过期。
- refresh token 随每次刷新顺延 **7 天窗**（11-05 08:00 刷新 → refreshExpiresAt 11-12 08:00 整，可反推）；grant 断档即用户身份整个 missing（10-17 grant 的 refresh 10-24 过期，10-25～11-02 晨报因此静默）。
- `auth status --verify` 在令牌过期时的表现（**竞态**）：该次调用内部先惰性刷新（oauth/token 200）、再验用户（user_info 200），但**首个回执仍可能带刷新前的一致性结论**，守卫据此判死。生产两天同模式：
  - 11-05 08:00:00.735 刷新 200 → 08:00:00.827 user_info 200 → **08:00:00.844 触发 rejected**「固定飞书 profile 的应用、有效用户令牌与主人身份尚未核验一致。」
  - 11-03 08:00:00.845 / 0.933 / 0.945 同构。
- 复现补充（11-05 10:00:10 探针）：到期后首查确会触发惰性刷新（日志 200×2）。回执原文因长连接断连未捕获；keepalive timer 上线后本机无冷窗，信封级实锤留待再遇时补。

## 放大链（为什么之后彻底哑火）

准入拒绝 → `task_plan_block`（kind=authorization）写入并同事务置计划 paused（repo/task-plan.ts block）→ `reconcilePlans` → `pausePlan` → `plans.stop` **删除原生 schedule 任务** → 次日 08:00 连触发都没有。恢复需面板「解除阻断→启用」。第二层静默根因：计划 `delivery.mode='errors'` 按设计成功不推送（已改 always）。

## 方案取舍

| 方案 | 判定 |
|---|---|
| `identity()` 绑定匹配而结论未过时隔 1.5s **重读一次**（已实施） | 刷新在首次调用内已完成（日志可证），第二次读取必见新态；单次重读、有界、文案不变 |
| 重读门收窄到 `tokenStatus` 过期 | **否**：事故回执未捕获，无法证明陈旧字段是 tokenStatus 还是 verified；两者都由令牌态派生，绑定（appId＋owner openId）匹配才是「重读有意义」的正确边界 |
| 绑定不符也重读 | **否**：重读只会掩盖真实配置不一致 |
| 令牌保温 timer（运维层，已上线） | 90min 一次 verify，令牌永不过夜冷；顺带 refresh 7 天窗不再断档。属缓解，非代码兜底的替代 |
| 上游修 lark-cli | 正解但不可控（Go 二进制闭源），留待上游渠道 |
