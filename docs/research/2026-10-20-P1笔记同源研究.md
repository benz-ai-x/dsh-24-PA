# P1 待审正文与派生候选同源研究（V01）

功能组 C，#209；V03 原渠道恢复先验收，再实施本项。规格沿用 F06/F11、[既有知识版本契约](2026-10-19-R3-C知识版本与行动契约.md)，不改变本人内容审核与行动授权分离的规则。

## 已核验事实

当前 lark-cli 1.0.87 生产 reader 使用完整 XML、revision_id 和实际下载媒体摘要；第二次读取确认 revision 未变化。它保证实际文档快照一致，不能证明早先模型识别的摘要/候选就是该正文。首次发布当前把回读正文和旧 recognized 合并，正是缺口；重发已清空旧派生并 needs_rebuild。

noteDocumentXml 是本仓库版本化模板。canonicalDocument（saxes 6.0.0）保留标题与结构，忽略平台 ID/token 和登记系统状态行；同 token 换图片、重排结构或业务文字改变会影响审核指纹。生成时还未上传图片，因此派生来源比较排除 image 节点，正文仍严格按相同 XML 规范化；独立的资源完整性校验和最终全文指纹继续约束图片字节与位置，不降低审核要求。

## 实施决策

先将实际回读正文与生成 recognized 对应的模板正文比较。相等时把派生字段摘要、来源正文摘要及完整指纹作为同一版本内的同源证明持久化；不相等或纯正文重发时清空旧转写、摘要、行动、疑点、建议和相对日期，明确 needs_rebuild。恢复已提交版本只补原发布流程，不重新拼装新旧内容。

所有派生消费共用同一验证入口：候选采纳、可信检索、概览/回顾和审核卡。不具备同源证明的旧已批准版本不获得新可信性，保持历史凭证与既有外部对象，提示重新整理当前内容。摘要字段再次被改变也不能继续沿用旧证明。

沿用现行 R3 约定：本人可审核当前正文；若派生资料尚未重建，卡片与回执明确仅批准正文，旧候选始终不可执行，正文批准不等于新候选的内容批准或行动授权。标题/媒体仅按已定规范化规则等价，不因本项扩大可忽略正文范围。

## 验收入口

公开 Runtime note_submit → 审核卡 → note_adopt_actions/notes_search，以及真实发布恢复 module seam。SQLite/PG 两库验证初发/重发人名、日期、行动删除、疑点变化；无修改与元数据等价对照；旧批准缺证明、恢复和历史凭证不变。真实 Loader 再验证端到端审核与行动；外部 CLI 受控，真实账号兼容与手写准确率仍归 #46，V02 独立保留。
