# 功能 PR 交付流程

领取或推进实施 Issue、规划分支、创建或合并 PR 时使用本流程。一个功能 PR 交付可独立使用的用户流程，可包含多张 Issue；每张实施票只有一个主交付 PR。

## 定位与推进

1. **确定归属**：读取 [PR 交付计划](../planning/24PA-v1-PR交付计划.md) 中对应分组及专项计划，核对相关 Issue，列明本次范围、同组前置和跨组前置。若一票跨两个功能，先拆清交付与验收归属。
2. **核对基线**：按 [产品基线](product.md) 确认授权范围、目标版本和研究结论；功能分组的历史描述不覆盖后续已确认修订。缺失的关键路径研究补齐后进入开发。
3. **复用分支**：已有对应功能分支或 Draft PR 时继续使用；否则为该功能建立分支。组内按 Issue 分次提交、交接，完成单票后继续所属功能分支。
4. **记录进度**：每票保存实现提交、验收命令／结果及未完成项。按下表判断下一票能否推进；后续修改影响前置行为时重跑相关验收。

## 依赖与关闭

| 场景 | 满足条件与动作 |
|---|---|
| 同一功能 PR 的前置 | 代码已在功能分支且对应验收通过，即可推进下一项；记录「已实现，待功能合并」，Issue 保持打开。 |
| 跨功能 PR 的前置 | 前置功能已合并到默认分支且所依赖 Issue 验收通过；更新当前功能分支后继续。关闭状态或未合并提交本身不足以证明依赖可用。 |
| 转为可合并 | 全部前置、组内验收与完整操作演示通过，并满足下方合并标准；可以提前创建 Draft PR 供审阅。 |
| 关闭实施票 | 所属功能 PR 已合并且本票验收通过；PR 关联全部实际交付的 Issue，未完成事项保持打开。 |

GitHub 的 open/closed 与原生阻塞关系保留事项事实；组内推进另查提交和验收证据。领取、Frontier 与 Resolve 均用这套判定，操作方式见 [GitHub 事项约定](issue-tracker.md)。

## 合并标准

- **功能完整**：PR 说明原问题、交付后可完成的操作与覆盖 Issue；用输入、结果和实际对象依据演示完整流程。所需迁移、配置、用户入口、结果反馈和使用说明随功能交付，合并后只依赖已合并功能。
- **业务验收**：按目标基线及 v1 规格的 [Testing Decisions](../24PA-v1-SPEC.md#testing-decisions) 执行真实 dsh Loader、Session 与持久化验证；保留隔离 PostgreSQL 验证，并按默认 SQLite／可选 PostgreSQL 的存储契约覆盖受影响后端。模型、外部网络、时钟可替换；超时、重复、重启、未知结果及数据库升级／恢复随对应功能验收。
- **界面验收**：界面变更执行对应 T20 与目标模块场景，只按电脑端验收，覆盖 SVG／状态文字、空／加载／错误／离线状态、明暗主题、键盘操作及 1280×800、1440×900、1920×1080 电脑视口，不做手机断点或 390px 验收；维护入口按当前产品基线，展示基于真实状态，原型交互证据不替代真实数据与行为验收。
- **外部证据**：记录对应真实平台验证的结果与边界；缺凭据、授权或样本时标明未验证。示例、原型和离线桩不能替代真实验收；v1 全量手写评测与试运行归 [发布验收 P40](../planning/24PA-v1-PR交付计划.md#发布验收-p40)，各功能自己的验证仍在合并前完成。
- **审查闭环**：合并前使用 `code-review` 做双轴审查（Standards＝仓库标准与代码异味；Spec＝PR 承诺）。全部发现清偿并经复审确认后方可合并，审查与清偿记录留在 PR。

## 交付回写

合并后按上表逐票核对验收与关闭条件，回写实际 PR、提交和验收依据；涉及产品要求变化时完成产品基线要求的文档同步。交付结束须能逐项区分已合并、已验收和待完成内容。
